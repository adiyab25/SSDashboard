# Database schema (`@ssdashboard/db`)

The Drizzle schema for every module (Better Auth tables included) and the only migration history. The api's `migrate` entry point applies the migrations; nothing else does.

Agent gotchas: [AGENTS.md](AGENTS.md).

## Never touches

- A migration that has shipped. Fix forward with a new one.
- Update or delete rights on the ledger history for the app role.
- Update or delete on `movement_groups`, `stock_movements`, `movement_serials`, `stock_receipt_lines`, `stock_transfers`, `cost_records`, `order_events`, `customer_merges`, `credit_entries`, `settlement_statements`, `settlement_lines`, `settlement_line_matches`, `settlement_period_events`, `order_cost_rules`, `licenses`, and `license_checks`. All are append only (declared in `APPEND_ONLY_TABLES`, trigger and revoke in [0002_baseline_rules.sql](migrations/0002_baseline_rules.sql), for the two license tables in [0004_license_rules.sql](migrations/0004_license_rules.sql), and for `stock_transfers` in [0019_stock_transfer_rules.sql](migrations/0019_stock_transfer_rules.sql)); a correction is a new row, and the database sets their `recorded_at`, whatever a writer sends. A settlement period is never deleted (by any role), its account never changes, its status only follows its close and revoke events, and a closed period's dates never change (`PeriodClosed`). A settlement account's owner is fixed for life (`SettlementOwnerFixed`). A task is cancelled, never deleted.
- A credit reversal of another customer, line, quantity, or payout method, a payout through an unmatching method, a posting split across customers or request hashes, and a match row off its line's chain (or after `accounted`, except a `cleared` row with the reason `superseded` once the line's statement is superseded, or after `cleared`): each is refused by a check, a composite key, an exclusion constraint, or a trigger in [0002_baseline_rules.sql](migrations/0002_baseline_rules.sql).
- Core tables from extensions. Extensions keep their own tables in their own schema.

## How to test

```bash
pnpm --filter @ssdashboard/db test
pnpm --filter @ssdashboard/db test:e2e
pnpm db:generate
```

`test:e2e` needs Postgres from `deploy/compose.dev.yaml`. Specs: unit [test/client.spec.ts](test/client.spec.ts) and [src/table-ownership.spec.ts](src/table-ownership.spec.ts) (every schema table has an owner); e2e [test/client.e2e-spec.ts](test/client.e2e-spec.ts), [test/migrate.e2e-spec.ts](test/migrate.e2e-spec.ts), [test/tenant.e2e-spec.ts](test/tenant.e2e-spec.ts) (the tenant column and key rules, with planted failures), [test/schema.e2e-spec.ts](test/schema.e2e-spec.ts) (the append only guards, one case per built table of A4; the declared list, trigger set, and revoked set are equal; `recorded_at` is stamped by the database), [test/operating-day.e2e-spec.ts](test/operating-day.e2e-spec.ts) (the Cairo operating day, stamped by trigger), [test/orders.e2e-spec.ts](test/orders.e2e-spec.ts) (stores, channels, connections, outbound commands, the spec 0015 connector tables, orders, order lines, and events), [test/customers.e2e-spec.ts](test/customers.e2e-spec.ts) (customers, phones, external ids, the flag checks, merges, and merge suggestions), [test/credit.e2e-spec.ts](test/credit.e2e-spec.ts) (credit entry checks, reversals, and the two connection posting race), [test/settlement.e2e-spec.ts](test/settlement.e2e-spec.ts) (accounts, the period exclusion, statements, lines, match rows, and the superseded clear), [test/tasks.e2e-spec.ts](test/tasks.e2e-spec.ts) (owner hats, outcomes, dedupe keys), [test/hats.e2e-spec.ts](test/hats.e2e-spec.ts) (spec 0008: the hat and grant tables' keys, checks and app role grants, `users.role` holding only `user`, and the AC-16 role mapping of the rules migration), [test/guard-gaps.e2e-spec.ts](test/guard-gaps.e2e-spec.ts) (constraints the per table suites do not name), and [test/enum-parity.e2e-spec.ts](test/enum-parity.e2e-spec.ts) (each database enum with a Zod twin in `@ssdashboard/contracts` equals it, so the two change together). `pnpm db:generate` makes a new migration from the schema (run from the repo root).

After the baseline reset in [ADR 0003](../../docs/adr/0003-reset-migrations-to-one-baseline.md), every developer recreates the dev database after each change to a baseline file until the freeze (each milestone of feature 4 is one): drop and recreate just this checkout's own database, then run `pnpm db:migrate`; or, alone on the server, `docker compose -f deploy/compose.dev.yaml down -v` then `pnpm bootstrap`. The `down -v` step removes the shared dev volume, so read the warning in the [root README](../../README.md) first. `pnpm bootstrap` stops with this instruction if it finds a database migrated by the old history.
