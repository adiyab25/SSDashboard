# packages/db

## Overview

The Drizzle schema for every module (Better Auth tables included) and the only migration history. The api's `migrate` entry point applies these migrations; nothing else does.

## Stack

Drizzle ORM and drizzle-kit, `pg` driver, PostgreSQL 18 with `pg_trgm`, `unaccent`, and `btree_gist` (enabled by `migrations/0000_baseline_extensions.sql`).

## Commands

```bash
pnpm db:generate                                 # From the repo root: new SQL migration from the schema
pnpm --filter @ssdashboard/db test               # Unit tests
pnpm --filter @ssdashboard/db test:e2e           # Against Postgres from deploy/compose.dev.yaml
```

## Conventions

- Tables live under `src/schema/`, one file per area (`locations.ts`, `stock-receipts.ts`, `parties.ts`, and `auth.ts` sit beside the module files; identity's `hat_assignments` and `permission_grants` are in `identity.ts`), re-exported from `src/schema/index.ts`. `src/table-ownership.ts` is the module map: it says which api module owns each table.
- Review every generated SQL migration before committing it; migrations are plain SQL and part of the release.
- Every table has `tenantId()` (`src/schema/columns.ts`), filled by the database from the `ssd.tenant_id` setting; every primary key, unique constraint, or unique index that holds a non uuid column includes `tenant_id` (`test/tenant.e2e-spec.ts` fails otherwise; lead with it, and `ON CONFLICT` targets must name `tenant_id` too). Never pass `tenant_id` from application code.
- What Drizzle cannot express (triggers, grants, roles, a partial unique index with `NULLS NOT DISTINCT`, seeds) is never written into a generated file. It goes in a `drizzle-kit generate --custom --name <x>` migration of its own, like `0002_baseline_rules.sql`; `0001_baseline_tables.sql` is generated only.
- New tables are readable and writable by the app role through default privileges. Every statement that names the app role runs in a `DO` block that reads `coalesce(nullif(current_setting('ssd.app_role', true), ''), 'ssdashboard_app')` and quotes it with `format('%I', ...)`. An append only table is declared in `APPEND_ONLY_TABLES` (`src/table-ownership.ts`), must `REVOKE UPDATE, DELETE, TRUNCATE` from it, and gets the `ssd_reject_change` row and truncate triggers, like the ledger history in `0002_baseline_rules.sql`; `schema.e2e-spec.ts` fails unless the declared list, the trigger set, and the tables the app role may only insert into are the same.
- Every function and trigger body in the rules file names tables as `public.<table>` and the plpgsql ones set `search_path = pg_catalog, public, pg_temp`, because the app role may create temp tables that would hide an unqualified name. `ssd_operating_day` stays a plain inlinable `sql` function (qualified names, no `SET`).
- A column a trigger fills (`operating_day`, stamped by `ssd_stamp_operating_day` from `effective_at`) is `not null` without a default; writers use SQL that leaves it out, never a Drizzle insert. A `not null` column that needs a seeded row as its default (`products.product_group_id` is `MAIN`) has no column default either, because the tables file runs before the seeds: the create path and test helpers pass it.
- Every foreign key needs an index that leads with its columns in order (a partial `WHERE <col> IS NOT NULL` index counts); `test/schema.e2e-spec.ts` lists any foreign key without one (spec 0002 AC-36).
- Descending index columns use `.desc().nullsFirst()`: Drizzle's bare `.desc()` emits `DESC NULLS LAST`, but a plain `ORDER BY x DESC` asks for `DESC NULLS FIRST`, and PostgreSQL cannot use the index for it (`schema.e2e-spec.ts` fails on any `DESC NULLS LAST` key).
- Composite foreign keys keep a bin in its row's location and a lot on its row's SKU; reuse `(bin_id, location_id)` and `(lot_id, variant_id)` for new tables that reference them.
- The package also re-exports Drizzle's `sql`, `inArray`, and `SQL` so the api uses this package's single drizzle-orm copy.

## Gotchas

- Never edit or delete a migration that has shipped. Fix forward with a new one.
- `recorded_at` on append only history belongs to the database: the trigger `<table>_0_stamp_recorded_at` (`ssd_stamp_recorded_at`, fired first by name) overwrites any value a writer sends, with `now()` on the stock ledger and credit entries (one instant per posting) and `clock_timestamp()` where a latest row or replay order is read by it (cost records, cost rules, order events, merges, match rows, period events, audit entries, licenses). `audit_entries` also gets `audit_entries_1_stamp_id` right after it (`id := uuidv7()`, spec 0010 AS1), so a writer chooses neither an entry's instant nor its keyset position. `licenses` and `license_checks` get the same id stamp (`ssd_stamp_id`, `0004_license_rules.sql`), and `license_checks.seq` is restamped from its own sequence (`license_checks_stamp_seq`) even under `OVERRIDING SYSTEM VALUE`, because the latest check is the highest `seq`. `licenses.payload_sha256` is deliberately not unique: the duplicate rule counts only rows whose envelope re-verifies, so a forged row cannot block a genuine license; the advisory lock `LICENSE_CHECK_LOCK` is the duplicate guard, so any new writer of `licenses` must take it. A new append only table with `recorded_at` needs the trigger too (`schema.e2e-spec.ts` checks it). Historical time goes in `effective_at` or `effective_from`; a test that plants past instants disables the trigger as the owner around the insert (the scale seed does for order events).
- The append only tables (`movement_groups`, `stock_movements`, `movement_serials`, `stock_receipt_lines`, `cost_records`, `order_events`, `customer_merges`, `credit_entries`, `settlement_statements`, `settlement_lines`, `settlement_line_matches`, `settlement_period_events`, `order_cost_rules`, `audit_entries`) have their triggers and the app role revoke in `0002_baseline_rules.sql`; `licenses` and `license_checks` (spec 0009) have theirs in `0004_license_rules.sql`. A correction is a new row.
- Settlement periods: `status` follows the latest `settlement_period_events` row. Insert an event and the trigger sets `status`; a write of `status` that disagrees with the latest event is refused. A period's account never changes, a closed period's dates never change (`PeriodClosed`), and no role deletes or truncates a period. A settlement account's owner never changes (`SettlementOwnerFixed`); archive it and open another.
- Match rows form one chain per line: the first row supersedes nothing, each later row supersedes the current head of its own line, and an `accounted` row is never superseded, except by a `cleared` row with the reason `superseded` once a statement supersedes the line's statement (domain review D1), and a `cleared` row is never superseded (review R17); `lineMatchState` in contracts agrees. A statement supersedes only a statement of its own account (composite key). Carrier line identity is `external_line_ref` plus `fee_code` (unique `NULLS NOT DISTINCT`), so two `other_fee` fees of one delivery are two lines; `fee_code` is set on every `other_fee` line and on no other kind (two checks). `partner_text` and `payment_reference` are capped at 500 characters; `settlement_period_events.reason`, `customer_merges.reason`, and `stock_movements.reason_code` are codes (`reasonCodeShape`).
- Credit entries: every entry carries `request_hash`. Entries that share an `idempotency_key` share posting, customer, and hash: the exclusion constraint `credit_entries_posting_holds_together` (GiST through `btree_gist`, in the rules file) waits for a conflicting uncommitted entry and then refuses, at every isolation level, and takes no lock per entry. Never guard a per row rule with an advisory lock per row: a 20,000 entry posting ran out of shared memory (`max_locks_per_transaction`, review R16). The reversal guards (credit and movement groups) read the original themselves and refuse one their statement cannot see, instead of leaving it to the foreign key (FOR KEY SHARE is not usable: it needs UPDATE, which the app role lacks on history). A reversal mirrors its original's customer, kind, funding, order, line, quantity, exchange, refund, payout method, and negated amount. The app role cannot delete tasks (`tasks` has DELETE and TRUNCATE revoked; cancel instead).
- The operating day is stamped by the `ssd_stamp_operating_day` trigger from `movement_groups.effective_at`, `stock_movements.effective_at`, `orders.placed_at`, `order_events.occurred_at`, `credit_entries.effective_at`, `tasks.created_at`, and `audit_entries.recorded_at` (`test/operating-day.e2e-spec.ts` pins the list). Writers never pass `operating_day`. `orders` and `tasks` are updatable, so `orders_operating_day_follows_placed_at` and `tasks_operating_day_follows_created_at` refuse a change of the day unless `placed_at` or `created_at` changes in the same update (the guard runs before the stamp, by trigger name). The seeds are the store `MAIN` and the channel `manual` (default store `MAIN`), both in `0002_baseline_rules.sql`.
- `migrate` seeds one `not_set` row per `order_cost_rules` kind, from the operating day, after the `install` row (`seedOrderCostRules` in `src/migrate.ts`). It adds only a kind that has no row yet, so a rerun adds nothing and a rule someone set is never touched. The seed writes no value.
- `users.role` holds only `user` (Better Auth's admin plugin writes it; spec 0008 AC-16). `hat_assignments` and `permission_grants` are current state: the app role may insert, read and delete them, never update or truncate. The AC-16 mapping of the old `admin` and `staff` roles sits between the `AC-16 role mapping` markers of `0002_baseline_rules.sql`, which `test/hats.e2e-spec.ts` runs on planted people.
- `location_owner_policies` (owned by inventory): the app role may update only its eight policy columns plus `updated_at`, `updated_by`, and `locked_terms_changed_at` (column grant, `0012_owner_policy_grant.sql`; the last is stamped only when a locked term changes, and an archived location of the type comes back only while it is earlier than the archive), never insert, delete, `owner_type`, or `tenant_id`; its four CHECKs (`0011_owner_policy_editing.sql`, declared in the Drizzle schema) keep every row consistent, keep partner and customer stock off line, and pin the consignment row to settle with its partner (spec 0009 AC-24, owner ruling 2026-11-08). `migrate.e2e-spec.ts` pins the column grants; `owner-policy-upgrade.e2e-spec.ts` proves an install at 0010 upgrades cleanly.
- Catalog search (spec 0012, `0013_catalog_search_text.sql` and `0014_catalog_search_rules.sql`): `product_variants.search_text` belongs to the database (it keeps the spec's `default ''`, unlike `operating_day`, because the insert trigger always overwrites it). `ssd_search_normalize(text)` (plain inlinable `sql`, `IMMUTABLE`, no `SET`, on the builtin `pg_c_utf8` collation so it never depends on the server locale) is the only normalization; the trigger `product_variants_search_text` restamps a row from `ssd_variant_search_text` on insert and on any update of `sku`, `option_values`, `product_id`, or `search_text` itself (a written value never sticks), and `products_search_text_follows` and `product_options_search_text_follows` restamp a style's variants with `SET search_text = search_text`, never touching `updated_at`. Never write the column from application code; `test/search-normalize.e2e-spec.ts` holds the fixtures. Overlapping writes: a variant entering a style (insert, or a move) takes `FOR SHARE` on the style row in the stamp trigger, and the options follow trigger takes `FOR NO KEY UPDATE` on the affected style rows in id order, so a variant write and a rename or option write of the same style wait for each other (style row first, then variant rows); writers of `products` and `product_options` must run READ COMMITTED (a REPEATABLE READ one could miss a variant committed while it waited). `ssd_search_normalize` is the same only within one PostgreSQL major version (its Unicode tables move between majors): after a major upgrade restamp with `UPDATE product_variants SET search_text = search_text`, a step feature 26's upgrade runbook owns. pg_trgm extracts Arabic trigrams only where the database's character type classifies Arabic letters as letters (the test database does; the same file pins it); feature 26 confirms the client database's ctype.
- Catalog styles (spec 0012 milestone 2, `0015_catalog_styles.sql` generated, `0016_catalog_option_roles.sql` hand written): `seasons` and `product_groups` carry `created_at` and `updated_at` (the stale check); `product_options.role` (`option_role`: `size`, `color`, `other`) is set by the api from `OPTION_ROLE_NAMES` when an option is created, and 0016 backfilled the options that existed before from the same lists, updating only the options whose role changes (each option update restamps its style's variants) (`test/catalog-styles-upgrade.e2e-spec.ts` proves they agree and that an option staying `other` keeps its row version); 0015 fails, changing nothing, on an install that already holds two active variants of one style with the same `option_values` (only a planted or imported row can; the api never makes one): the error names `product_variants_options_unique` and the duplicated key, and the operator archives or recodes one of the two variants' option values, then reruns `migrate` (the same test pins the failure); `product_variants_options_unique` (partial, `WHERE archived_at IS NULL`) refuses two active variants of one style with the same `option_values`, so a test that plants several variants in one style gives each its own option values.
- A new table must be added to `src/table-ownership.ts` under its owning module, or `table-ownership.spec.ts` fails. The api's module wall (`apps/api/src/module-boundary.spec.ts`) reads the same map.
- Each migration runs in a transaction. Anything that cannot (`CREATE INDEX CONCURRENTLY`) goes in its own small migration that is safe to run twice.
- Expand and contract: add the new column, move data in SQL, drop the old one at least one minor release later.
- Extensions keep their own tables in their own schema and never migrate core tables.
- Migrations create the app role (`APP_DB_ROLE`, default `ssdashboard_app`) and a schema owned by it, so the owner (`MIGRATION_DATABASE_URL`) must be a superuser, or on a managed database hold `CREATEROLE` and membership in that role. `migrate` stores `ssd.tenant_id` and `ssd.app_role` on the database on its first run (`ALTER DATABASE ... SET`, which only reaches new sessions) and writes the `install` row; every later run restores either setting when it is missing (reset, or lost in a plain restore): the tenant from the `install` row, the role from the owner of the `pgboss` schema, never the default; a database setting that names another tenant than the `install` row throws `TenantMismatch` and is never overwritten; a later run with a different `TENANT_ID` throws `TenantMismatch` (a tenant left in the setting by an interrupted first run counts), a different `APP_DB_ROLE` throws `AppRoleMismatch`, and a superuser, `CREATEROLE`, `BYPASSRLS`, `REPLICATION`, or owner role, a role holding the owner's privileges or a member of any role, and a role whose own settings (all databases or this one) set `ssd.*` or `search_path` is refused (`UnsafeAppRole`, refused, never reset) on every run; a rerun without them uses the stored values. The e2e suites create scratch databases with that owner URL.
- A database migrated by the pre baseline history (nine files) cannot take the baseline: drop the dev volume and rerun `pnpm bootstrap` (it checks and says so).
- `uuidv7()` (the default for every `id`) needs PostgreSQL 18.
- The api and worker call `assertSessionTenant` at start (`DatabaseModule`) and stop with `SessionTenantMismatch` when a session's `ssd.tenant_id` is unset or is not the `install` row (a role setting beats the database setting). Their pool (`createDatabase` with `onTenantMismatch`) also runs the check on every new connection before it serves a query and stops the process on a mismatch, so a database unreachable at start is still checked. On PostgreSQL 18 the app role cannot set `ssd.*` on itself, but can set its own `search_path` (`migrate.e2e-spec.ts` proves both).
