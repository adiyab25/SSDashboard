# Audit trail

One append only log of who did what, when, and why, written in the same database transaction as the change, so there is never a change without its entry or an entry without its change.

## Owns

- The table `audit_entries` (schema in [packages/db/src/schema/audit.ts](../../../../packages/db/src/schema/audit.ts)); the app role may only insert and read it, triggers refuse every update, delete, and truncate, and the database stamps each entry's `id` and `recorded_at` itself, whatever the writer passes.
- `AuditService.record(tx, entry)`, `recordMany(tx, entries)` (one business action, one correlation id), and `newCorrelationId(actor?)` (a system job's own job id, else a new one), the writer of every entry of a listed code: [audit.service.ts](audit.service.ts). It checks the action code and its record type against the registry, applies the reason policy ([audit-reason.ts](audit-reason.ts), `checkedAuditReason`; a call may tighten it with `reasonRequired: true`, never loosen it), masks personal values in `before` and `after` with the shared list plus the record type's own personal keys (listing their paths in `personal_fields`), refuses a phone shaped key, a label that is not a short code, and undo arguments that are not ids, codes, or numbers, masks phones in the reason, and inserts through the caller's transaction; the insert SQL (`entryValues`, `INSERT_ENTRIES`) lives in [audit-entry-sql.ts](audit-entry-sql.ts), which only `AuditService` and the undone entry writer may name (`module-boundary.spec.ts`, security review AS36). The 500 character limit is measured on the masked reason (review M4R18).
- `AuditQueryService`, the only reader: [audit-query.service.ts](audit-query.service.ts): `list(query, viewer)`, `get(id, viewer)` (one entry with its field diff, each change marked `added`, `removed`, or `changed`), `view(id, viewer)`, `forRecord(viewer, ...)`, and the export's bound, size check, and keyset batches (each taking the viewer). Every public reader guards itself, whoever calls it (security review AS29): the four entry readers refuse a viewer without `audit.read`, the export reads one without `audit.export` (`AuditReadForbidden`, 403), and each leaves out cost fields for a viewer without `cost.view`. Every entry view carries `undone` (one extra query on the page's ids) and `canUndo` (the registry marks the action undoable and the entry names its handler, it is not undone yet, and the viewer holds `audit.undo`).
- The one step undo (spec 0010, AC-14): [audit-undo.registry.ts](audit-undo.registry.ts) holds the handlers owning modules register from their own `onModuleInit` (`AuditUndoRegistry.register(code, handler, '<module>')`, exported by `AuditModule`; a module may register only a handler code its own undoable actions name, else `AuditUndoHandlerForeign`, security review AS33). The rest lives in the leaf [audit-undo.module.ts](audit-undo.module.ts), which only the api's `AppModule` imports, never the worker: [audit-undo.service.ts](audit-undo.service.ts) runs one undo in one transaction (the entry id lower cased, an advisory lock on it, `NotUndoable`, `AlreadyUndone`, the undone code's reason policy checked and the reason masked before any owner code runs, the owner's handler, then the `<action>_undone` entry on the same record through [audit-undone.writer.ts](audit-undone.writer.ts), which no module exports and `module-boundary.spec.ts` keeps to the undo; a unique index refusal on `undoes_entry_id` is `AlreadyUndone`; a failing read after commit answers from the row written, but a read refusal (`AuditReadForbidden`) is passed on, security review AS37); [audit-undo-start-check.ts](audit-undo-start-check.ts) stops the api at start when an undoable code's `undoHandler` has no handler (review M4R1: the worker never runs it, `audit-routes.spec.ts`); [audit-undo.controller.ts](audit-undo.controller.ts) is `POST /api/audit/entries/:id/undo` (`audit.undo`, a reason of 1 to 500 characters, 200 with the undone entry). A handler refuses with `UndoNotPossible(code)`; only a code its action lists in `undoRefusalCodes` reaches the 409 answer as `undoCode`, with a fixed message (security review AS31). The table's `audit_entries_undo_matches` trigger refuses an undo row that does not truly undo its target.
- The routes, staff audience, `@Permission('audit.read')` (spec 0008): `GET /api/audit/entries` and `GET /api/audit/entries/:id` in [audit-entries.controller.ts](audit-entries.controller.ts), and `GET /api/audit/records/:type/:id/entries` in [audit-records.controller.ts](audit-records.controller.ts), all in `AuditModule`, which never imports the platform module (spec 0009 makes platform import audit). Cost fields in a diff reach only a reader with `cost.view`: every reader that answers an entry's `before` and `after` (the list, the detail with its `changes`, the record history, the undo answer, and the export's `before` and `after` cells) goes through [audit-cost-fields.ts](audit-cost-fields.ts), which matches a cost key in any spelling (`unit_cost`, `UnitCost`: lower case, `_`, `-`, and spaces dropped, like the route sweep) and inside JSON text a diff stores as a string (security review AS30, review M4R8).
- The CSV export, `POST /api/audit/entries/export` (`audit.export`; a POST since security review AS28, because it writes `audit.exported` and a POST passes the session guard's Origin check, so a link from another site cannot plant that entry; the filter is the query string and there is no body; a GET to that path is the entry detail and answers 404), in the leaf [audit-export.module.ts](audit-export.module.ts): [audit-export.controller.ts](audit-export.controller.ts) reads the time zone and the `x-audit-reason` header (percent encoded, 1 to 500 characters, 400 `INVALID_REASON`), [audit-export.service.ts](audit-export.service.ts) bounds the file by the newest key inside the filter, accepts only a day range of at most 366 days (both ends included, else 400 `INVALID_FILTER`), refuses more than 200,000 rows (413 `EXPORT_TOO_LARGE`, decided before streaming), records `audit.exported` in its own transaction before the first byte, and streams exactly the counted rows (never its own entry) in keyset batches of 1,000; a reader that goes away stops the stream and logs one line. The app root lists this module first, so a fixed path it serves under `/api/audit/entries/` is routed before `/:id` ([audit-routes.spec.ts](audit-routes.spec.ts)).
- The typed errors and their api mapping: [audit.errors.ts](audit.errors.ts), [audit-http.ts](audit-http.ts) (`AuditReasonRequired` is 422 `REASON_REQUIRED`, `AuditReasonTooLong` 422 `REASON_TOO_LONG`, `AuditReasonInvalid` 422 `REASON_INVALID`, `AuditReadForbidden` 403 `FORBIDDEN`, `AuditEntryNotFound` 404 `ENTRY_NOT_FOUND`, `AuditExportTooLarge` 413 `EXPORT_TOO_LARGE`, `NotUndoable` 409 `NOT_UNDOABLE`, `AlreadyUndone` 409 `ALREADY_UNDONE`, `UndoNotPossible` 409 `UNDO_NOT_POSSIBLE`, with `undoCode` only when the action declares it and always a fixed message).
- The masking rules over the shared redaction list: [personal-data.ts](personal-data.ts) (record type keys, phone shaped keys and numbers, undo argument shape).
- External ids (a Shopify customer id, a WhatsApp contact id) travel in a diff as text, never as numbers: a whole number of 10 to 15 digits is masked as phone shaped, so a numeric id would be hidden (security review AS20).
- Reasons follow the record type: customer facing types keep a reason code only, one of the action's `reasonCodes` (422 `REASON_INVALID` for a typed note or an unlisted code), every other type keeps free text with phones and emails masked (spec 0010, AC-5).
- The action registry, the record types with their labels and personal keys, and the six actor constructors live in contracts: [audit-actions.ts](../../../../packages/contracts/src/audit/audit-actions.ts), [audit-record-types.ts](../../../../packages/contracts/src/audit/audit-record-types.ts), [audit-actor.ts](../../../../packages/contracts/src/audit/audit-actor.ts).

- Its registry row (spec 0009, AC-6, `packages/contracts/src/modules/module-registry.ts`): `audit`, core, no toggle. Every controller here declares `@RequiresModule('audit')` (`src/platform/modules/requires-module.spec.ts` fails the build otherwise), so the module gate never answers `MODULE_OFF` for it while the module is core.

## Never touches

- Any other module's table. Record labels and diffs come from the calling module; person names come from the staff directory by id, never from a join.
- Any owning module: an undo reaches the owner only through the handler it registered, and hands it only the checked, masked reason. A file here imports only its own folder, `database`, `config`, `platform`, and identity's staff directory (`src/module-boundary.spec.ts`).
- Its own transaction for a recorded change: `record` writes only through the caller's `tx`, never opens one, and never swallows an error. The undo and the export's own entry are the only transactions this module opens.
- A customer's phone, name, or address (Law 151): they are masked or refused before the insert.
- The owner database role. No code path updates or deletes an entry.

## Decisions

No ADRs yet. Record non obvious decisions as ADRs in docs/adr/ and link them here.

- The registry (`AUDIT_ACTIONS`) stores catalog keys (`audit.actions.stockReceiptVoided`), not label text: the screen translates them in the viewer's language, and the i18n parity test keeps English and Arabic in step (spec 0010, AC-10).
- Every reader orders by the table's own columns (`audit_entries.recorded_at DESC, audit_entries.id DESC`), never a bare `recorded_at`: the readers select `recorded_at` as text under the same name, and a bare `ORDER BY` name means the output column, which no index serves (spec 0010 task 18, guarded by `audit-reading.spec.ts`). A day filter also bounds `recorded_at` by a UTC superset window (`filtersOf`), so an old day range starts at the right place in the newest first index instead of walking the table; the BRIN index on `operating_day` stays.
- Undone codes are derived, never listed (spec 0010 task 16, security review AS5): each undoable code `X` brings `X_undone`, reason required, final, with the one shared label `audit.actions.actionUndone`, proven by `X`'s own proof file. `record` refuses an undone code; only the undo module's writer of undone entries writes one.

## Retention and who may read

Entries are kept for the life of the install (spec 0010, AC-16, owner question 4). The rules above keep personal data out of the table, so there is no age limit. No code path deletes or rewrites an entry. If a lawyer ever requires removing old rows, the only allowed way is a reviewed migration run by the owner role, never the app.

Who may read (spec 0010, AC-13), all by default on the manager hat only, with no partner or portal route:

- The list, the entry detail, and the record history need `audit.read`.
- The CSV export (`POST /api/audit/entries/export`) needs `audit.export`.
- The undo (`POST /api/audit/entries/:id/undo`) needs `audit.undo`.
- Every reader checks its own permission, and leaves out cost fields for a viewer without `cost.view`, whichever module calls it. A cost entry (`COST_ENTRY_ACTIONS` in [audit-cost-fields.ts](audit-cost-fields.ts), today only `cost_record.recorded`) is hidden whole from such a viewer (the owner's ruling of 2026-11-11, "Hide whole entry"): `visibleEntries` in [audit-query.service.ts](audit-query.service.ts) adds the condition in SQL to the list (every filter), the record history, the detail and the undo's read back (404 `ENTRY_NOT_FOUND`, the missing entry's answer), and the export's bound, count, and batches (so the CSV and the `rows` its `audit.exported` entry records never include one, and paging has no gap). The undo answers such an entry 404 too (`isEntryVisible`), before `NOT_UNDOABLE` could say it exists. The action filter's options come from the registry (`AUDIT_ACTION_CODES`), never from the data, so offering the code says nothing about whether an entry exists. A viewer without `cost.view` also sees a holder's `audit.exported` entry redacted when the export could have held a cost entry (the entry's `after` carries `costVisible: true`, written when the exporter held `cost.view`, and its action filter is a cost entry action or there is none): who, when, and the reason stay visible, but `after` is replaced by `{ "redacted": true }` (no filter, no `rows`) in the list, history, detail (its one change is `redacted`), undo answer, and CSV, so the entry never says a cost entry exists; an export by someone without `cost.view` (no marker) or filtered to another action stays complete for everyone, the marker included (it only says the exporter held the grant, which the actor's hat shows). A legacy entry has no marker and stays fully visible: no cost entry exists on any install before milestone 3 ships, so no earlier export can have held one. `COST_ENTRY_ACTIONS` is derived from the registry's `costEntry` flag.
