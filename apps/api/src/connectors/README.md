# Connectors

The link to the brand's outside accounts (Shopify first): the commands written back to them and, from spec 0015 on, the connections, inbox, and mappings. Today the outbound command reads spec 0013 milestone 2 needs (a stand-in until spec 0015 task 13 builds the outbound framework), from spec 0015 task 6 connecting a Shopify store, and from task 7 the signed Shopify webhook, the durable inbox, and the inbox job that turns a Shopify order into an app order (the milestone 1 tracer bullet).

## Owns

- The connector tables (defined in [packages/db](../../../../packages/db/src/schema/connectors.ts)): `connections`, `outbound_commands`, `inbound_events`, `connection_external_ids`, `connection_stock_levels`, and `connection_sync_runs`, all owned by `connectors` in [table-ownership.ts](../../../../packages/db/src/table-ownership.ts). Today it writes `connections` and `connection_sync_runs` (task 6), `inbound_events` and `connection_external_ids` (task 7, order mappings only), and reads `outbound_commands`.
- `ConnectorsService` ([connectors.service.ts](connectors.service.ts)): `openCommandsFor(linkedType, id, tx)` (the `waiting` and `failed` commands of a record, read in the caller's transaction), `syncStateFor(linkedType, id)` (the same rows for the order page's command block), `storeOfConnection(connectionId, tx)` (a connection's store, which the orders module checks before it trusts a channel's customer id, until task 13 registers the `ConnectionStoreSource`), and `writeBackAvailable(orderId, kind)`, which answers false: no executor registers before feature 18 (the rule of spec 0015 AC-24), so Shopify orders are edited and cancelled in Shopify.
- Its registry row (spec 0009, AC-6, `packages/contracts/src/modules/module-registry.ts`): `connectors`, core, no toggle, requires `channels`, with the capability `connectors.shopify.sync` (core, `kind: read`, `windDown: none`; owns the `connector-shopify` queue and serves `ConnectionsController`). The other capabilities of spec 0015 (`connectors.inbox`, `connectors.shopify.stock_push`, and the rest) land with their code (AC-6).
- `connections/` (spec 0015 task 6, AC-1, AC-2): `ConnectionsController` (`@Audience('staff')`, `@RequiresModule('connectors')`, `@Permission('settings.manage')`) with `GET /api/connections` (keyset cursor on created at and id, newest first, `limit` 50, at most 100), `POST /api/connections/shopify` (201 `{ id, health: 'connecting' }`; 409 `SHOP_ALREADY_CONNECTED`, `STORE_CODE_TAKEN`; 422 `INVALID_SHOP_DOMAIN`, `INVALID_BODY`), `GET /api/connections/:id` (`ConnectionDetail`, 404 `NOT_FOUND`), and `POST /api/connections/:id/check` (202; 409 `CONNECTION_ARCHIVED`). `ConnectionsService.connect` writes, in one transaction, the store and its channel (`ChannelsService.createShopifyStore`), the connection (health `connecting`, credentials sealed under its new id, `credentials_hint`, `config.appOwner`), the audit entry `connection.created` (record type `connection`, label the store code, never a credential), and the `connect` job (`JobSender.sendIn`, grouped by connection). The shapes are `packages/contracts/src/connectors/connections.ts` and `connection-config.ts`. No answer carries a credential: only `credentials.set` and the client id's last 4 characters.
- `connections/connection-stores.ts`: `ConnectionStores`, the `ConnectionStoreSource` that `ConnectorsModule` registers with `ChannelsService.registerConnectionStores` from its `onModuleInit`, so channels names a connection's store without reading `connections`. `ConnectorsService.storeOfConnection` stays for the orders module until orders moves to `storeLabelsByConnection`.
- The module wiring: [connectors.module.ts](connectors.module.ts) `ConnectorsModule` (api and worker: the services, both controllers, `ConnectionSecrets`, the store source, the hook verifier and inbox writer) and [connectors-worker.module.ts](connectors-worker.module.ts) `ConnectorsWorkerModule` (worker only, imported by `WorkerModule`: the one `ShopifyClient`, the queue worker, the `connect` and `inbox` jobs; it imports `OrdersModule`, so it lives in its own file: `OrdersModule` imports `ConnectorsModule`, and one file importing both would be an import cycle).
- `hooks/` (spec 0015 task 7, AC-4 to AC-6): `mountHooks` ([hooks/mount-hooks.ts](hooks/mount-hooks.ts), called by `app.setup.ts` after Better Auth and before the JSON parser) reads the raw body of `/api/hooks/*` (at most 2 MB; 413, empty, above, by `Content-Length` or while reading) and, on `POST /api/hooks/shopify/:connectionId`, asks `ShopifyHookVerifier` ([hooks/shopify-hook-verifier.ts](hooks/shopify-hook-verifier.ts)) before anything is parsed: a live Shopify connection, `X-Shopify-Shop-Domain` equal to its shop domain, and `verifyShopifySignature` ([hooks/shopify-signature.ts](hooks/shopify-signature.ts): HMAC SHA256 of the raw bytes, base64, `timingSafeEqual` on two 32 byte buffers) with its webhook secret (the client secret, or a legacy token's API secret), opened once and cached in process 5 minutes per (connection, key version). A malformed, unknown, or archived id, a wrong shop, or a missing or wrong signature all answer the same empty 401 and write no row; a wrong shop or signature on a live connection counts one failure (`hook_auth_failures`, at most one write per connection per minute). A pass sets `request.hook`, which `AudienceGuard` reads as the `hook` audience. `ShopifyHooksController` (`@Audience('hook')`, `@RequiresModule('connectors')`, no permission) answers 200 `{}` (400 `INVALID_HOOK` without a topic or webhook id, 400 `INVALID_HOOK_BODY` for a body that is not JSON); `ShopifyHooksService` asks `ModuleStateService.acceptsHook('connectors.shopify.sync')` (a row is `ignored_unlicensed` when told; always `process` for this core capability today) and in one transaction inserts the `inbound_events` row (dedupe on `X-Shopify-Webhook-Id`, `ON CONFLICT DO NOTHING`; payload from `minimizeShopifyWebhook`, [hooks/shopify-hook-payload.ts](hooks/shopify-hook-payload.ts): the topic, the Shopify gid, `updated_at`, plus item, location, and quantity for inventory levels; `subject_label` null until the read back), sends the `inbox` job (event id, connection id, kind; priority 20) for a topic milestone 1 processes, and moves `last_inbound_at` at most every 30 seconds. Lead decision D9: the four order topics and `app/uninstalled` get a job; every other verified topic is recorded and stays `received` for its milestone 2 or 3 task. A verified topic this release does not know is answered 200 and not recorded. A paused connection still records.
- `InboundEventFailed` ([connectors.events.ts](connectors.events.ts), task 7, AC-8): `connectionId`, `eventId`, `subjectType`, `subjectExternalId`, `subjectLabel`, `failureCode`, published by the inbox job in the transaction that marks the event `failed`.
- `connections/connection-secrets.ts` (spec 0015 task 4, AC-2): `ConnectionSecrets`, the AES-256-GCM seal and open of a connection's credentials (`client_credentials` or a legacy `access_token`) under `CONNECTOR_SECRET_KEY`, bound to the connection id, with the key version derived from the key (`connectorKeyVersion`), opening under `CONNECTOR_SECRET_KEY_PREVIOUS` during a rotation, and `reencrypt` (the step of the re-encrypt job, whose scheduled job is task 12's). Provided by `ConnectorsModule`: the connect route seals, the worker's connect job opens.
- The Shopify adapter in [shopify/](shopify/README.md): the client, the query texts, the fixtures, the order mapper, the connect job and its health decision, and the `connector-shopify` queue.
- The events ([connectors.events.ts](connectors.events.ts)): `OutboundCommandQueued`, `OutboundCommandSynced`, `OutboundCommandFailed`, and `OutboundCommandResolved` (`commandId`, `connectionId`, `kind`, `linkedType`, `linkedId`, `failureCode`), published through the platform `DomainEvents` by whoever changes a command. Nothing here publishes them yet: spec 0015 task 13's `enqueue` and executors will, and the e2e suites use a fixture connector.

## Never touches

- Other modules' tables: the orders module keeps `orders.write_back_state` from these events itself (its write back projection), and stores come from `ChannelsService`.
- A command's `payload` in a log line, an error, or an event: it may hold an address (Law 151).
- A credential, an access token, or a key in a log line, an error, an answer, or any row but `connections.credentials_ciphertext`: only `ConnectionSecrets` and the worker's memory hold them in the clear.
- Writing a command: `enqueue`, the executors, retry, and resolve are spec 0015 task 13, not built here.
- A webhook body beyond the minimized payload: no name, phone, address, note, or line text reaches a row, a log line, job data, or an event (Law 151). Rate limiting the public hook is feature 26's Caddy configuration.

## How to test

```bash
pnpm --filter @ssdashboard/api exec vitest run src/connectors
pnpm --filter @ssdashboard/api build
pnpm --filter @ssdashboard/api exec vitest run --config ./vitest.config.e2e.ts test/orders-edit.e2e-spec.ts
pnpm --filter @ssdashboard/api exec vitest run --config ./vitest.config.e2e.ts test/shopify-connect.e2e-spec.ts
pnpm --filter @ssdashboard/api exec vitest run --config ./vitest.config.e2e.ts test/shopify-hook.e2e-spec.ts
```

The unit tests need no database; the orders edit e2e suite drives `openCommandsFor` and the events against Postgres with a fixture connector; the connect suite runs the api and the worker in process against the `connect-*` fixtures (rows in one transaction, health codes and warnings, 409 and 422 answers, 403 for a non manager, and a sentinel secret searched in every answer, row, job, sync run, and log line). The hook suite (`test/shopify-hook.e2e-spec.ts`) signs webhooks in the test with a fake secret against planted connections: one row and 200, a repeat adding none, the same empty 401 for a tampered byte, a wrong shop, no signature, an unknown, malformed, or archived connection, 413 above 2 MB, the tracer bullet into `GET /api/orders`, coalescing, `stale`, `update_deferred`, `not_visible`, `test_order`, a failed apply with `InboundEventFailed` in the same transaction, a 500 kept `received`, `READS_FAILING`, `app/uninstalled`, `PROTECTED_DATA_MISSING`, an unprocessed topic, and no personal data or secret in any payload, row, or log line. `hooks/*.spec.ts` hold the signature check and the payload minimizer.

## Decisions

- **A stand-in, decided by the lead for spec 0013 milestone 2**: the module, its service file, and its events file carry the names spec 0015 gives them, so task 13 grows them in place rather than replacing a fake. No ADR yet.
- **Hook choices** (integrations lane, spec 0015 task 7, no ADR yet): the signature is checked in an Express middleware before the guards (so `AudienceGuard` can read `request.hook`), which makes an unsigned call from a signed in person the hook's empty 401, not a 403; an archived connection counts no failure; a verified delivery without a topic or webhook id answers 400; an unknown verified topic is answered 200 and not recorded (the subject type column has no value for it).
- **Connect choices** (integrations lane, spec 0015 task 6, no ADR yet): the connect job checks scopes handle by handle (whether Shopify lists `read_x` beside a granted `write_x` is unverified until task 1 records it); it reads no further than the scopes when one is missing; webhooks are registered only when every check passes; a refused registration ends `degraded` with `WEBHOOKS_MISSING`; a transient failure leaves health as it was and marks the run failed with the client's code; the store's names are filled from the shop name only on the first check that reaches the shop.
