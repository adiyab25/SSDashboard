# Shopify connector

The adapter between the shared core and a brand's Shopify store (Admin GraphQL API, version `2026-10`). Today its synthetic fixtures, the GraphQL client, the query texts, the order and customer mappers, the connect job (spec 0015 task 6), and the inbox job (task 7, with the hook in [../hooks/](../README.md); orders in full by task 9, customer webhooks by task 11) exist; the other jobs arrive with tasks 8, 9a, 10, and 12 onwards.

## Owns

- `fixtures/`: hand written, synthetic Shopify Admin GraphQL order recordings for API version `2026-10`, one folder per scenario, to be replaced by recordings from a development store ([fixtures README](fixtures/README.md)).
- `shopify-client.ts` (spec 0015 task 5, AC-25): `ShopifyClient`, one per process, with per connection state: the client credentials token cache (fetched again 60 seconds before expiry; a legacy access token used as is), the throttle reading from `extensions.cost.throttleStatus` and a wait before a call whose expected cost exceeds what is available, `THROTTLED` retried up to 5 times and HTTP 429 after `Retry-After` (else 1 second), a 30 second timeout, one call per connection at a time, `API_VERSION_FELL_FORWARD` when `X-Shopify-API-Version` differs from `SHOPIFY_API_VERSION` (`2026-10`), no redirect ever followed (`redirect: 'error'`; a 3xx is `REQUEST_REJECTED`, so the token header and the client secret never travel elsewhere), a `Retry-After` above 60 seconds not slept but a transient `RATE_LIMITED` at once, answers read up to 10 MB (`RESPONSE_TOO_LARGE` above), `confirmAccess` (one fresh token exchange, or a shop read for a legacy token: the `app/uninstalled` confirmation), and typed errors (`ShopifyTransientError`, `ShopifyRejectedError`, with `APP_NOT_INSTALLED`, `APP_ORGANIZATION_MISMATCH`, `CREDENTIALS_REJECTED` for a refused token) whose messages and logs carry codes only. Calls go to `https://<shop>` or `SHOPIFY_MOCK_ORIGIN`. Provided once per worker process by `ConnectorsWorkerModule` (`connectors.module.ts`); the api never gets one.
- `shopify-queries.ts`: every query and mutation text, one constant each with its operation name (connect: shop, access scopes, locations, latest order for the protected data check, webhook subscriptions list and create; the order read back `ORDER_READ`, operation `OrderRead`, variable `id`, with its page sizes and cost estimate; the customer read back `CUSTOMER_READ`, operation `CustomerRead`, variable `id`: id, `updatedAt`, first and last name, `defaultPhoneNumber.phoneNumber` and the deprecated `phone`, about 2 points, `CUSTOMER_READ_EXPECTED_COST`).
- `order-mapper.ts` (spec 0015 Inbound processing item 4, AC-9, AC-10, AC-12, AC-13, _Value sourcing_): the one order mapper, pure (no database, clock, log, or Shopify call). `ShopifyOrder`, the zod schema of exactly what `ORDER_READ` selects, and `parseShopifyOrder` for the inbox job; `mapShopifyOrder` (to spec 0013's `ChannelOrderInput`, with the go live or found first states and the actor kind they need), `mapShopifyOrderSnapshot` (to `ChannelOrderSnapshot`), `foundStatesOf`, `cancelReasonCodeOf` (`channel.` plus the lower case reason, else `channel.other`), `firstActiveFulfillmentOf`, `replacementInput` (`<name>-R<n>`, `<gid>:R<n>`), and `shopifyOrderName` (the order name cleaned of control and direction characters and capped at 64, also the inbox's `subject_label`). The order name, every discount code, and the unmapped gateway names get the same control and direction clean up as the other mapped text. Each result also carries the unmapped lines, the unmapped gateway names, every discount code, and the flags `test_order`, `gift_tag_not_free`, and `gift_reason_not_a_gift_code` for the job to record. Task 9 adds `shopifyPaymentOf` (the payment a new order would get), `gatewayMappingOf` (the order's gateway names and what each maps to now, built with `Object.fromEntries` so a `__proto__` name stays an own key, security review L5), `gatewayKeyOf` and `gatewayMethodOf` (the one gateway key, security review N1), `paymentTransactionIdsOf` and `creationPaymentOf` (the rederive of lead decisions D10 and D10a from the creation facts only), the refusal of a fulfillment created more than a day after the order's `updatedAt` (`ORDER_UNREADABLE`, the L3 residual), the ISO instant checks on every Shopify time it reads (security review L3), and the `held` lines of `mapShopifyOrderSnapshot` (while a fulfillment is active, exactly the lines the app holds at their applied quantities). It throws only `ShopifyOrderMappingError`, a code plus field paths, never a read value (Law 151).
- `order-mapping-state.ts` (task 9): `OrderMappingState`, the zod shape of an order mapping's `state` (`appliedLineIds`, kept only for milestone 1 readers, `appliedLines` with quantities, `unmappedLines`, `unmappedGateways`, `discountCodes` (every code ever seen, code review m3), the immutable creation facts `creationGateways` and `creationTransactionIds` (lead decision D10), `deliveryFulfillmentId`, `paymentMethodLocked`; keys of later tasks are kept), `parseOrderMappingState` (`MAPPING_STATE_UNREADABLE`), `unionOfCodes`, and `createdOrderState` for a new order.
- `known-order-plan.ts` (task 9, AC-9, AC-11, AC-13, AC-14, D10, pure): `planKnownOrder` turns a newer read back of a known order into the named orders calls: the cancel (`channel.<reason>`, and nothing else), the late variant links of `state.unmappedLines` whose variant now maps, the snapshot for `applyChannelEdit` (every open line while no fulfillment is active and on the read where the first one appears; the held lines afterwards; nothing for a milestone 1 mapping without `appliedLines` once its fulfillment was reported, code review m4), the first active fulfillment's carrier delivery, and the rederive of D10 (only when the config maps a creation gateway differently, from the creation gateways and transactions only); `nextKnownOrderState` is the mapping state after the apply.
- `storable-text.ts` (security review N3, N4): `isStorableText` (no U+0000, no unpaired surrogate: what `text` and `jsonb` accept), `withoutLoneSurrogates`, and the zod `StorableShopifyId` and `StorableShopifyText` for Shopify strings stored verbatim.
- `customer-mapper.ts` (task 11, AC-15, pure): `ShopifyCustomer` (what `CUSTOMER_READ` selects), `parseShopifyCustomer` (`ShopifyCustomerMappingError` `CUSTOMER_UNREADABLE`, paths only), and `mapShopifyCustomer`: the phone (`defaultPhoneNumber.phoneNumber`, else the deprecated `phone`) through `EgyptianPhone.parse`, null when absent or not parsing; `channelCustomer` `shopify_customer` with the connection and the customer gid; the first and last name joined and cleaned; `seenAt` the customer's `updatedAt`.
- `shopify-app.ts` (task 6): `SHOPIFY_REQUIRED_SCOPES` (the 8 slice 1a handles the spec names; the slice 1b refund and return scopes join after task 1 confirms them), `SHOPIFY_WEBHOOK_TOPICS` (the 13 topics), `hookAddress` (`PUBLIC_URL` + `/api/hooks/shopify/<connection id>`), `isHttpsAddress`, and `topicsToCreate` (skips a topic already subscribed to exactly that address).
- `connect-health.ts` (task 6, AC-1): `decideConnectHealth`, the pure verdict of a connect check: `failing` with the first of `SCOPES_MISSING` (with the missing handles), `PROTECTED_DATA_MISSING` (the latest order lacks a ship to name, phone, or address line; nothing with no order yet), `CURRENCY_MISMATCH` (against the `currency` setting), `PUBLIC_URL_NOT_HTTPS`, else `ok`; the warnings `SHOP_TIMEZONE_DIFFERS` (against the `timezone` setting) and `APP_OWNED_BY_PERSON` never change the health.
- `connector-shopify.queue.ts` (tasks 6 and 7): `CONNECTOR_SHOPIFY_QUEUE`, the one pg-boss queue `connector-shopify` owned by `connectors.shopify.sync` (`CONNECTOR_SHOPIFY_RETRY`: 17 retries with backoff from 30 seconds, each wait capped at 15 minutes, so at least 3 h 15 min of retries, longer than the 3 hour `READS_FAILING` rule; expiry 300 seconds; worker `groupConcurrency: 1`, which pg-boss enforces in its fetch across workers), `ShopifyJobData` (the kinds `connect` and `inbox`: the connection id, and for `inbox` the event id, nothing else), `INBOX_JOB_PRIORITY` (20), and `connectionGroup` (`group: { id: connectionId }` and the retry policy on every send, so a queue an earlier build created with other options still retries this way). `connector-clock.ts`: `ConnectorClock`, the clock the inbox job judges the 3 hours by (a test binds a moved one).
- `connector-shopify.worker.ts` (task 7): `ConnectorShopifyWorker`, which declares the queue and its one handler through the worker's `JobRegistry` and runs each job by its kind (`ConnectJob.connect`, `InboxJob.run` with the pg-boss `retryCount`).
- `inbox.job.ts` (tasks 7, 9, and 11, AC-5 to AC-15, Inbound processing item 3): `InboxJob`. It skips unless the event is `received`; a paused connection leaves it `received` and completes (resume is task 16). `app/uninstalled` is confirmed first (security review L1, the topic header is not signed): `ShopifyClient.confirmAccess`; only `APP_NOT_INSTALLED`, `CREDENTIALS_REJECTED`, or `APP_ORGANIZATION_MISMATCH` confirms (health `failing` with that code, the event `processed`), Shopify accepting records the event `ignored` `uninstall_not_confirmed`, and a transient error retries. An order topic needs a connection `config` that parses (else the event fails `CONNECTION_CONFIG_INVALID`), then reads the order back with `ORDER_READ` before any unit of work: a transient error counts an attempt and throws (pg-boss retries; the event stays `received`); health turns `degraded` `READS_FAILING` once an event of the connection with a failed attempt was received 3 hours ago by `ConnectorClock`, or when the last pg-boss retry fails, and the next good read clears it. **Milestone 1 limit**: after the last retry, and on a paused connection, incomplete or unreadable credentials, or a token refusal, the event stays `received` with no job until the scheduled sweep of task 12 (or the resume of task 16) sends it again. A token refusal sets health `failing` with its code and leaves the event `received` (no task per order). A successful read keeps `API_VERSION_FELL_FORWARD` in `health_warnings` while the answer is in another version and clears it when they match. A read back whose order id is not the event's gid fails the event `READ_BACK_MISMATCH`; a Shopify time that is not an ISO instant fails it `ORDER_UNREADABLE` (security review L3), and every time is bound in SQL as UTC ISO text. Inside `OrderTransactions.run` it locks the event and the order mapping again: a test order is `ignored` `test_order`; an empty read back is `ignored` `not_visible`; a known order is `ignored` `stale` (snapshot not newer than `external_version`), else applied (task 9, below); a new order writes its mapping first (`createdOrderState`: `appliedLineIds`, `appliedLines`, `discountCodes`, `unmappedGateways`, the creation facts `creationGateways` and `creationTransactionIds` of lead decision D10, `unmappedLines` when any, and `deliveryFulfillmentId` for every order created not cancelled whose creation read already holds an active fulfillment, imported shipped orders included, so a later refund never reaches `applyChannelEdit` (code re-review R1)), then `OrderIntake.createFromChannel` (actor `system_job` `connectors.shopify.inbox` with the job id, or `import` with the event id as the run when the mapper says so), the mapping's `local_id`, a live order's named move when Shopify already cancelled it (`cancelFromChannel`; an answer that applied nothing is outcome `cancel_not_applied`) or fulfilled it (`recordCarrierDelivery`), and `last_order_at`; with a listed gift tag on a paid order the outcome is `gift_tag_not_free`. Every other `received` order topic event of the same order received before this run's read back started becomes `processed` `coalesced` in the same transaction (a later one, or a refund event, waits for its own job; a held edit coalesces nothing, security review L2), and the event takes the order name as `subject_label`. **A known order's newer read back (task 9)**, in the same unit and in this order: a Shopify cancel calls `OrderIntake.cancelFromChannel` with `channel.<reason>` and nothing else (outcome `cancel_not_applied` when it applied nothing: `already_final` or `after_pickup`); late variant links (`linkChannelLineVariant`; one orders refuses as `VariantUnknown` is planned again with that variant unmapped); `OrderIntake.applyChannelEdit` with the snapshot (every open line while no fulfillment is active and on the read where the first one appears, code review m1; afterwards the held lines); `write_back_open` records the carrier delivery and ends the event `ignored` `held_write_back_open` without coalescing, the mapping and version untouched (the read back after the command syncs or is resolved is task 13's outbound framework, a TODO seam in `applyKnown`), and any other refusal is outcome `edit_not_applied` (orders raised `channel_edit_not_applied`); then the first active fulfillment calls `OrderTransitions.recordCarrierDelivery` with source `shopify_fulfillment` (its gid) at its `createdAt` (orders ignores a repeat, and takes the next one after it cleared the freeze; the mapping remembers it as `deliveryFulfillmentId`); then `rederivePaymentMethod` when the config maps a creation gateway to another method (D10; `PaymentMethodLocked` is recorded on the mapping as `paymentMethodLocked` and left, outcome `payment_method_locked`); then the mapping's `external_version` and `state` move to the read. A `ShopifyOrderMappingError` or an orders domain error rolls the unit back, and a separate transaction marks the event `failed` with the upper case code (`ORDER_NUMBER_TAKEN` from `OrderNumberTaken`) and publishes `InboundEventFailed`; any other error is retried. The context comes from the connection (`config.altPhoneAttribute`, `config.gatewayMethods`, `go_live_at`, its store's own channel), the settings `sales_tax_rate` (as `defaultTaxRate`) and `shopify_gift_tags`, and the variant mappings in `connection_external_ids` (none before task 8: lines stay unmapped; the product read before mapping, review M8, waits for task 8). When the latest finished connect run saw no order (`counts.latestOrderChecked` false), the first applied order without a ship to name, phone, or address line sets health `degraded` `PROTECTED_DATA_MISSING` (while health is `ok`). **A customer topic (task 11)** reads the customer back with `CUSTOMER_READ` (same transient, refusal, and token rules), fails `CUSTOMER_UNREADABLE` (a bad shape or a non ISO `updatedAt`) or `READ_BACK_MISMATCH`, is `ignored` `not_visible` for an empty read, `ignored` `stale` when an earlier processed event of the customer carried a webhook `updated_at` at or after the read's `updatedAt`, `processed` `no_phone` writing nothing when the phone is absent or does not parse, and otherwise calls `CustomersService.findOrCreate` with `phoneVerified: false` (owner ruling L1, option A: a Shopify customer's phone never links to an existing customer; a known phone with an unknown Shopify id attaches nothing and the event is `processed` `unverified_phone`, a known Shopify id with a new phone attaches no phone and is also `unverified_phone`; a new phone and id still create a customer) in one plain transaction with the event's end (no order is touched, so not `OrderTransactions.run`); other `received` customer events of the same customer received before the read are `coalesced`.
- `connect.job.ts` (task 6, AC-1, AC-2): `ConnectJob`, the `connect` kind (run by `ConnectorShopifyWorker`): opens the sealed credentials, gets the token, reads the shop, the scopes (stopping there when one is missing), the locations (counted only: the stock location mapping and the other locations report are later tasks), and the latest order (reduced to present or not at once), decides the health, and when it passes registers the missing webhook subscriptions (a refused one ends `degraded` with `WEBHOOKS_MISSING`). The token answers map to `APP_NOT_INSTALLED`, `APP_ORGANIZATION_MISMATCH`, `CREDENTIALS_REJECTED`; keys that no longer open to `CREDENTIALS_UNREADABLE`; other refusals to `SHOP_UNAVAILABLE`, `ACCESS_DENIED`, or `CONNECT_REJECTED`. It fills the store's names from the shop name through `ChannelsService.renameStore` the first time it reaches the shop (`api_version` still null, so names a manager edited later are kept), stores `config.shopTimezone` and `api_version`, writes `API_VERSION_FELL_FORWARD` into the warnings when any answer of the run came in another version (a matching run clears it), and writes a `connect` sync run (status, counts: locations, online locations, missing scopes, topics subscribed and created; cost points). A transient error marks the run failed with its code and throws, so pg-boss retries.

## Never touches

- Other modules' tables, the stock ledger, and the owner database role.
- The connections routes and tables outside its jobs: `connections/` owns them (see [../README.md](../README.md)). A Shopify call never happens outside a job of the `connector-shopify` queue.
- A real shop domain, token, secret, or customer's data: fixtures use invented people and `fixture-store.myshopify.com` only.

## Decisions

- **Orders in full and customer webhooks** (integrations lane, spec 0015 tasks 9 and 11, 2026-11-08, no ADR yet):
  - **Gateway mapping change: driven from the read back, no PATCH yet; the rederive uses the facts at creation only (lead decisions D10 and D10a, 2026-11-08).** `PATCH /api/connections/:id` (with `gatewayMethods`) belongs to task 16, which builds the Mapping tab, its audit code, and the access sweep row; until then nothing in the app changes `config.gatewayMethods` after connect. At `createFromChannel` the mapping records, once and never again, `state.creationGateways` (each gateway at creation and the method it mapped to then) and `state.creationTransactionIds` (every successful `SALE`, `CAPTURE`, and `REFUND` known at creation, D10a). Every gateway lookup uses one key, the raw Shopify name capped at 200 characters as `config.gatewayMethods` keys it (`gatewayKeyOf`, security review N1): the creation lookup, the stored key, the remap check, and the rederive, so a name that cleaning would change (padding, a right to left mark, more than 100 characters) never looks remapped. Nothing in the mapping state ever breaks `jsonb` (security review N3 and N4, code re-review R4): a gateway key drops a high surrogate left alone by the 200 cut, and a name holding U+0000 or an unpaired surrogate gets no key at all (treated as unmapped, never stored); creation looks a name above 200 characters up under that same key (code re-review nit 1); every cleaned text (gateway names listed as unmapped, discount codes, order name, line titles, ship to, note, customer name) loses its control characters and then its unpaired surrogates (`cleanText`, `withoutLoneSurrogates`); every Shopify id stored verbatim (order, line item, variant, fulfillment, transaction, customer) must be storable text (`StorableShopifyId`) or the read fails `ORDER_UNREADABLE` or `CUSTOMER_UNREADABLE`; and the connect job's shop name and time zone must be storable too (else the transient `INVALID_RESPONSE`). A newer read back rederives only when the current config maps one of the creation gateways to another method, and the new payment applies the creation rules to the creation gateways and the creation transactions only, with the current mapping; a gateway, a sale (a "mark as paid" `manual` sale), or a refund added after creation never counts (D10a: a later refund belongs to the refund path, task 10's `ChannelRefundRecorded`), so a cash on delivery order never turns prepaid behind the courier's back and a goodwill refund never raises what the courier collects. Orders answers a repeated rederive with no change. Mappings written before D10 (no creation facts) are never rederived: the creation facts cannot be told apart from later ones without the transaction times, which `ORDER_READ` does not read; a manager who remaps a gateway for such an order corrects it by hand. Task 16's PATCH, with the body fields named in the spec's API table (`expectedUpdatedAt`, `gatewayMethods`, `reason?`, and the rest), then only has to enqueue one read back of each order whose creation gateways changed.
  - **While a fulfillment is active** the snapshot holds exactly the lines the app holds, at the quantities last applied (`state.appliedLines`), with Shopify's current ship to: added lines and refunded quantities never reach `applyChannelEdit` (task 10's `exchange-by-edit.ts` and `ChannelRefundRecorded` take them), while a ship to change does, and orders refuses it after the carrier delivery (`edit_not_applied`). **On the read where the first active fulfillment appears** (its id is not yet `state.deliveryFulfillmentId`), the full snapshot is applied first and the carrier delivery recorded after it (code review m1): Shopify allowed those changes before the fulfillment froze the order. The small window this leaves: a line changed after the fulfillment but before our first read of it (a refund, a line added for an exchange) also counts as an edit. A milestone 1 mapping without `appliedLines` sends nothing to `applyChannelEdit` once its fulfillment was reported (code review m4), so a refund never looks like an edit; until then its first fulfillment read takes the full snapshot as above.
  - **A cancel ends the read back**: no edit, link, delivery, or rederive after `cancelFromChannel` (task 9a decides what a cancel with an active fulfillment does to stock).
  - **`held_write_back_open` is `ignored`**, not `processed`: nothing was applied and the version stays, so the read back after the command settles applies the change. It coalesces no other event (security review L2), so later events of the order keep their own jobs. The first fulfillment's carrier delivery is still recorded in that unit (AC-13; orders raises `delivery_created_before_edit_synced` for the open command), and a late link made there stays; because the delivery is then recorded while `deliveryFulfillmentId` is not, the next read takes the full snapshot and orders refuses a pre-fulfillment change (`edit_not_applied`, an attention for a person).
  - **A cancel that applies nothing** (`already_final`, `after_pickup`) is outcome `cancel_not_applied`, on a new or a known order, so the history shows why nothing changed.
  - **Customer stale rule without a version column**: `connection_external_ids` has no `customer` entity (spec 0002 enum), so a customer read is stale when an earlier processed event of the same customer carried a webhook `updated_at` at or after the read's `updatedAt`. A webhook's time is never later than what its own read saw, so only a truly older read is called stale; `findOrCreate` replays write nothing new anyway.
  - **Open, decided by task 1's recordings (code review m2)**: whether Shopify drops `currentQuantity` to 0 on a cancel that restocks. If it does, a live order first read already cancelled fails `NO_OPEN_LINES` instead of arriving cancelled; the mapper then needs a cancelled order rule.
  - **Open, a follow up (code re-review nit 2)**: the fulfillment time bound is relative to the order's `updatedAt`, which is itself unbounded; a broken answer with a far future `updatedAt` passes, becomes `external_version`, and makes every later read `stale`. Bounding both against the read's own clock (`read_started_at` plus a margin) would close it.
  - **Seams left**: task 8 (product read before an order with unmapped variants, new variant mappings; the late link already runs when a mapping exists), task 9a (fulfillment stock out after the carrier delivery step), task 10 (exchange by edit and refunds while a fulfillment is active), task 13 (one read back when a held command syncs or is resolved).

- **Synthetic fixtures** (owner ruling 2026-11-07): until a Shopify development store exists, fixtures are hand written and shaped per shopify.dev for `2026-10`; every file says "synthetic, to be replaced by recordings". No ADR yet.
- **Order mapper choices** (integrations lane, 2026-11-08, no ADR yet): a read that may be short (line items or discount applications with a next page, a full page of transactions, fulfillments, or a line's tax lines: 40 line items, 30 transactions, 10 fulfillments, 10 tax lines a line, `TAX_LINES_TRUNCATED` for the last; the pages keep `ORDER_READ`'s estimated cost near 805 of the 900 point budget (the transaction `id` D10 reads is a scalar)) is refused, never mapped, because a short snapshot would cancel the unread lines; a gift tag matches without regard to case; a gift tag whose setting value is not a `GiftReasonCode` maps as `other` and is flagged; a line without tax lines gets the context's `defaultTaxRate`, which the inbox job fills from the `sales_tax_rate` setting (lead decision D8, 2026-11-08), else `0.00`; an active fulfillment is one not `CANCELLED`, `ERROR`, or `FAILURE`; the found cash of a fulfilled order compares Shopify's `currentTotalPriceSet` with the prepayment.

## Carry-overs

Settled for the order mapper on 2026-11-08 from the `2026-10` reference (`https://shopify.dev/docs/api/admin-graphql/2026-10/`, pages read with WebFetch that day):

- **D4, `Customer.phone` deprecated.** `objects/Customer` marks `phone` (`String`) deprecated and documents `defaultPhoneNumber` (`CustomerPhoneNumber`, "The customer's default phone number"); `objects/CustomerPhoneNumber` documents `phoneNumber: String!`. `ORDER_READ` selects `customer { defaultPhoneNumber { phoneNumber } phone }`; the mapper reads `defaultPhoneNumber.phoneNumber` first and the deprecated `phone` only as a fallback, in one accessor (`customerPhoneOf`). Every fixture customer now carries `defaultPhoneNumber` beside `phone`. Drop `phone` from the query when a pinned version removes it.
