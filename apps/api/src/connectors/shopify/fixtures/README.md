# Shopify fixtures (synthetic, to be replaced by recordings)

> **These files are synthetic, to be replaced by recordings.** Nobody recorded them from a Shopify store. They are hand written, shaped per the Shopify Admin GraphQL reference for API version `2026-10` (`SHOPIFY_API_VERSION`, [spec 0015](../../../../../../docs/specs/0015-shopify-connector/index.md)). Owner ruling 2026-11-07: until a Shopify development store exists, fixtures are hand written. Spec 0015 task 1 records them again from a development store with invented customers; the open box is scope feature 13, "Re-record fixtures from a Shopify dev store" ([scope](../../../../../../docs/scope/index.md)). Replace with recordings from a development store (spec 0015 task 1; scope feature 13 box), and until then never claim a Shopify behaviour from these files.

Each file carries a top level `_fixture` key (`synthetic: true`, `note`, `apiVersion`, `scenario`, `step`, `shapedFrom`). JSON cannot hold comments, so that key is the banner. A reader that replays a file ignores `_fixture`.

## Layout

`fixtures/<scenario>/NN-<operation>.json`, the layout of spec 0015 ("Fixtures and the mock server", AC-26). `NN` is the order of the calls inside the scenario: file `02` is what Shopify answers after the change that follows `01`, so a replay that serves the same request twice serves the files in order. Every file holds:

- `request`: `method`, `url` (`https://<shop>/admin/api/2026-10/graphql.json`), `shopDomain`, `operationName`, `variables`, and `headers` (only `X-Shopify-API-Version`; no token).
- `response`: `status`, `headers` (`X-Shopify-API-Version`, `Content-Type`, and `Retry-After` on a 429), and `body` (`data`, and `extensions.cost` with the throttle status the client reads for [AC-25](../../../../../../docs/specs/0015-shopify-connector/index.md)).

A token exchange (`NN-access-token.json`, the client credentials grant) records `url` `https://<shop>/admin/oauth/access_token` with `operationName` and `variables` null and no body: the form carries the client secret, so it is never recorded, and the replay matches it on method and path. Its token value is an obviously fake string.

A bulk operation result (`NN-bulk-result.json`, task 12) records a `GET` of the signed result address (an invented `https://storage.fixture.example/...` host) with `operationName` and `variables` null, and its `body` is the JSONL text itself (a string, one node a line); the replay matches it on method and path.

The order files answer `ORDER_READ` (`../shopify-queries.ts`, operation `OrderRead`, variable `id`) and the customer files `CUSTOMER_READ` (operation `CustomerRead`, variable `id`; fields read on `objects/Customer` and `queries/customer` for `2026-10` on 2026-11-08: `id`, `updatedAt`, `firstName`, `lastName`, `displayName`, `defaultPhoneNumber.phoneNumber`, and the deprecated `phone`; the cost figures are invented); the fixtures keep the name and the variables and no query text, so a replay matches on shop, operation, and variables. Each order file holds at least every field `ORDER_READ` selects (and more, which the mapper's schema strips).

## Field conventions

- Shops: `fixture-store.myshopify.com` and `fixture-store-2.myshopify.com`. No real shop domain, token, or secret anywhere. Hosts of links inside the data end in `.example`.
- Ids are Shopify gids with invented numbers: orders `5550000...`, line items `6660000...`, variants `7770000...`, customers `8880000...`, fulfillments `9990000...`, one location `4440000000001` (the same number prefixes the order agreements, which are `OrderAgreement` ids).
- People: invented Arabic names (`مها تجريبية`, "Maha Experimental"), invented streets, areas that are public place names only. Phones are in the test style `+2010000001xx` (a valid Egyptian mobile shape, `EgyptianPhone.parse` accepts them; they are not claimed to be unassigned numbers).
- **Second phone**: an order custom attribute (`customAttributes`, what Shopify's admin calls a note attribute) with key `alt_phone`. Chosen because spec 0015's value sourcing reads it from "the order custom attribute named by `config.altPhoneAttribute`", so a test sets `altPhoneAttribute` to `alt_phone`; it keeps the note field for the customer's own note.
- **Sale amounts**: a product sale's `totalAmount` is the line's unit price less its discount allocation, times the sale's quantity (`Sale.totalAmount` is after discounts on the `2026-10` reference), so a removal and the addition it nets carry the same absolute amount; task 10 made every order fixture follow this.
- **Money**: every amount is a string with two decimals (`"450.00"`), in `shopMoney` and `presentmentMoney`, currency `EGP`. Real Shopify may trim trailing zeros; the recordings will settle it, and the mapper must parse the string, never compare text.
- **Prices**: tee 450.00 a piece, code `WELCOME10` 45.00 a line as a `discountAllocations` entry, VAT 14 percent as `taxLines` (`rate` 0.14, `ratePercentage` 14.0), shipping 50.00 with a 7.00 tax line.
- **Connections** (`lineItems`, `shippingLines`, `agreements`, `sales`, `refundLineItems`) hold `nodes` only, with no `edges`; `lineItems`, `discountApplications`, `agreements`, and each agreement's `sales` also hold `pageInfo { hasNextPage }`, as `ORDER_READ` selects it (the sales history's `pageInfo` was added by spec 0015 task 10), and no other connection holds `pageInfo`. A refund agreement carries `refund { id }` (`RefundAgreement`, task 10). `fulfillments`, `transactions`, `refunds`, and `customAttributes` are plain lists, as the reference types them.
- **Times**: UTC, ISO 8601 with `Z`. `updatedAt` always moves forward inside a scenario.
- `customerJourneySummary.lastVisit` and `firstVisit` carry `utmParameters` and a `landingPage` with `email_token=fixture-not-on-the-allow-list` to test the UTM allow list (spec 0002 Follow-up m5).

Findings and gaps:

- **`Customer.phone` is deprecated** on `2026-10`; its documented replacement is `defaultPhoneNumber { phoneNumber }` (`CustomerPhoneNumber`, checked 2026-11-08). Every fixture customer carries both, the same number, so the mapper reads the replacement first and the deprecated field only as a fallback (carry-over D4 in the [Shopify README](../README.md#carry-overs)).
- **`LineItem.fulfillableQuantity` is deprecated.** The fixtures use `unfulfilledQuantity` and `refundableQuantity`, both listed on the page; `ORDER_READ` selects `unfulfilledQuantity` (carry-over D5).
- **`discountApplications`** (checked 2026-11-08: `DiscountApplication.targetType`, `DiscountCodeApplication.code`, `DiscountApplicationTargetType` `LINE_ITEM` and `SHIPPING_LINE`): each order carries its codes as `LINE_ITEM` code applications (carry-over D6). The older `discountAllocations[].discountApplication` entries inside line items stay as written and are not selected by `ORDER_READ`.
- **Not verified**: the `Location` fields beyond `id`; `Order.agreements` ordering; whether Shopify lists `paymentGatewayNames` as `Cash on Delivery (COD)` (a merchant's own manual payment name) or `manual` after "mark as paid"; the real size of the cost extension numbers. These are invented to be plausible.
- **Tax mode and totals** (audit A3 and review round 1, 2026-11-14): every order carries `taxesIncluded: true` (prices include VAT, the `prices_include_vat` default) and `currentShippingPriceSet` (the shipping after discounts and refunds, which the mapper charges; `totalShippingPriceSet` stays in the files but is no longer read), and every line item carries `quantity` (units ordered, refunded and removed ones included). Every creation read's `currentTotalPriceSet` equals what the intake computes: the open lines (current quantity times unit price, less the discount allocations prorated to the current quantity) plus `currentShippingPriceSet`; `currentSubtotalPriceSet` is that total less the shipping. A returned or removed line lowers the current total and subtotal by its discounted price, and a cancelled order's current total may be 0 (it is not compared). The 2026-11-14 passes corrected the current totals of `order-same-variant-lines` (01 to 03, and their `totalPriceSet`), `order-imported-refund-before-go-live`, `order-imported-refund-after-go-live`, `order-refunded-after-fulfillment` (02, 03), `order-edit-pair-across-midnight` (02), and `order-imported-refunded` (02), which had subtracted an undiscounted price or forgotten the discount, and the current subtotals of the same files. The two recorded bulk run requests (`backfill-go-live` 04, `backfill-paged-fallback` 03) carry `taxesIncluded`, `currentShippingPriceSet`, and the line item `quantity` in their query text, as `ordersBulkQuery` sends it.
- `Order.confirmed` and webhook payloads are not used. A webhook body is a REST style payload, not part of these GraphQL fixtures; spec 0015 task 7's signature tests carry their own known good and tampered bodies.

## Who uses them

`../order-mapper.spec.ts` maps every order scenario with the real mapper (spec 0015 `order-mapper.ts`). `apps/api/test/orders-intake.e2e-spec.ts` (spec 0013 milestone 3) reads every order scenario through `apps/api/test/shopify-order-reader.ts`, which parses `response.body.data.order` with the mapper's exported `ShopifyOrder` schema, and maps it with `mapShopifyOrder`, `mapShopifyOrderSnapshot`, and `replacementInput`. A scenario's files are used by number, and the mapper reads only the fields `ORDER_READ` selects. The bad phone scenario has its own customer id on purpose, so the order stays unlinked (a known customer id would link it).

`../edit-netting.spec.ts` and `../exchange-by-edit.spec.ts` (spec 0015 task 10) read `order-edited-size-swap`, `order-same-variant-lines`, `order-edit-pair-across-midnight`, `order-exchange-added-lines`, `order-refunded-after-fulfillment`, and `order-imported-refunded`; `apps/api/test/shopify-edit-netting.e2e-spec.ts` replays the first five through the real inbox job (`order-exchange-added-lines` twice, once with the original delivered and once still shipped).

`apps/api/test/shopify-hook.e2e-spec.ts` (spec 0015 task 7) replays `order-created-cod`, `order-edited-size-swap` (01 and 02), `order-unmapped-line`, `order-number-collision` (03, the name that collides), and the inbox scenarios (`order-not-visible`, `order-test-order`, `order-read-server-error`, `order-protected-data-missing`, `order-read-mismatch`, `order-version-fell-forward`) through the real inbox job, with `connect-app-not-installed` and `connect-credentials-rejected` as token answers; the inbox scenarios are read only there, not by the mapper spec or the orders intake suite. Its webhook bodies are built and signed inside the test with a fake secret, never stored here.

`apps/api/test/shopify-orders-in-full.e2e-spec.ts` also replays `order-prepaid-gateway` 01 with the card gateway unmapped (`GATEWAY_UNMAPPED`, then created once mapped), `order-total-mismatch` (`TOTAL_MISMATCH`), and `order-free-shipping` (no shipping charged); `../order-mapper.spec.ts` reads `order-partly-refunded-quantity` for the prorated discount (review round 1).
