# Catalog

Products and their SKUs (variants) for the staff back office: create a product, list and read SKUs, edit and delete a SKU; styles, seasons, product groups, barcodes, and cost records (spec 0012).

## Owns

- Routes, all staff only: `POST /api/products` (optional `styleCode`, `seasonId`, `productGroupId`: defaults the SKU code, none, `MAIN`; a code a SKU holds answers `SKU_TAKEN`, a style code only a style holds `STYLE_CODE_TAKEN`, also when it defaulted to a free SKU code), `GET /api/skus`, `GET /api/skus/:id`, `PATCH /api/skus/:id`, `DELETE /api/skus/:id` in [catalog.controller.ts](catalog.controller.ts), which also holds `catalogHttpError`, the one map from `CatalogError` codes to HTTP answers
- Styles (spec 0012, AC-8 to AC-10): [styles/](styles/) `GET /api/styles` (keyset by style code, filters `seasonId` or `none`, `productGroupId`, `status`, and `q`, built by [search/style-list-sql.ts](search/style-list-sql.ts)) and `GET /api/styles/:id` (`stock.view`); `PATCH /api/styles/:id` (name, description, season, group, tags, stale check), `POST /api/styles/assign` (1 to 200 styles, all or nothing, one `style.edited` per changed style under one correlation id), and `POST /api/styles/:id/variants` (`catalog.edit`); `PATCH /api/styles/:id/code` (`catalog.manage`). Adding a variant locks the style row first, matches option names and values after `ssd_search_normalize` (either language against either), appends a missing option (at most 3, role from `OPTION_ROLE_NAMES`) or value, and inserts the variant stocked, untracked, in `pc`; `product_variants_options_unique` answers `OPTION_COMBINATION_TAKEN`. An option given twice, or a name or value that normalizes to nothing in both languages (`-`), answers 400 `INVALID_INPUT`, the route's one bad input status. Style, season, and group ids in requests are lowercased by the contract (`CatalogId`), so an uppercase id is the same id and a case only change records nothing; `style.edited` diffs carry `seasonCode` and `productGroupCode` beside the ids
- Seasons and product groups (spec 0012, AC-6, AC-7): [seasons/](seasons/) and [product-groups/](product-groups/), list (`stock.view`), create, edit with the stale check, archive, unarchive, delete only while unreferenced (`catalog.manage`), both over the one [style-grouping-store.ts](style-grouping-store.ts); the seeded `CORE` season and `MAIN` group are renamed but never recoded, archived, or deleted. A style takes a season or group only through `CatalogService.assignableGrouping` (exists, not archived, read `FOR SHARE` so an archive waits)
- Cost records (spec 0012, AC-12, AC-13): [cost-records/](cost-records/) `GET /api/styles/:id/cost-records` (`stock.view` and `cost.view`; keyset by `recorded_at` and `id`, newest recorded first, at most 50) and `POST /api/styles/:id/cost-records` (`catalog.edit` and `cost.view`, 201): a record for the style or, with `variantId`, an override of one of its variants (a variant outside the style, an unknown style, or an unknown season answers 404 `NOT_FOUND`; any season, archived too). A record from before today's operating day (`ssd_operating_day(now())`) needs a reason (422 `REASON_REQUIRED`); the reason lives only in the `cost_record.recorded` entry (record type `style`, record id the style, `reasonRequired: true` when backdated). `CostRecordsService` only inserts, inside `catalogTransaction`, with `recorded_by` the caller; it answers the new record and every variant's cost in force today. "Recorded by" names come from identity's `StaffDirectoryModule`
- The style page's cost (spec 0012, AC-12, AC-16): every `StyleDetail` answer carries each variant's `cost` in force today from `CostService.costForMany`, and the controller passes it through `serializeStyleDetail` (in [styles/styles.service.ts](styles/styles.service.ts)), which drops the `cost` key on every variant for a caller without `cost.view` (`cost` is in `COST_FIELD_KEYS`)
- The channel upsert contract for spec 0015 (spec 0012, AC-14, AC-15, AC-17): [channel-sync/catalog-channel-sync.ts](channel-sync/catalog-channel-sync.ts) `CatalogChannelSync`, exported by `CatalogModule`, the only way a sales channel creates or changes catalog rows. `applyProduct(tx, ChannelProductInput, actor)` runs in the caller's READ COMMITTED transaction (checked at entry, `ChannelSyncError` `NotReadCommitted`; the actor must be a `system_job`, else `NotSystemJob`, [channel-sync/channel-sync-error.ts](channel-sync/channel-sync-error.ts); it never opens, commits, or retries one; the caller reruns the whole call on a deadlock) and answers `ChannelProductResult` (`packages/contracts/src/catalog/channel-product.ts`, which refuses control and bidi override characters in every channel text): one advisory lock per call, `pg_advisory_xact_lock(727_020, hashtext('catalog.channel_style:' || handle with ASCII letters lowercased))` ([channel-sync/channel-rules.ts](channel-sync/channel-rules.ts)), then, after the first resolve, one `pg_advisory_xact_lock(727_021, hashtext('catalog.channel_sku:' || code))` per SKU code planned as new, in sorted order, and a second resolve (lead ruling 2026-11-11: the same product under two handles makes one style); each variant resolves by the mapped `variantId` (else `sku_mismatch` or `needs_sku`), else by the trimmed, uppercased SKU (ASCII only: a non ASCII SKU is `invalid_sku`, a non ASCII barcode `barcode_conflict`; `linked` on its first link; the SKU is checked again after the variant lock), else is created (`needs_sku` and `invalid_sku` never are); a new style only when the first variant must be created (code from the handle, or the first SKU code when the handle keeps no letter or digit; `-2`, `-3` on a clash, the base cut to stay within 64 characters; group from `catalog.store_product_groups`, season from `catalog.new_style_season`, both read through `SettingsService` in the transaction; unknown or archived gives `MAIN` and none), deleted again if it ends with no variant; content (the name in `channel_name_language`, tags, product type, vendor as `brand`, price, compare at price, weight, requires shipping, a linked variant's option values, the one `from_channel` barcode) and the link itself (`channel_linked_at`, `channel_name_language`) only from the source store (`catalog.source_store_id`, any store while null; lead ruling 2026-11-11); compare before every write, so a second identical call writes no row and no entry. Clashes never abort the caller: they are pre-checked under the held locks, inserts take `ON CONFLICT DO NOTHING` (a variant insert that returns no row is then identified: the SKU's holder, else the option values' holder, else `UnknownConflict`), and a savepoint is kept only where a parallel writer can still clash (an archived variant holding the option values, a channel barcode being replaced). Entries `style.channel_created`, `style.channel_updated`, `sku.channel_created`, `sku.channel_linked`, `sku.channel_updated` carry the changed fields (options as `[{ name, value }]`) and a `channel` object (store, product, variant ids). `unlink(tx, { styleIds, variantIds }, actor)` clears `channel_linked_at` (and the style's `channel_name_language`), turns channel barcodes into app barcodes, bumps `updated_at`, and records `style.channel_unlinked` and `sku.channel_unlinked` as the `system_job` actor. A 2,048 variant product is created in one call in about 4 s and applied unchanged in about 0.2 s (measured 2026-11-11 in `channel-sync.e2e-spec.ts`), so the statements are not batched
- Channel owned fields (spec 0012, AC-15): `PATCH /api/skus/:id` answers 409 `FIELD_OWNED_BY_CHANNEL` (`field: 'price'`) for a new price on a linked variant, and `PATCH /api/skus/:id` and `PATCH /api/styles/:id` (`field: 'name.en'` or `'name.ar'`) for a name that changes a linked style's `channelNameLanguage`; `PATCH /api/styles/:id` (`field: 'tags'`) for a tags change of a linked style, `DELETE /api/skus/:id/barcodes/:barcodeId` (`field: 'barcode'`) for a `fromChannel` barcode, and `POST /api/styles/:id/variants` (`field: 'options'`) for a new option or value on a linked style; resending the stored value passes, and a stale `updatedAt` answers `STALE_RECORD` first. `SkuDetail` carries `channelLinked`, `channelNameLanguage`, and `barcodes[].fromChannel`; `StyleDetail` carries `channelLinked`, `channelNameLanguage`, and each variant's `channelLinked` and `barcodes[].fromChannel`
- Barcodes (spec 0012, AC-10): [barcodes/](barcodes/) `POST /api/skus/:id/barcodes` and `DELETE /api/skus/:id/barcodes/:barcodeId` (`catalog.edit`); a code any SKU holds answers `BARCODE_TAKEN` with that SKU's `skuCode`
- Audit entries (spec 0012, AC-17) for every person action above, through `AuditService.record` in the action's own transaction: `style.edited`, `style.code_changed`, `style.variant_added`, `sku.barcode_added`, `sku.barcode_removed`, `cost_record.recorded`, `season.*`, `product_group.*` (the actor helpers are in [catalog-caller.ts](catalog-caller.ts)). Creating a product stays unaudited (spec 0006); the channel sync's entries are written as the caller's actor (a `system_job`), under the correlation id `AuditService.newCorrelationId(actor)` gives
- Archiving a SKU (`setArchived`, called by inventory's SKU lifecycle) archives its style only with its last active variant; unarchiving a SKU unarchives its style. Both lock the style row (`SELECT ... FOR NO KEY UPDATE`, its own statement) before the conditional style update, the lock `addVariant` takes first, so an archive, an unarchive, and a variant add of one style queue and the later one sees the earlier one's variants (`master-data.e2e-spec.ts` holds both races). Deleting a style's last SKU deletes the style and its options
- Every catalog write transaction goes through [catalog-transaction.ts](catalog-transaction.ts) (`catalogTransaction`): READ COMMITTED, run again once on a deadlock or serialization failure (`isRetryable` of `src/database/sql.ts`), like the ledger's `ledgerTransaction`
- The catalog logic: [catalog.service.ts](catalog.service.ts), wired in [catalog.module.ts](catalog.module.ts)
- SKU search (spec 0012, AC-3 and AC-4): [search/sku-list-sql.ts](search/sku-list-sql.ts). `GET /api/skus` first runs `ssd_search_normalize(q)` in SQL (the same function the stored `product_variants.search_text` uses), keeps the first 5 distinct words, then `buildSkuListSql` unions three branches, each filtered (status, `seasonId` or `none`, `productGroupId`, `styleId`, cursor), ordered by code (`COLLATE "C"`), and limited: the exact barcode (`barcodes_code_unique`), the code prefix (`product_variants_sku_c_idx`), and, when a word has 3 or more characters, every word contained in `search_text` (`product_variants_search_trgm_idx`). Rows carry the style, season, product group, and option values; `GET /api/skus/:id` adds the barcodes. `search_text` is kept by database triggers, never by this module's code
- Cost lookup: [cost.service.ts](cost.service.ts) `CostService.costFor(variantId, onDate)` returns the unit cost with its cost basis from `cost_records` (a variant override beats its style's record on the same day; the latest `recorded_at` breaks the next tie, and the greatest `id` the last one), or `not_set`, never 0. `CostService.costForMany(variantIds, onDate)` answers the same for many variants in one query, plus the chosen record's `effectiveFrom` and `inheritedFrom` (`style` or `variant`), keyed by each id as given; `CostService.today()` is today's operating day. The rule is the pure [cost-selection.ts](cost-selection.ts) (`selectCost` and `pickCostRecord`). Cost records are append only
- Renaming a SKU also renames the style code of a one variant product whose style code was the old SKU code; a code that only another product's style holds answers `STYLE_CODE_TAKEN` (409), a code another SKU holds `SKU_TAKEN`
- A product is a style: `style_code` (the SKU code on the create path unless `styleCode` is given), a `product_group` (`MAIN` for a one line brand) and an optional season, with 0 to 3 options (`role` size, color, or other) and 1 to N variants
- The catalog tables, defined in [packages/db](../../../../packages/db/src/schema/catalog.ts): products, options, variants, barcodes, units of measure and conversions, product groups, seasons, and cost records

- Its registry row (spec 0009, AC-6, `packages/contracts/src/modules/module-registry.ts`): `catalog`, core, no toggle. Every controller here declares `@RequiresModule('catalog')` (`src/platform/modules/requires-module.spec.ts` fails the build otherwise), so the module gate never answers `MODULE_OFF` for it while the module is core.

- Row locks for stock (spec 0011 AC-18): `CatalogLocks` ([catalog-locks.service.ts](catalog-locks.service.ts)), exported by `CatalogModule`: `lockForShare(tx, variantIds)` and `lockForUpdate(tx, variantIds)` lock SKU rows in id order inside the caller's transaction and answer kind, tracking, and archived; `serialTrackedVariantIds(executor)` lists the serial tracked SKUs. Inventory calls them, so it never reads `product_variants`.

## Never touches

- Ledger tables (`movement_groups`, `stock_movements`, `movement_serials`, `stock_levels`, `reservations`, `serials`). Stock figures come from the inventory module.
- Other modules' tables.
- The SKU archive, unarchive and code change routes. They belong to [inventory/sku-lifecycle](../inventory/sku-lifecycle/).

## Decisions

- **The style list's `q` matches an active style by its active variants only** (review of spec 0012 milestone 2, nit 1): an archived size must not bring its active style into a search for that size's code or color. With `status=archived` every variant counts, since an archived style has no active one. AC-8 did not say; [search/style-list-sql.ts](search/style-list-sql.ts) holds the rule.
- **The retry helper lives in catalog, not inventory**: catalog never imports inventory (the module wall), so `catalogTransaction` reuses only the shared `isRetryable` and sets no lock timeout (no catalog write waits on hot stock rows).
- **Lock order, a follow-up for the stock ledger session (owner of inventory)**: inventory's SKU lifecycle (`lockForArchive` before `setArchived`, and the code change before `setCode`) takes the variant row before the style row, while the style writers (`addVariant` appending an option or value restamps every variant of the style) take the style first. PostgreSQL then aborts one side with a deadlock; the catalog writers and the SKU lifecycle each run again once, so the person sees no error, but locking the style first in inventory would remove the deadlock.
- **Follow-up (spec 0012 milestone 1, migration 0014 has shipped in the M1 pull request)**: `product_options_search_text_follows` fires on every update of an option; `AFTER UPDATE OF name, values, product_id` would skip role only updates. A later forward migration may narrow it.

- **Channel sync choices the spec left open (spec 0012 milestone 4)**: a non source store only resolves (no content, no option values, no link, lead ruling 2026-11-11), answering `linked` for an existing variant, while a variant or style it creates is seeded from its data but stays app owned (no `channel_linked_at`, `channel_name_language` null, an app barcode, only the option values its new variants need); swapping option values or barcodes between two variants of one product answers `option_conflict` or `barcode_conflict` on every apply (each variant's new value is still held by the other; there is no two pass apply, review minor 3), so the connector's task asks a person to clear one first; a variant another writer created in parallel in another style links that style when the product ends on it, else that style stays as it is; a variant resolved outside the target style takes content but not option values (its options belong to its own style), and only the target style is linked; a new variant of an archived style is created archived (the sync never unarchives, and a style is never archived with an active variant); a SKU or catalog variant a previous variant of the same product already took answers `invalid_sku`; a channel barcode failing the barcode pattern answers `barcode_conflict`; `unlink` keeps channel barcodes as app barcodes rather than deleting scannable codes. Conflict outcomes take precedence over `updated` (the rest of the variant still applies).

Record other non obvious decisions as ADRs in docs/adr/ and link them here.
