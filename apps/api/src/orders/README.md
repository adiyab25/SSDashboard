# Orders

The one place that writes an order: the order, its lines, and the history of every move of its two state machines (the parcel and the money). Other features never touch the order tables; they call named moves inside one order transaction.

## Owns

- Its registry row (spec 0009, AC-6, `packages/contracts/src/modules/module-registry.ts`): `orders`, core, no toggle. Every controller here declares `@RequiresModule('orders')` (`src/platform/modules/requires-module.spec.ts` fails the build otherwise), so the module gate never answers `MODULE_OFF` for it while the module is core.
- The order tables (defined in [packages/db](../../../../packages/db/src/schema/orders.ts)): `orders`, `order_lines`, `order_events` (append only), and `shipments`, all owned by `orders` in [table-ownership.ts](../../../../packages/db/src/table-ownership.ts). Only this module reads or writes them.
- `OrderWriter` ([writer/order-writer.ts](writer/order-writer.ts)), the only file that issues `INSERT` or `UPDATE` on `orders` and `order_lines` and `INSERT` on `order_events` (`orders-single-writer.spec.ts` fails otherwise). It writes figures that [writer/order-money.ts](writer/order-money.ts) computed with the contract functions (`LineAmounts`, `allocatePayments`, `codExpected`, `codDue`, `deriveOrderOutcome`) and publishes one `OrderStateChanged` per event row: `insertOrder` and `insertEvents` for a new order, `applyChange` for every later move (line cancels, allocation shares, new lines, the row, and its event rows, with `updated_at` set to `clock_timestamp()`), and `projectWriteBackState` for the projection. `applyChange` holds two rules no caller can skip: the money freeze (once `carrier_delivery_created_at` is set it refuses a change of `cod_expected_amount`, `prepaid_amount`, the totals, the shipping shares, any line's shares, a line cancel, or a new line with `OrderLocked`; only milestone 5's partial delivery split passes `freezeAllowance: 'partial_delivery_split'` to move lines under it, never a frozen column), and `outcome`, which it derives with `deriveOrderOutcome` after every change (no caller passes one). Every move first takes the row lock and checks the concurrency token with `lockOrderForChange` ([writer/locked-order.ts](writer/locked-order.ts)). `setChannelLineIds` and `setLineVariant` write a line's channel id or variant only from null, with no event and `updated_at` kept.
- `OrderTransactions.run(work)` and the `OrderTransaction` type ([order-transactions.ts](order-transactions.ts), spec 0013 AC-22): the only way to open an order unit of work; a `run` inside a `run` throws `OrderTransactionNested`. It is spec 0011's `LedgerService.transaction` (milestone 4), so an `OrderTransaction` is also a `StockTransaction` and the reservation calls inside an order write are legal: READ COMMITTED, lock waits capped at 5 seconds (the ledger's `LockTimeout` becomes `OrderLockTimeout`, 503 `BUSY`), one rerun of the whole `work` after a deadlock (`orders-stock.e2e-spec.ts` forces one and finds one order, one event set, one audit entry, one reservation set). **Because `work` can run twice it must be rerunnable**: read its inputs again inside, keep no state outside it between runs, call no provider or other connection inside it, and write every row of its unit inside it. Every orders write method takes an `OrderTransaction`, so a plain Drizzle transaction does not type check. `orderTransactionFromLedger(tx)` is the one sanctioned adapter (review N3) for a transaction the ledger itself hands to orders (the `ReservationFilled` and `ReservationShortened` handlers now, a posting's `within` callback in milestone 5); `order-transactions.adapter.spec.ts` counts the casts to `OrderTransaction` per file (exactly two, both in `order-transactions.ts`) and fails any file outside its allow list (`stock/short-lines.projection.ts` today) that names the adapter.
- `OrderIntake.createManual` ([intake/order-intake.service.ts](intake/order-intake.service.ts)): the manual, gifted, reopened, and replacement order (AC-1, AC-2, AC-23), idempotent on `clientRef` (stored as `channel_order_ref`, found under an advisory lock and the partial unique index). It takes the customer from `CustomersService.findOrCreate`, the number from `NumberingService.next` as its last step, and writes `order.created_manually`.
- The channel calls of feature 13 on `OrderIntake` (milestone 3, AC-14, AC-23, AC-25; in process, no route, every one inside the caller's `OrderTransactions.run`), built against `ChannelOrderInput`, `ChannelOrderSnapshot`, and `RederivePaymentMethodInput` in `packages/contracts/src/orders/order-api.ts`:
  - `createFromChannel(tx, input, actor)` (actor `system_job` or `import`): idempotent on the store and `channel_order_ref` (`{ orderId, created: false }` on a repeat), `OrderNumberTaken` for a second number in a store, lines priced at their own tax rate and the shipping at `shippingTaxRate` or else `sales_tax_rate` (an unmapped line keeps the channel title), a deposit stored as it arrives, the customer from the main phone and `channelCustomer` (kept only when its connection belongs to the store, `ConnectorsService.storeOfConnection`), the note and source fields, `relatedOrder`, and the first states planned by [intake/channel-first-states.ts](intake/channel-first-states.ts) (the go live state for a `system_job`, found states for an `import` from an allow list checked against the amounts by `assertFoundAmounts`, `InvalidOrderInput` otherwise). It refuses (`InvalidOrderInput`) a channel not bound to the store (`default_store_id`), a manual entry channel (`manual`, `whatsapp`, `instagram`), and on an internal store a number shaped like the store's own (`<SO prefix>-<year>-<digits>`). No audit entry.
  - `applyChannelEdit`, `rederivePaymentMethod`, `cancelFromChannel`, and `recordChannelLineIds` refuse an order whose channel is a manual entry kind (`InvalidOrderInput`), read from the channel's kind, never from `channel_order_ref` (a manual order keeps its `clientRef` there).
  - `applyChannelEdit(tx, orderId, snapshot, actor)`: diffs the snapshot with the pure [intake/channel-snapshot.ts](intake/channel-snapshot.ts) and plans it with `planEdit` (`keep_raw` main phone, `drop` second phone); answers `{ applied: false, why }` for `write_back_open` (no attention) and, with `channel_edit_not_applied`, for `carrier_delivery_exists`, `not_editable`, `changes_payment`, `overpaid`, `needs_a_line`, and `gift_must_stay_free`; an applied change writes `order.edited` (actor `system_job`, reason `channel_edit`, `after.origin = 'channel'`) and `OrderEdited` with `origin: 'channel'`.
  - `recordChannelLineIds(tx, orderId, ids, actor)` (`ChannelLineIdConflict`), `linkChannelLineVariant(tx, orderId, channelLineId, variantId)` (`LineAlreadyMapped`, `shipped_with_unmapped_lines` past `packed`), `rederivePaymentMethod(tx, orderId, input, actor)` (`PaymentMethodLocked`, one cash event of reason `payment_method_rederived`, `order.payment_method_rederived`), and `cancelFromChannel(tx, orderId, reasonCode, actor)` (`{ applied: false, why: 'already_final' | 'after_pickup' }`, `channel_cancel_after_pickup`).
- `OrderEditing.edit` ([editing/order-editing.service.ts](editing/order-editing.service.ts), AC-2, AC-8 to AC-11): the concurrency token (409 `ORDER_STALE`), the freeze (409 `ORDER_LOCKED`), `EDIT_IN_SHOPIFY` while `ConnectorsService.writeBackAvailable(orderId, 'shopify.order_edit')` is false, `GIFT_NOT_ALLOWED`, the customer relink on a new main phone, `packed` back to `confirmed`, one `order.edited` entry, and `OrderEdited`. The change itself is planned by the pure [editing/edit-plan.ts](editing/edit-plan.ts) (`planEdit`, `editAuditDiff`), which knows no person or route, so milestone 3's `applyChannelEdit` reuses it.
- `OrderTransitions` ([transitions/order-transitions.service.ts](transitions/order-transitions.service.ts), AC-7, AC-8, AC-15): `confirm`, `cancel` (until pickup, the duplicate link with both orders locked in ascending id, `cod_due_amount` 0, the automatic `unpaid` to `nothing_to_collect` by `system_job`, the `unpack_cancelled_order` and `terminate_carrier_delivery` attentions, `CANCEL_IN_SHOPIFY` for a person, `OrderCancelled`), `markPacked` (409 `WRITE_BACK_OPEN` while `ConnectorsService.openCommandsFor` answers any command, whatever `write_back_state` says), `unpack` (only from `packed`), and a minimal `recordCarrierDelivery` (sets the freeze once; milestone 3 adds its callers).
- `WriteBackProjection` ([projections/write-back.projection.ts](projections/write-back.projection.ts), AC-12): on the four `OutboundCommand*` events of an order it recomputes `write_back_state` (`failed`, else `waiting`, else `none`) from `openCommandsFor` in the publisher's transaction, under the order row lock (`projectWriteBackState` locks before the read), so two command changes in parallel serialize and the later one reads the earlier one's commit. It is the one writer path that takes a plain transaction (spec 0013 Key invariants).
- `OrderStock` ([stock/order-stock.ts](stock/order-stock.ts), AC-13, AC-26): the seam to the stock ledger, called inside the order transaction by both creations (`afterCreate`, never for an import found past `packed` or cancelled), edit (`afterEdit`: release the cancelled lines, then reserve the added ones, the SKU rows locked first in ascending id), cancel (`afterCancel`: `releaseSource` and every `short_quantity` to 0), confirm and pack (`topUp`: `reserveLines` again; a pack with a line still short throws `LineShort`, 409 `LINE_SHORT`, Q-16.5), and `linkChannelLineVariant` (`afterLink`). Every call is spec 0011's `reserveLines` (`shortage: 'reserve_available'`), `releaseLines`, or `releaseSource` with `sourceType: 'order'` at `OnlineStockService.onlineLocation()`, and `short_quantity` is written from each answer's `unfilled` through `OrderWriter.setShortQuantities`. It registers the `orders.open_orders_held` check with `OnlineStockGate` at module start and serves `holdOpenOrdersAt` for the route below.
- `ShortLinesProjection` ([stock/short-lines.projection.ts](stock/short-lines.projection.ts), AC-13): on the ledger's `ReservationFilled` (to `stillUnfilled`) and `ReservationShortened` (plus `quantity`, and the `reservation_shortened` attention for support) for `sourceType: 'order'`, it writes one line's `short_quantity` in the ledger's own transaction through `OrderWriter.projectShortQuantity`, which takes no order row lock and writes only an open line of an order in `new`, `confirmed`, or `packed`.
- `OrderStockController` ([stock/order-stock.controller.ts](stock/order-stock.controller.ts), AC-26): `POST /api/orders/hold-open-orders` (`{ locationId }`, `catalog.manage`, `@Audience('staff')`, `@RequiresModule('orders')`), answering `{ linesHeld, linesShort, linesLeft }` (`HoldOpenOrdersResult`), 404 `LOCATION_NOT_FOUND`, 503 `BUSY`; one `OrderTransactions.run` per batch of at most 200 lines, oldest order first.
- The public events ([orders.events.ts](orders.events.ts)): `OrderPlaced`, `OrderEdited`, `OrderCancelled`, `OrderStateChanged`, `OrderAttentionRaised` (ids and codes only), published through the platform `DomainEvents`.
- `OrderQueries` ([reading/order-query.service.ts](reading/order-query.service.ts)): the list and search (keyset on `placed_at`, `id`), the order page, the form options, and the reads other modules call (`summaryOf`, `forCustomers`, `countsForCustomers`, `writeBackViewOf`), with the cost serializer ([reading/order-cost.ts](reading/order-cost.ts)).
- `OrdersController` ([reading/orders.controller.ts](reading/orders.controller.ts)): `GET /api/orders`, `POST /api/orders/search`, `GET /api/orders/options`, `GET /api/orders/filter-options`, `GET /api/orders/:id`, `POST /api/orders`, `POST /api/orders/gifted`, all `@Audience('staff')`. `options` is declared before `:id`.
- `OrderMovesController` ([moves/order-moves.controller.ts](moves/order-moves.controller.ts)): `POST /api/orders/:id/edits`, `/confirm`, `/cancel` (`orders.confirm`), `/pack`, `/unpack` (`fulfillment.work`), all `@Audience('staff')`, each taking `expectedUpdatedAt`, opening one `OrderTransactions.run`, and answering the order page (with its open write back commands) through the cost serializer. A reason outside its list answers 422 `REASON_INVALID` (`OrderBodyPipe`). Both controllers declare `@RequiresModule('orders')`.

## Never touches

- Other modules' tables. Stores and channels come from `ChannelsService`, customers from `CustomersService`, SKU codes from `CatalogService`, actor names from the staff directory, settings from `SettingsService`, and outbound commands from `ConnectorsService`.
- The stock ledger's tables. Reservations go through `LedgerService` (`transaction`, `reserveLines`, `releaseLines`, `releaseSource`, `reservationsFor`), the online location and the gate through `OnlineStockService` and `OnlineStockGate`, SKU facts through `CatalogService.getSkus` and SKU row locks through `CatalogLocks`; the shipment posting arrives in milestone 5.
- Personal data in logs, errors, domain events, and audit columns (Law 151): ship to fields, the customer note, and raw phones are redacted by the shared list, the module logs by order id only, and an error never echoes a phone.
- A state change outside the transition tables of `packages/contracts/src/orders/order-states.ts`, and `orders.outcome` set by hand: it is written only from `deriveOrderOutcome`.

The unit suite needs no database. The suites that create orders put their SKUs on the shelf of an online warehouse first (`test/order-stock.ts`, `stockedOnline`), because an order reserves at creation and a pack refuses a short line; `orders-stock.e2e-spec.ts` covers the reservations, short lines, the fill and shorten events, the online gate check with `hold-open-orders`, and the forced deadlock rerun; `orders-stock-online.e2e-spec.ts` the online flag: holds at the old location staying there, the move A to B, a line moved off a location that is no longer online, an order of 201 lines across two batches, the order that waits for a flag move, and the cost of the gate and the hold with 200 open orders. ## Decisions

- **Migrations 0009 and 0010**: the columns, checks, and indexes are one generated migration; the `goodwill_for` enum value is its own generated migration (`ALTER TYPE ... ADD VALUE` alone in its file), not a hand written custom one, because Drizzle generates it and a second `generate` must report no changes. Nothing in 0009 uses the new value, so the single migrate transaction is safe.
- **Actor with a hat**: a person actor carries the hat they act under (`access.actingHat('orders.confirm')`), because the spec 0010 audit actor needs it; the spec's `{ type: 'person', userId }` is the same shape plus `hat`.
- **A second phone that does not parse** is refused on a person's create and edit (422 `INVALID_PHONE_ALT`), unlike the main phone, which is kept as typed with `phone_unparseable`: dropping it would lose the courier's second number silently. **From a channel** (milestone 3, review N4) the customer already placed the order, so nothing is refused: on creation the second phone is stored as null and `phone_unparseable` is raised with source `ship_to_phone_alt`; on a channel edit a valid stored second phone is kept (security L9) and the attention raised, and an empty one stays empty with no new attention. Its text is kept nowhere: `contact_phone_raw` holds only a main phone that does not parse (spec 0013 Value sourcing). A channel main phone that stops parsing keeps its text in `contact_phone_raw` and sets `customer_id` to null.
- **A channel snapshot** (milestone 3): a ship to field, the customer note, or the area codes sent as null keep the stored value; the payment, type, source, and discount code are never diffed (`rederivePaymentMethod` corrects the payment); a line the channel no longer holds is cancelled with `edit_removal` (one of spec 0002's line cancel reasons, like a replaced line; `channel_edit` is the audit reason only), a line with no channel id included once the matching rule found it no partner; a variant never goes back to unmapped (a replace keeps the stored variant when the snapshot line is unmapped), and an unmapped line whose snapshot names a variant is left to `linkChannelLineVariant`. A frozen or no longer editable order refuses only a snapshot that would change something, so an echo raises no attention. A channel edit of a `packed` order writes `packed` to `confirmed` as `system_job` (the transition row now lists that actor).
- **First states of a channel order** (security M1): an `import` names its run by a uuid, recorded on both first events (`order_events.source_type` `import_run`, `source_id` the run id; no migration, the columns are free text and uuid). The found pair must be on the allow list: `new`, `confirmed`, `packed` only with a first cash state (`unpaid`, `prepaid`, `nothing_to_collect`); `cancelled` only with `nothing_to_collect`, as a live cancel leaves it (security R3); `collected_by_carrier`, `remitted`, `reconciled` only once a carrier fact touched the order and only with its `carrierDeliveryCreatedAt`. The cash must also fit the amounts: `unpaid` needs a COD expected above 0, `prepaid` a prepayment with nothing expected on delivery, `nothing_to_collect` nothing due (`cod_due_amount` 0, which a cancelled, refused, or returned order has even with a COD expected, so the rule reads the amount due rather than the expected), `collected_by_carrier` and `remitted` an amount due, `reconciled` an amount due or a full prepayment. A found order past `packed` takes the matching line states (`delivered` for delivered and exchanged, `returned_to_origin` for refused and returned, `lost`), sets the freeze at the given time or else its placed time, and a found collected, remitted, or reconciled cash records the amount due as collected (and remitted); a found `partially_delivered` is refused, because its line split is not known. A `cancelled` or `refused` import names its reason (the order table requires it).
- **Retired SKUs** (security L6): a channel order keeps a line of an archived variant (the sale happened in Shopify); `linkChannelLineVariant` refuses one (`VariantUnknown`), because a new mapping names a SKU still sold.
- **A media buyer id from a channel** is stored as null (review minor 6): it would go into a foreign key unchecked, and the staff directory can only be read outside the order transaction.
- **`rederivePaymentMethod` outside the first states**: besides the spec's guards (no carrier delivery, nothing collected), it refuses with `PaymentMethodLocked` an order outside `new`, `confirmed`, and `packed` or a cash past `unpaid`, `prepaid`, and `nothing_to_collect`, because a cancelled order's `nothing_to_collect` must not move back to `unpaid`.
- **Channel kinds of a manual order**: `manual`, `whatsapp`, and `instagram`, active only; any other channel is 422 `CHANNEL_NOT_ALLOWED`. A manual order's campaign source is `whatsapp_thread` on a WhatsApp channel and `manual` otherwise; a reopened order copies the original's.
- **Prepayment shape**: `cod` carries no prepayment and any other method is a full prepayment (the body schema enforces the pairing); the amount is checked against the computed total (422 `PARTIAL_PREPAYMENT_NOT_SUPPORTED`).
- **A sale with a total of 0 is refused** (`INVALID_BODY`): a sale needs an amount to collect or a prepayment, and a gift goes through `POST /api/orders/gifted`. A sale line whose net is 0 is refused (`LINE_FULLY_DISCOUNTED`) unless the person also holds `orders.gift`.
- **Reopening**: only for the customer of the original (canonical on both sides, an order with no customer on either side is refused) and once per original, whatever became of the reopened order, cancelled included (the owner's ruling in milestone 2; 409 `ALREADY_REOPENED`; the original's row is locked, `orders_related_order_idx` serves the check). Replacement and goodwill links are not tied to the customer.
- **`sales_tax_rate`** is a registered core setting (default `14.00`, manager, reason required), read with `SettingsService.get(key, tx)` inside the order transaction.
- **Counts for the returner signal**: a refusal counts by the operating day of its `refused` event, a returned line by the operating day the order was placed.
- **Edits refuse what the form cannot mean**: an edit of an order outside `new`, `confirmed`, and `packed` answers 409 `ORDER_LOCKED` like the freeze; a new main phone that does not parse is refused on a person's edit (422 `INVALID_PHONE`) rather than kept as typed, because the edit exists to fix it, while `planEdit`'s `unparseablePhone: 'keep_raw'` (milestone 3's channel edit) keeps the text in `contact_phone_raw` and reports `phoneUnparseable` for the `phone_unparseable` attention, as on creation; a sale line with nothing to pay is refused (`LINE_FULLY_DISCOUNTED`) unless the person holds `orders.gift`, as on creation; a line that is not an open line of the order is 422 `INVALID_BODY`; an edit that changes nothing writes nothing (no audit entry, no event, `updated_at` kept).
- **The write back projection leaves `updated_at` alone**: a command settling changes `write_back_state` only, so it never makes a person's open edit stale; every person's move sets `updated_at`.
- **`OrderEdited` names its audit entry by correlation id** (`auditCorrelationId`), because `AuditService.record` does not return the entry id the spec's payload names.
- **Cancel shape**: a target with a reason other than `duplicate` is 422 `INVALID_BODY`; a `duplicate` with no target, an unknown one, or the order itself is 422 `DUPLICATE_TARGET_REQUIRED`; an order that already links to another (a reopened one) cannot take a `duplicate_of` link, and neither a cancelled target nor a target that is itself `duplicate_of` this order is accepted (422 `INVALID_BODY` each, so duplicates never form a cycle). The two orders are locked in ascending id, compared lower cased. A cancel keeps `prepaid` cash as it is (the refund is feature 18's).
- **`recordCarrierDelivery` arrived in milestone 2** in its minimal form (the freeze, once, and `delivery_created_before_edit_synced`), because the edit lock and the cancel attention read it; the e2e suites call it directly until features 13 and 19 do.
- **Stock holds (milestone 4)**: only a line whose SKU can hold stock is reserved (stocked, not archived, not lot tracked, because an order line names no lot); any other line, like an unmapped one, is neither reserved nor short and never blocks a pack. With no online location nothing new is reserved: a line holding nothing reads short by its quantity, a held line keeps its stored short (it still copies `unfilled_quantity`), and a pack answers `LINE_SHORT`. Reservations at the old location stay there (the lead's ruling of 2026-11-12, agreeing with spec 0011 AC-19): a top up leaves a line held at a location that is not online where it is (it ships from where its pieces are); the gate check counts a line held at the candidate or at the current online location as held; `hold-open-orders` reserves the lines holding nothing, moves a line of a `new` or `confirmed` order held at a location that is not online (releasing there cannot oversell), and never releases a hold at the online location; a held line of a `packed` order counts as held wherever it is and never moves, because its pieces are in a box (re-review N1). Every stock call that can reserve (create, link, every edit, the confirm and pack top ups, each hold batch) takes the online flag lock shared first (`OnlineStockService.shareOnlineFlag`; `makeOnline` and `stop` take it exclusive first), so an order never reserves at a location after the flag moved away from it, and such calls wait while a flag move runs; an edit takes it even when it only removes lines, because the same unit may reserve next (the Shopify inbox applies a removal, then creates an exchange replacement), and only a cancel takes none (re-review N5, final delta check). Two parallel flag moves still give one success and one 409 `ONLINE_GATE_STALE` (re-review N3). What is reservable is decided on the SKU rows locked `FOR SHARE` (`CatalogLocks`), and a ledger refusal that still reaches an orders route answers with the ledger's own codes (`ledgerHttpError`). The short quantities of a unit are written after its last `reserveLines`; the pair locks are still taken per ledger call, so two edits that swap the same two sizes in opposite directions can deadlock once, which the runner's rerun breaks. A refused pack rolls back its own top up with it. `hold-open-orders` refuses a location that is missing, archived, or could never feed online stock (the online stock service's candidate read) with 404 `LOCATION_NOT_FOUND`, locks the batch's orders in ascending id, keeps one order's lines in one batch when they fit, and answers `linesLeft` as the lines still unheld there after the call (the gate check's count). The `reservation_shortened` attention carries the event's `cause` as its source type and the reservation as its source id. The gate check's action points at `POST /api/orders/hold-open-orders`, which needs `{ locationId }` in its body.
- **Follow-up (re-review N2)**: a line held short at a location that no longer feeds online stock is never re-homed by a top up (it keeps its hold where it is, by the ruling above), so it stays short until stock arrives there or `hold-open-orders` moves it at the next flag move. Re-homing short lines of `new` and `confirmed` orders to the online location is left for a later task.
- **Follow-up (lead to decide)**: `hold-open-orders` still reserves a line of a `packed` order that holds nothing anywhere at the candidate (AC-26 as written); whether a packed order's unheld line should be left alone is the lead's call.
