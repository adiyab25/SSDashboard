# apps/api/src/identity

## Overview

The identity module: sign in for staff and partner users alike (Better Auth wired into NestJS, a global audience aware session guard, lockout and rate limits kept in PostgreSQL, two factor, the break glass commands) in `sign-in/`, which audiences a person may use and how their sessions follow hat changes in `sessions/`, and admin managed staff accounts in `staff/`, wired by one `IdentityModule` (`identity.module.ts`). Governed by [spec 0005](../../../../docs/specs/0005-staff-sign-in/index.md). The run book for operators is [docs/runbooks/staff-sign-in.md](../../../../docs/runbooks/staff-sign-in.md). What it owns and never touches: [README.md](README.md).

## Key files

| File | Owns |
|---|---|
| `identity.module.ts` | The one module: controllers, providers and the three global guards in their order, `SessionGuard`, then platform's `AudienceGuard`, then platform's `PermissionGuard` (spec 0008 guard order). It has no Nest `exports`; the public surface is the import wall's list in `src/module-boundary.spec.ts` |
| `sign-in/auth.factory.ts`, `sign-in/mount-auth.ts` | Builds Better Auth and mounts it at `/api/auth`; the cookie contract (no `Domain`, `Path` from `STAFF_BASE_PATH`) and the portal host 404 |
| `sign-in/portal-host.ts` | Whether a request carries the `PORTAL_ORIGIN` host name (`X-Forwarded-Host` or `Host`, any port, trailing dot ignored) |
| `sign-in/session.guard.ts`, `sign-in/public.decorator.ts` | The global guard, audience aware (spec 0005, AC-29): `staff` and `partner` routes need a live session whose person may use that audience (`request.staff` or `request.partner`), else 403 `WRONG_AUDIENCE`; `public` routes pass without the cookie; `portal` and `hook` routes are never read at all |
| `sessions/session-audiences.ts` | The `SessionAudiences` port (`audiencesFor(userId)`, `staffCondition()`), its token `SESSION_AUDIENCES`, the hat based `HatSessionAudiences` bound in `identity.module.ts` and built by `create-admin`, the pure `audiencesOfHats(hats)` both judge by, `holdsHat(hat)` (a SQL condition on `users`), and `homeOf` (`home` on `GET /api/me`) |
| `access/access-loader.ts` | `AccessLoader.load(userId)`: the person's hats, extra grants and partner account in one read, as platform's `Access`; the session guard calls it on every `staff` and `partner` request and sets `request.access` |
| `sessions/revoke-sessions.ts` | `revokeSessions(userId, tx)` (all of a person's sessions, inside the caller's transaction; the one writer of that delete, used by the staff service and the break glass reset) and `hatChangeEndsSessions(before, after)`, the AC-33 (b) rule |
| `sessions/hat-change-log.ts` | `hatChangeLogLine`, the AC-33 (e) log line of a hat change (hats added and removed, and the optional `before`, `after` and `reason` of spec 0008 AC-13), written field by field by `AuthAudit.hatsChanged` |
| `sessions/create-admin-audiences.spec.ts` | Fails while `src/create-admin.ts` builds a different `SessionAudiences` class from the one `identity.module.ts` binds |
| `../platform/audience/` | `@Audience(...)` and the deny by default `AudienceGuard`; `audience.spec.ts` fails the build for a controller without exactly one |
| `../platform/access/` | `Access`, `@Permission(...)`, `@AnyHat()`, `@CurrentAccess()` and `PermissionGuard` (spec 0008); `permission.spec.ts` fails the build for a staff or partner handler without exactly one valid declaration |
| `sign-in/current-staff.ts` | Reads the signed in user from the request (`AuthenticatedRequest` with `CurrentStaff` on staff routes, `PartnerRequest` with `CurrentPartner` on partner routes). Neither carries a role, hats or permissions: what a person may do is only `request.access`. Ledger routes take the poster from here |
| `sign-in/session-policy.ts`, `sign-in/sign-in-lockout.ts` | 12 hour sliding session with a 7 day cap, five strikes lockout, and the `sign_in_slots` that cap how many passwords or codes are checked at once (`takeSlot`, `giveBack`) |
| `sign-in/auth-hooks.ts` | Origin check, forced password change, lockout counting; the before hook takes a sign in slot as its last step and the after hook gives it back on every ending |
| `sign-in/first-admin.ts`, `sign-in/reset-admin.ts` | The logic behind `create-admin` (the first person wears `manager` with `cost.view`, refused while an active manager exists) and its reset modes (refused for a person without `manager`) |
| `sign-in/auth-cleanup.job.ts` | Nightly worker job that deletes expired sessions, tokens, counters and sign in slots older than 60 seconds |
| `sign-in/mail-recipients.ts` | `MailRecipients`: the recipient and token row the mail worker reads at send time |
| `sign-in/locks.ts` | The advisory locks: `ADMIN_RULE_LOCK` (the last admin rule) and `SIGN_IN_SLOT_LOCK` (slots for one email handed out one at a time, only ever tried) |
| `staff/staff.service.ts`, `staff/staff.controller.ts` | `/api/staff` (`people.manage`): invite, edit, disable, reset, revoke. Until spec 0008 milestone 2 the `role` field is a preset turned into hats with the AC-16 mapping (`replaceAccess`, the transitional writer of the hat tables) |
| `staff/staff-directory.ts` | `StaffDirectory`: read only names for other modules |

## Commands

```bash
docker compose --env-file .env run --rm api node dist/create-admin.js --email <email> --name <name>
docker compose --env-file .env run --rm api node dist/create-admin.js --reset-password --email <email>
docker compose --env-file .env run --rm api node dist/create-admin.js --reset-two-factor --email <email>   # add --reset-password to do both in one transaction
```

`create-admin` prints a live temporary password to stdout. Never capture or log that output.

## Conventions

- The public surface is `IDENTITY_PUBLIC_FILES` in `src/module-boundary.spec.ts`, and the import wall there fails any other import of a file inside `identity/` from another module (spec 0005, AC-27): `identity.module.ts` (the app root), `sign-in/current-staff.ts` (the `AuthenticatedRequest` type), `sign-in/public.decorator.ts` (`@Public()`), `staff/staff-directory.ts` (`StaffDirectoryModule`) and `sign-in/mail-recipients.ts` (`MailRecipientsModule`). The app entry points (`app.module.ts`, `app.setup.ts`, `create-admin.ts`, `worker.module.ts`, `main.ts`, `worker.ts`, `migrate.ts`) and `apps/api/test` sit outside the wall. `IdentityModule` has no Nest `exports`: a consumer imports `StaffDirectoryModule` or `MailRecipientsModule` directly. Never make the Better Auth instance, `SignInLockout` or `AuthAudit` public; the auth tables are written only from here (the table wall in the same spec fails on any other module naming them).
- `StaffDirectory` and `MailRecipients` sit in their own small modules because the worker loads them: they must never depend on Better Auth, the guards or the mail producer. `MailRecipients.token()` returns a live reset or invite token: never log what it returns.
- Every controller needs exactly one `@Audience(...)` on the class (`src/platform/audience/`); a spec fails the build without it, with two, on a handler, or with a path prefix that does not match (`partner`, `portal`, `hooks`). Open routes use `@Audience('public')` plus a class level `@Public()` (the spec keeps them equal). A live session that does not fit the route's audience gets 403 `WRONG_AUDIENCE`, from `SessionGuard` for staff and partner routes and from `AudienceGuard` for the rest.
- `SessionGuard` serves `staff`, `partner` and `public` routes (spec 0005, AC-29). On `portal` and `hook` routes it returns at once: no cookie, no Origin check, no session lookup, so a staff cookie can never act there; their own proof (a portal sealed token, a hook signature) comes with their features, and until then `AudienceGuard` denies them. The Origin check, the disabled check, the 7 day cap and the forced password change (`GET /api/me` or `GET /api/partner/me` only) apply to staff and partner alike. A controller with no audience is held to the staff rule. Never use `@Public()` to get around any of it.
- Platform's `AudienceGuard` (`src/platform/audience/audience.guard.ts`) reads `request.staff` and `request.partner`, so a partner session reaches a partner handler end to end (`sign-in/session-guard-routes.spec.ts` proves it, with the guards built by hand in the module's order). It is the only block on `portal` and `hook` routes until their own proof exists.
- Which audiences a person may use comes only from the `SessionAudiences` port, asked on every request; `HatSessionAudiences` answers from the person's hat rows (no hat: no audience, and the guard ends the sessions). What they may do is the `Access` that `AccessLoader` reads on the same request; never cache either, and never read `users.role` (spec 0008). `/api/staff`, the last admin rule and `create-admin` (`first-admin.ts`, `reset-admin.ts`) put `staffCondition()` in every query on `users`, so a partner user is never listed, found (404), counted as a manager, or made one (AC-28). A new staff query on `users` needs the same condition, and a staff write runs in the same transaction as the `find(tx, id, true)` that checked it. `createFirstAdmin` and `breakGlassReset` take the port as a required argument.
- Delete a person's sessions only through `revokeSessions(userId, tx)` (`sessions/revoke-sessions.ts`), inside the transaction of the change; never repeat the `DELETE FROM sessions` statement.
- A route that posts to the ledger validates with `PostingRequest` or `ReverseRequest` from `@ssdashboard/contracts`, never `PostingInput`, and sets `postedBy` from `sign-in/current-staff.ts`. `src/inventory/controller-contracts.spec.ts` fails if a controller imports the service schemas.
- Sign in failures give identical answers for unknown emails, wrong passwords and locked accounts, so the api never reveals which accounts exist.
- Take `ADMIN_RULE_LOCK` (`sign-in/locks.ts`) before any change that could remove the last active admin: an active person wearing `manager` (`holdsHat('manager')`, spec 0008 AC-14).
- A password, second factor code or current password answer is checked only with a slot in `sign_in_slots` (spec 0005, AC-3). `SignInLockout.takeSlot` hands slots out under `pg_try_advisory_xact_lock(SIGN_IN_SLOT_LOCK, hashtext(email_key))`, one short transaction per try; while the email's turn is taken it pauses about 20 ms with no connection held and tries again, and after `SLOT_WAIT_MS` (2 s) the attempt is turned away uncounted. Never wait on that lock inside a transaction (`pg_advisory_xact_lock`, `lock_timeout`): every waiter would hold a pooled connection. Taking the slot must stay the last step of the before hook: once a slot is held nothing may throw before the after hook, which gives it back on every ending (a counted failure in the same transaction as the upsert, tried once more on 40P01 or 40001 and never given back uncounted instead). A new route that checks a password or code takes a slot the same way. A slot older than 60 seconds (`clock_timestamp()`) holds no place; the app role cannot `UPDATE` a slot.
- Sign in takes a slot only for a body Better Auth goes on to check (`wellFormedSignIn` in `sign-in/auth-hooks.ts`: its body schema, `z.email()`, at most `PASSWORD_MAX_LENGTH`; Better Auth's sign in has no minimum). Anything else is Better Auth's own 400, the same whether the email is locked or not. Keep that schema in step with Better Auth's `/sign-in/email` on every upgrade.
- `sign_in_attempts` rows of one email are locked all addresses row (`*`) first, then by address in byte order: `addFailure` upserts `*` first and `reset` locks with `ORDER BY` before it deletes. Keep that order in any new writer.
- A turn away is recorded: on sign in, and on a code for a pending sign in, as `SignInFailed` reason `locked`; on the current password routes and a first code while turning two factor on, as an `AuthAudit.turnedAway` log line (route, ids, address, user agent, `locked`; no event, since AC-23 names none).
- Raw SQL in this module never names `tenant_id` except as an `ON CONFLICT` target; the column default fills it (spec 0005, AC-32; `test/auth-tenant.e2e-spec.ts`).
- One staff origin (`PUBLIC_URL` today, `STAFF_ORIGIN` after spec 0007's rename) is the Better Auth base URL, the only trusted origin, the Origin check, the `Secure` flag and the base of email links. Read it only through `staffOrigin(env)` and `staffBase(env)` (origin plus `STAFF_BASE_PATH`) in `src/config/env.ts`; email links are `staffBase` plus the route (`src/mail/mail.worker.ts`). Never add `PORTAL_ORIGIN` to the trusted origins.
- Cron settings (`AUTH_CLEANUP_CRON`, `LEDGER_RECONCILE_CRON`), `STAFF_BASE_PATH` (non empty segments that do not start with a dot) and `PORTAL_ORIGIN` (a different host name from `PUBLIC_URL`, not just another port) are checked at startup in `src/config/env.ts`; a bad value stops the process.
- Changing `STAFF_BASE_PATH` on a live install leaves an old cookie on the wider path that shadows the new one: every session must be revoked (`docs/runbooks/staff-sign-in.md`, section 9.3).

### What spec 0008 must meet (hats, spec 0005 AC-29 and AC-33)

Spec 0005 milestone 3 built the seams; the hat model plugs into them without changing what they promise. `test/session-audiences.e2e-spec.ts` now runs on real hat rows with the real `HatSessionAudiences` (wrapped only to count its calls). Spec 0008 milestone 1 met items 1, 2, 5 (for `create-admin` and `/api/staff`) and 10; items 3, 4, 6 come with milestone 2's `HatService`, items 7 and 8 with milestone 3, and item 9 is still open.

1. **The port and its token.** Implement `SessionAudiences` (`sessions/session-audiences.ts`) from the hats and bind it to `SESSION_AUDIENCES` in `identity.module.ts` in place of `StaffOnlySessionAudiences`. `audiencesFor(userId)` answers `partner` for the partner hat and `staff` for any other hat, and an empty set for no hat (the guard then deletes the person's sessions and answers 401 `SESSION_EXPIRED`). `staffCondition()` is the same answer as a SQL condition on `users` (no partner hat, at least one hat). `create-admin` is a plain command with no Nest container: `src/create-admin.ts` must build the same class and pass it to `createFirstAdmin` and `breakGlassReset`, which take it as a required argument; `sessions/create-admin-audiences.spec.ts` fails until it does. `home` comes from `homeOf` (`partner` for the partner hat, else `backoffice`) on both `GET /api/me` and `GET /api/partner/me`.
2. **Never cache audiences or hats in the session.** Not in the session row, the cookie, Better Auth's cookie cache (it stays off) or process memory: the guard reads them from the database on every request, so a grant or a removal acts on the next request with the same cookie (AC-33 a). The partner account id on `request.partner` comes from the person's row, never from a header, path or body.
3. **The revoke call inside the hat transaction.** The hat service judges every change with `hatChangeEndsSessions(before, after)` (`sessions/revoke-sessions.ts`) and, when it says so, calls `revokeSessions(userId, tx)` with its own open transaction, before it commits (no hat left, a move between the staff and partner audiences, another partner account; AC-33 b and c). Never call it after the commit or on another connection. Spec 0008 may end sessions in more cases, never in fewer.
4. **`HatsChanged` and its log line.** After the commit the hat service writes `AuthAudit.hatsChanged(hatChangeLogLine(context, beforeHats, afterHats, { before, after, reason }))` (ids, address, user agent, time, hats added and removed, and the `{ hats, costView, partnerAccountId }` holdings and reason of spec 0008 AC-13; never an email, name or phone) and emits spec 0008's `HatsChanged` event with the same `before`, `after` and `reason`. Pass the holdings on every change, so a cost only change is logged too. A listener that throws must never fail the change.
5. **`LAST_ADMIN` under `ADMIN_RULE_LOCK`.** Removing the hat that grants user administration from the last active holder answers 409 `LAST_ADMIN`, checked under `pg_advisory_xact_lock(ADMIN_RULE_LOCK)` (`sign-in/locks.ts`) in the same transaction as the change, as the staff service and `create-admin` do today. Identity keeps the lock and the rule; only the hat that counts changes. A partner user is never counted and never holds it.
6. **A person cannot change their own hats** (AC-33 f).
7. **Reshape `CurrentPartner`** (`sign-in/current-staff.ts`): add `partnerAccountId` next to `userId`, read by the guard from the person's hat row (spec 0008 AC-9).
8. **Mark the who-am-I handlers with handler metadata** when `GET /api/partner/me` lands: the forced password change exemption in `sign-in/session.guard.ts` matches the path (`WHO_AM_I`) today, so a partner `@Get(':id')` registered before that controller could let a temporary password through (security review L3).
9. **Decide the Better Auth side of "no hat".** Better Auth routes (`/api/auth/*`) skip `SessionGuard`, so a person with no hat can still sign in and use them on their own account until their next guarded request. If AC-10's "cannot sign in" is literal, the before hook in `sign-in/auth-hooks.ts` must also ask `SessionAudiences`.
10. **Consider one pure `audiencesOfHats(hats)`** shared by the `SessionAudiences` implementation and `HatService`, so the guard's answer and the hat change rule (`hatChangeEndsSessions`) can never drift.

## Gotchas

- Better Auth encrypts two factor secrets and backup codes with `BETTER_AUTH_SECRET`. Changing that secret makes every enrolled authenticator unusable.
- The `X-Forwarded-For` header is trusted only because `caddy` is the one service that publishes ports in `deploy/compose.yaml`. `test/compose-ports.spec.ts` guards that.
- Better Auth skips the after hooks when a route ends with an error that is not an `APIError`, so such a request holds its slot until it is 60 seconds old.
- Better Auth keeps pending two factor challenges as `verifications` rows with an identifier starting `2fa-`. Any reset that must end a half finished sign in has to delete them too.
- Cookie `Path` comes from `advanced.defaultCookieAttributes.path`, which Better Auth 1.7.15 merges over its own `path: "/"` for every cookie it creates, the clearing on sign out included (`dist/cookies/index.mjs`). A per cookie `advanced.cookies.<name>.attributes` would override it, so never set one. `test/staff-cookie.e2e-spec.ts` proves the path and the missing `Domain`.
- The Caddyfile does not set `X-Forwarded-Host` explicitly; confirm what Caddy's `reverse_proxy` sends when feature 26 adds the portal site. Today `deploy/Caddyfile` serves one site, so there is no portal host yet. The portal check reads both `X-Forwarded-Host` and `Host`, compares host names (port and trailing dot ignored, as cookies do), and only refuses.
