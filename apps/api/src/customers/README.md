# Customers by phone

One customer per normalized Egyptian phone number, however the number was typed: the one door that orders, Shopify, imports, and the confirmation queue link a customer through, plus search, the customer profile, and her timeline.

## Owns

- Its registry row (spec 0009, AC-6, `packages/contracts/src/modules/module-registry.ts`): `customers`, core, no toggle. Every controller here declares `@RequiresModule('customers')` (`src/platform/modules/requires-module.spec.ts` fails the build otherwise), so the module gate never answers `MODULE_OFF` for it while the module is core.
- The customer tables (defined in [packages/db](../../../../packages/db/src/schema/customers.ts)): `customers`, `customer_phones`, `customer_external_ids`, `customer_merges`, and `customer_merge_suggestions`, all owned by `customers` in [table-ownership.ts](../../../../packages/db/src/table-ownership.ts). Only this module reads or writes them.
- `CustomersService` ([customers.service.ts](customers.service.ts)), the one exported service. It holds:
  - `findOrCreate(tx, { phone, channelCustomer, name, seenAt })`: the six rules of spec 0014 AC-1 ([find-or-create/find-or-create.ts](find-or-create/find-or-create.ts)). It takes the phone lock, then the channel id lock, so parallel calls create one customer; it opens at most one merge suggestion per pair.
  - `findByPhone`, `canonicalOf`, `idsOf`, `briefs`: reads that resolve a merged customer to its survivor through one hop of `merged_into_id`.
  - `lockCustomers(tx, canonicalIds)`: the `customer` advisory locks over whole id sets ([customer-locks.ts](customer-locks.ts)), for credit and for merges.
  - `addPhone(tx, customerId, phone, actor, { reasonCode?, correlationId? })` ([phones/add-phone.ts](phones/add-phone.ts), milestone 2): under the phone lock, `added` (not primary, on the canonical customer), `already_held`, or `held_by_other` with the other canonical id and one `second_phone_conflict` suggestion; a phone is never moved. A person's `added` writes `customer.phone_added`, under the caller's `correlationId` when given (so it joins the caller's business action), else a new one; a system job or import writes no entry.
- Merge and undo ([merges/](merges/), milestone 2, not exported: no other module merges): `CustomerMerges` (`merge`, `undo`, and the `mergeIn` and `undoIn` that take the caller's transaction) by pointer only, under `lockCustomers`, writing `customer.merged` and `customer.unmerged` (one entry per changed record under one correlation id); `MergeSuggestions` (the open list and dismiss, `customer.merge_suggestion_dismissed`); `CustomerMergeUndoHandler`, the audit undo handler `customers.merge_undo` that `CustomersModule.onModuleInit` registers, so the audit screen's undo of a `customer.merged` entry runs the same `undoIn` and records `customer.merged_undone`.
- The merge routes ([merges/customer-merges.controller.ts](merges/customer-merges.controller.ts)), all `@Audience('staff')`: `POST /api/customers/merges` and `POST /api/customers/merges/:id/undo` (`customers.merge`), `GET /api/customers/merge-suggestions` (`customers.view`), and `POST /api/customers/merge-suggestions/:id/dismiss` (`customers.merge`). `CustomersModule` is listed in `AppModule` before the leaf `CustomerProfileModule`, so `merge-suggestions` is matched before `:id`. Every id it takes (`survivorId`, `mergedId`, `suggestionId`, and the path ids) is lower cased first, because Postgres answers ids in lower case.
- The flag ([flags/](flags/), milestone 3): `CustomerFlags` (not exported) behind `PUT /api/customers/:id/flag` and `POST /api/customers/:id/flag/clear` (`customers.flag`, `@Audience('staff')`; the path id is lower cased). Both the service and the controller are provided by the leaf `CustomerProfileModule` (milestone 4), because a set with reason code `suggestion_applied` recomputes the returner signal from order counts. Set writes a `manual` flag on the canonical row with the person, now, and the note, and `customer.flagged`; clear empties the flag on every id of the canonical customer and writes one `customer.unflagged` per changed record under one correlation id. `CustomersService.setFlagFromImport(tx, customerId, kind, importRunId)` ([flags/set-flag-from-import.ts](flags/set-flag-from-import.ts)) is the import entry point of feature 15: `set` or `kept_manual`, no audit entry.
- `POST /api/customers/search` ([search/](search/)) by phone, name fragment, or the flagged list (a per person throttle and one log line per search without personal data), `@Audience('staff')` with `customers.view`.
- `CustomerProfileModule` ([profile/customer-profile.module.ts](profile/customer-profile.module.ts), milestone 4), the leaf of spec 0014's Decision: imported only by `AppModule` (after `CustomersModule`), it imports `CustomersModule`, `OrdersModule` (for `OrderQueries`), `ChannelsModule`, `PlatformModule` (settings), `AuditModule`, and `StaffDirectoryModule`, and exports nothing. The orders module imports `CustomersModule`, so the parts that read orders live here, without a cycle. It holds:
  - `GET /api/customers/:id` ([profile/customer-profile.service.ts](profile/customer-profile.service.ts)), `customers.view`: the profile, plus for a viewer with `orders.view` the returner `signal` and the `orderCount` (`CUSTOMER_PROFILE_GUARDED_FIELDS`).
  - `GET /api/customers/:id/timeline` ([profile/customer-timeline.service.ts](profile/customer-timeline.service.ts)), `customers.view`, declared before `:id`: one timeline over every id of the canonical customer, merged from the own rows (merges and undos, phones at their first seen time, channel ids at their creation, the current flag) and `OrderQueries.forCustomers`, keyset paged (`cursor`, `limit` 1 to 50 default 25, `kinds`), seen through the viewer's lens (`timelineLens` over `CUSTOMER_TIMELINE_KINDS` in `packages/contracts`).
  - `CustomerRiskSignals` ([profile/customer-risk-signals.ts](profile/customer-risk-signals.ts)): the returner signal (AC-13) and the order count, read only through `OrderQueries.countsForCustomers`, with the thresholds of the setting `customer_risk_signal`.
  - `ChannelLabels` ([profile/channel-labels.ts](profile/channel-labels.ts)): the store or channel label of a channel customer id, for the profile and the timeline.

## Never touches

- Other modules' tables. Store and channel labels come from `ChannelsService`, the name of the person who set a flag from `StaffDirectory`; orders come only through the orders module's `OrderQueries` (`forCustomers`, `countsForCustomers`), never a table (the module wall test fails otherwise).
- Another module's customer id: a merge never rewrites it, every read resolves it.
- A phone or channel id on another customer: nothing here ever moves one.
- Personal data in logs and errors: a phone, name, or flag note never reaches a log line, an error message, or an audit entry (Law 151).
- The ledger and the owner database role.

The unit suite holds `profile/timeline-cursor.spec.ts` and `profile/customer-timeline-lens.spec.ts` (the lens over built `Access` objects).

## Decisions

- **Search throttle** ([search/customer-search-throttle.ts](search/customer-search-throttle.ts), security review M1): each person may run `CUSTOMER_SEARCH_LIMIT` (30) searches in a sliding `CUSTOMER_SEARCH_WINDOW_MS` (one minute); the next call answers 429 `SEARCH_RATE_LIMITED` with `Retry-After`. The windows live in the memory of the api process, which is right while one api process serves a client (spec 0007); a second process per client would need a shared store. The owner changes the two constants. A refused call is not counted, and every allowed search logs `person`, `mode`, `results`, and `paged`, never the typed phone or name.
- **Lock order of `lockCustomers`**: locks are taken in the order of their lock key (the `hashtext` value, then the id), not in plain ascending id as spec 0014 words it. Two ids that share a hash then still lock in one order, so two merges can never wait on each other in a circle. The set of locked customers is the same.
- **Names and caching**: a name is stripped of invisible format characters (`\p{Cf}`, such as direction marks) before it is stored, so a pasted name cannot hide text or differ from itself; both routes answer `Cache-Control: no-store`, and a refused (429) search logs one warning with the person id only.
- **The flagged list** (AC-5 with AC-11): every canonical customer whose canonical flag is set, a customer whose only flag sits on a merged record included. Each customer is listed through the one row holding her canonical flag (her own row's, else the most severe merged one, then the latest set, then the lowest id), ordered by that row's set time, then its id, both descending, and the cursor is that pair, so no customer is skipped or repeated. The own flag half reads `customers_flagged_idx` in order; the merged half reads merged rows through `customers_merged_into_idx` (merges keep them few). An index on flagged merged rows would be a `packages/db` change if that half grows.
- **Name search cursor**: the cursor holds only the id of the last row (never a name); the next page starts after that row's own name and id, and an id that names no customer is 400 `INVALID_CURSOR`.
- **Migrations 0006 to 0008**: the flag set time check is added by a generated migration after a hand written one that backfills it, so a database that already holds a flagged customer upgrades.
- **Merge locks, then read again**: a merge reads both id sets, takes `lockCustomers` over them, then checks again under the locks that both ids are still canonical and neither set moved, else 409 `CUSTOMER_CHANGED`. The canonical check under the locks matters: a merge that read the pair before another merge of it committed, and the sets after, sees the same sets twice. Twenty parallel merges of one pair give one merge and nineteen 409s (`SAME_CUSTOMER` or `CUSTOMER_CHANGED`).
- **Undo rule**: a merge (survivor `S`, merged `X`) is undone only when no undo row names it (else `MergeAlreadyUndone`, 409 `MERGE_ALREADY_UNDONE`) and, under the locks, `S` is canonical and `X` points at `S` (else `MergeNotLatest`, 409 `MERGE_NOT_LATEST`). Unlike a merge, the undo deliberately re-reads the merge row and the two pointers under the locks instead of comparing `idsOf` sets: what it restores is the merge row's own `repointed_ids`, and the conditional update of those rows refuses `MergeNotLatest` when any of them no longer points at `S`, so a set that grew since (a later merge into `S`) is left alone. The audit handler turns both into `UndoNotPossible` with the same code; any other refusal is a plain `UNDO_NOT_POSSIBLE`. An undo from the customer route writes `customer.unmerged`; the audit screen's undo writes only `customer.merged_undone` on the merged record (the handler never writes an entry), so the repointed records get no entry of their own there.
- **Audit entries**: `customer.merged` is written on each changed record (the merged one and every record repointed from it), not on the survivor, whose row does not change; only the merged record's entry carries the undo. `customer.merge_suggestion_dismissed` is written on both customers of the pair, resolved to today's canonical ids (one entry when the pair already resolves to one). Entries carry ids, `mergedIntoId`, counts, and reason codes only.
- **Suggestion closing rule**: a merge marks the suggestion it names `applied` with its merge id, and also marks `applied` (with the same merge id) every other open suggestion whose two customers now resolve to one, since the merge settled them. A suggestion the merge names must be about the two merged customers, else 409 `SUGGESTION_MISMATCH`; an unknown suggestion id is 404 `SUGGESTION_NOT_FOUND` (the dismiss route answers the same). An undo reopens (back to `open`, with no merge id, decider, or decision time) every suggestion its merge applied, the named one included, whose pair no longer resolves to one customer: an undone merge puts the pair back in To review, where a person can dismiss it. The named one is not kept `applied`, because no column records which suggestion a merge named (decided by the lead, 2026-11-08, review m2). One pair still has one row ever.
- **`addPhone` lands on the canonical customer**: a phone added through a merged id is attached to the survivor, so an undo restores pointers, not phones (spec 0014 Consequences).
- **Bodies**: a missing (absent, null, or empty) reason code the route requires is 422 `REASON_REQUIRED`; an unlisted one, or a null or empty one where the code is optional, 422 `REASON_INVALID`; any other bad body 422 `VALIDATION_FAILED` naming paths only (`CustomerBodyPipe`).
- **The customer's stamp** (review m1, decided by the lead 2026-11-09): the profile's `updatedAt` is the greatest `updated_at` over every id of the canonical customer (`idsOf`), not the canonical row's alone. A merge stamps the rows it moves (with the write stamp below) and leaves the survivor's row alone, so absorbing a record moves the customer's stamp, and a flag set or clear made with a stamp read before the merge answers `STALE_RECORD` instead of clearing a flag the person never saw. An undo takes its records out of the set, so the stamp can step back to the value it had before the merge; the customer then reads exactly as she did when that stamp was issued, which is what the check protects. The records an undo restores get a fresh stamp, so the restored customer's stamp is newer than any stamp issued while the two were one, and every stamp issued then is stale on both (`customers.e2e-spec.ts` checks both directions).
- **The write stamp** (review m1 of milestone 3, decided by the lead 2026-11-09): every write that moves the customer's stamp (merge, undo, flag set and clear, `setFlagFromImport`) stamps `updated_at` with `nextStampOf(ids)` ([customer-stamp.ts](customer-stamp.ts)): `greatest(clock_timestamp(), max(updated_at) over the customer's id set + 1 microsecond)`, read after the `customer` locks. `now()` is the transaction's start, before the wait for the locks: a flag set that committed while a merge waited could carry a newer stamp than the merge's, so the absorbed record left the stamp where it was and a clear sent with the set's stamp emptied its flag unseen. Plain `clock_timestamp()` would suffice for writers under the locks on a clock that never steps back; the `+ 1 microsecond` floor makes the stamp move forward even when it does, or when a writer outside the locks (`findOrCreate`'s name write still uses `now()`) left a newer value. Business times (`risk_flag_set_at`, `decided_at`) stay `now()`. This changes milestone 2 code (the merge and undo updates) on the milestone 3 branch on purpose; PR #56 (milestone 2) stays as it is.
- **Flag concurrency**: set and clear take `lockCustomers` over the customer's id set, then lock the canonical row (`FOR UPDATE`), then every id merged into her in id order, and compare the customer's stamp with `expectedUpdatedAt` (409 `STALE_RECORD`); a set answers the stamp after its write. A clear that finds its id resolved to another canonical customer after the locks answers `STALE_RECORD` too. A set needs a canonical id (409 `CUSTOMER_MERGED`): a person flags the customer she sees, never a record merged away. A clear asked through a merged id works on its survivor, empties every flagged id, and bumps the canonical row's `updated_at` even when only a merged id held the flag, so the person's next stamp moves on.
- **The flag note**: stripped of invisible format characters (`\p{Cf}`, as a name is, review m5) and trimmed, then held to 500 characters, so the cap counts what is kept (the contract does this, and the service cleans again with `cleanCustomerName`); a blank note stores none (422 `NOTE_TOO_LONG` from `CustomerBodyPipe`, never echoed). The set answer carries the note, so it is `Cache-Control: no-store`; an `expectedUpdatedAt` before 1970 is 422 `VALIDATION_FAILED`. The name of the person who set the flag is read after the commit; a failed lookup answers `setByName: null` rather than a 500 for a written flag. It lives only on the customer row; audit entries carry the flag kind and source, never the note.
- **Import precedence**: `setFlagFromImport` answers `kept_manual` when any id of the canonical customer holds a `manual` flag (a merged record's included), else writes `blacklist_import` on the canonical row with no person and no note, replacing an older import or rule flag there. It refuses `CUSTOMER_CHANGED` when a merge moved the id set while it waited for the locks (the import retries the row). Ordering rule (review m3): its locks are held until the caller's transaction ends, so prefer one call per transaction; a transaction that flags several customers calls it in the order of the canonical lock key (`hashtext` of the canonical id, then the id), so two imports never wait on each other in a circle, and retries the whole transaction on a deadlock (`40P01`, against a merge spanning two of its customers) or on `CUSTOMER_CHANGED`. `importRunId` is not stored (no column holds it); the import's own audit entry carries it.
- **The leaf module** (spec 0014 Decision, milestone 4): `CustomerProfileModule` holds the profile, the timeline, the signal, and the flag routes, because they read orders and `OrdersModule` imports `CustomersModule`. The flag service and controller moved there too (the build plan names only the profile): the apply rule below needs the order counts inside the flag set's transaction, and the leaf provides `CustomerFlags` itself, so `CustomersModule` still exports only `CustomersService` (AC-19). Route order rests on `AppModule` listing the leaf after `CustomersModule`; `customers-merge.e2e-spec.ts` calls `GET merge-suggestions` and would fail otherwise.
- **The timeline cursor** ([profile/timeline-cursor.ts](profile/timeline-cursor.ts)): base64url of the last entry's (`at`, source key, id), with the shared `encodeKeyset` of `platform/keyset-cursor.ts`. The source keys compare as plain text: `channel_id`, `flag`, `merge` (merges and undos), `order`, `phone`. The own sources are read in one query in that order; the order source resumes from the orders module's own (`placed_at`, `id`) cursor, built from the position with the same shared encoding (no orders change): after an order, its own key; after an entry sorted before `order` at the same instant, (`at` plus one microsecond, the nil uuid); after one sorted after `order`, (`at`, the nil uuid). The own query answers at most `limit + 1` entries after the position and the orders `limit` plus their next cursor; the service sorts and cuts, and the next cursor is the last kept entry. All reads run in one repeatable read snapshot. The plus one microsecond is counted as a `BigInt` (a float loses it far from 1970), and the decoder refuses a year before 1970 or after 9998 (one microsecond past 9999-12-31 is year 10000, which the order source's cursor refuses); an `InvalidCursorError` from the order source is 400 `INVALID_CURSOR` too (review m1).
- **The timeline's entries**: one `phone_added` per phone the customer holds (the primary included) at its first seen time; the `flag` entry is the current canonical flag at its set time, on the record holding it; a merge or undo row shows when its survivor or merged record is one of her ids, with the other record as a brief (`otherRole` `merged`, or `survivor` when she is the record merged away). The merge's `undoable` (only with `customers.merge`) follows the undo rule; the `audit` link (only with `audit.read`) names the merged record, which carries the merge's entries.
- **The lens of the profile's order data**: `signal` and `orderCount` need `orders.view` (AC-15: order data needs it), so they are left out of the answer for a viewer without it (`CUSTOMER_PROFILE_GUARDED_FIELDS`, each key asked on its own). Every hat with `customers.view` holds `orders.view` today.
- **The returner signal** (AC-13): `sinceDay` is the calendar day `windowDays` before today in the `timezone` setting (`localDate`), passed to `countsForCustomers`, so the window is `windowDays + 1` calendar days, today included (180 means today and the 180 days before it; `profile/customer-risk-signals.spec.ts` pins it either side of Cairo midnight in winter and in summer time); the settings are read through the transaction, so a changed threshold applies on the next read. The rule is `suggestedRiskFlag` in `packages/contracts` (nothing when any id holds a flag; refusals first).
- **Applying a suggestion** (AC-13, the one tap): `PUT /api/customers/:id/flag` with reason code `suggestion_applied` is accepted only when, recomputed under the flag set's locks, no id of the customer holds a flag and the signal suggests exactly `kind`; the `customer.flagged` entry's `after` then also carries `refusals`, `returns`, and `windowDays`, the counts as the flag set's transaction saw them (its snapshot, not a later read). The person must also hold `orders.view`, since the yes or no answers about order counts (AC-15). Otherwise 422 `REASON_INVALID`, the code an unlisted reason answers.
