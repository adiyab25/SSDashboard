# apps/api

## Overview

The NestJS backend that holds every business rule. One codebase, three entry points in the `app` image: `api` (HTTP, `src/main.ts`), `worker` (pg-boss jobs, `src/worker.ts`), and `migrate` (`src/migrate.ts`, runs migrations and exits).

## Commands

```bash
pnpm --filter @ssdashboard/api dev        # Watch mode on port 3001
pnpm --filter @ssdashboard/api test       # Unit tests (src/**/*.spec.ts)
pnpm --filter @ssdashboard/api test:e2e   # test/*.e2e-spec.ts against Postgres (build first), except the scale suite
pnpm --filter @ssdashboard/api test:scale # only test/scale.e2e-spec.ts (build and migrate first); the `scale` CI job
pnpm --filter @ssdashboard/api worker     # Run the built worker (pg-boss jobs)
```

## Conventions

- One folder per business module under `src/<module>/`, holding its module, services, controllers, specs, and a `README.md` (the five headings of `docs/templates/module-readme.md`, checked by `pnpm lint:repo`) side by side.
- Inside the api and worker, log through Nest's `Logger` (routed to `RedactingLogger`); `console` appears only in command line paths (`create-admin.ts`, the startup env failure) and never with personal data. A new field that carries personal data goes into the list in `packages/config/src/redaction.ts`.
- Read config only through the injected `ENV` token, never `process.env` directly; add every new variable to `env.ts` and `.env.example`.
- Database access goes through the Drizzle client from `database.module.ts`; tables are defined in `packages/db`, not here.
- Import Drizzle helpers (`sql`, `inArray`, `SQL`) from `@ssdashboard/db`, never from `drizzle-orm`: pg-boss's `@opentelemetry/api` peer makes pnpm create a second drizzle-orm copy whose types do not match.
- Pass an array to raw SQL as one literal, `${pgArray(ids)}::uuid[]`; Drizzle expands a plain JS array into a list of parameters.
- Validate query strings with `new ZodQueryPipe(<contract schema>)` (`src/platform/zod-query.pipe.ts`); a bad query answers 400 with the stable code `INVALID_QUERY`, or the code passed as its second argument (`new ZodQueryPipe(schema, 'INVALID_FILTER')` in the audit list).
- Read brand settings only through `SettingsService.read(keys, tx?)` or `get(key, tx?)`; pass the transaction when the value must agree with the rows you write (the lock date), else the read is cached for up to 30 seconds. Never query `settings` directly, and change a setting only through `SettingsService.write` (`PUT /api/settings/:key`), which audits, notifies, and enqueues the reconcile job.
- A module that changes a record a manager must be able to trace calls `AuditService.record(tx, entry)` inside its own transaction, with an action code from the registry in `packages/contracts/src/audit/audit-actions.ts` (spec 0010 AC-11, AC-19).
- List endpoints page with a keyset cursor (the last row's sort key, base64url encoded) and compare and order with `COLLATE "C"`, so pages never skip or repeat rows (`src/inventory/locations/locations.service.ts`).

## Gotchas

- ESM with NodeNext resolution: relative imports need the `.js` suffix (`./app.module.js`).
- The api never migrates on boot. Run `pnpm db:migrate`, which builds the api first.
- Better Auth needs NestJS's body parser off for `/api/auth`, and its cookies stay host only (never a `Domain`), `Secure` on an https `PUBLIC_URL`, `HttpOnly`, `SameSite=Lax`, on `Path=<STAFF_BASE_PATH>` (else `/`); see [src/identity/AGENTS.md](src/identity/AGENTS.md).
- The core never imports an extension; extensions load by dynamic import only.
- `DATABASE_URL` is the application role, which cannot create databases. The e2e helpers create scratch databases with `MIGRATION_DATABASE_URL` (the owner) and run the ledger as the app role with `options=-c role=ssdashboard_app`.
- `test/scale.e2e-spec.ts` seeds the spec 0002 load (50,000 variants, 150,000 orders and the rest) and the spec 0010 audit load (5,000,000 entries, `test/scale-audit-seed.ts`, which turns the three audit stamp triggers off as the owner around the load and always back on); the audit list reads go through the real `AuditQueryService`, whose issued SQL each plan check explains. It runs only through `test:scale` (`vitest.config.scale.ts`), in the `scale` CI job (nightly, `scale` label on a pull request, or by hand); `vitest.config.e2e.ts` excludes it. `pnpm --filter ... test:e2e -- <file>` does not filter in this repo (the `--` is forwarded and vitest ignores it): call `pnpm --filter @ssdashboard/api exec vitest run --config ./vitest.config.e2e.ts <file>` for one file.
- The route sweep `test/access-sweep.e2e-spec.ts` reads every route from the running module graph and needs a `FIXTURES` entry per route (`METHOD /path`, the permission spec 0008's route mapping names, and a path, body and headers to call it with); a new route without one fails it. Its helpers are `test/route-catalog.ts` (routes from Nest metadata) and `test/in-process-api.ts` (the app in process on a scratch database).
- The undo start check (every undoable code in `AUDIT_ACTIONS` has a registered handler, else the process stops with `AuditUndoHandlerMissing`) runs only in the api: `AuditUndoStartCheck` is provided by `AuditUndoModule`, which only `AppModule` imports. Never import `AuditUndoModule` into `WorkerModule` or give `AuditUndoRegistry` a start hook: the worker loads `AuditModule` to record entries, does not load every owning module, and would crash loop on deploy (review M4R1; `src/audit/audit-routes.spec.ts` fails it). A module that owns an undoable code must be imported by `AppModule` so its handler registers before the check.
- The module wall is `src/module-boundary.spec.ts`: a file in one module that names another module's table (by Drizzle export or SQL name, from `TABLE_OWNERSHIP` in `packages/db`) fails it, and so does an extension that names a core table. Its `KNOWN_BREACHES` list may only shrink. It also holds the identity import wall: another module may import only the files in `IDENTITY_PUBLIC_FILES` from `src/identity/`. And the audit walls: only the undo may name the undone entry writer (`AuditUndoneWriter`), and only `AuditService` and that writer may name the entry insert pieces in `src/audit/audit-entry-sql.ts` (`entryValues`, `INSERT_ENTRIES`; security review AS36).
