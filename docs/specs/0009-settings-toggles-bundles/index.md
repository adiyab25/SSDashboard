## Summary

One image becomes a Warehouse install, an Operations install, or both through three things kept in one place: a typed list of every brand setting (what it is, its default, who may change it), a list of modules and capabilities with the bundle each belongs to and an on or off switch, and a signed license file that says which bundles the brand bought and until when. When a module is off, its pages hide, its api answers "module off", and its background jobs and schedules are removed, so nothing is left running half way. When the yearly Operations plan lapses, the app warns first (30, 14, 7 days), gives 14 days of grace, then winds down gently: it keeps following, matching, and closing the cash of shipments already out with Bosta, lets work already in flight finish, and a renewal catches up the mirror without acting on the gap. A Warehouse license is perpetual unless it carries an expiry (pilot and trial licenses), in which case it warns, graces, and turns read only the same way. Every step that acts on the outside world on the brand's behalf (creating Bosta shipments, refunding, writing to Shopify, sending Meta events or WhatsApp messages, approving exchanges by rule) is its own switch, off on a fresh install, and acts only on what happens after it was switched on.

## Requirements

**User stories**:
- As the brand's manager, I want one settings screen where I can see and change how the brand works (policies, automations, modules, owner types, cost rules), with the reason recorded, so that the app fits the brand without a developer.
- As the vendor, I want one image for every brand, switched by a license and toggles, so that a Warehouse only brand and a full Operations brand run the same tested code, and a paid pilot can carry a time limited Warehouse grant.
- As the brand owner, I want a lapsed Operations plan to warn me early and never strand cash already out with the carrier, so that I am never afraid of the app switching off under me, and my last month in the app can still close.
- As an operations agent, I want automations to stay off until a manager switches each one on, and to act only on what happens after that, so that nothing ships, refunds, or messages a customer by surprise.
- As a developer, I want a module that is off to leave no schedules, queued jobs, or half sent commands behind, so that turning it back on is safe.

**Acceptance criteria**:

*The settings registry and its read path*
- **AC-1** (registry): Every brand setting is one entry in one registry in `packages/contracts/src/settings/` with: `key`, the Zod `schema` of its value, `default`, `bundle` (`core`, `warehouse`, or `operations`), `group` (the settings screen section), `whoMayChange` (`settings.manage`, the permission of spec 0008, or `nobody`), `reason` (`required` or `optional`, passed to `AuditService.record` as the tightening flag spec 0010 AC-5 allows), `exposure` (`public_config` or `staff`), `sqlRead` (true when SQL reads the row, so a seed row must exist), and optionally `warning` (a message key the change dialog shows, naming what else the change moves) and `confirm: 'typed'` (the dialog asks the person to type the setting's name). An `executing_step` entry also carries `notifiesCustomer` (AC-21). A unit test (`registry.spec.ts`) fails when two entries share a key, a default fails its own schema, a `sqlRead` key has no seed row in the baseline, an `executing_step` entry defaults to anything but `false` or lacks `notifiesCustomer`, or an entry lacks an English or Arabic label key.
- **AC-2** (one read path): `SettingsService.read(keys)` and `SettingsService.get(key)` are the only readers of the `settings` table and return typed values. A key with no row returns its registry default. A stored value that fails its schema returns the default, logs one error naming the key (never the value), and is flagged `invalid` in the staff read; an entry marked `onInvalid: 'refuse'` (a setting that guards money, the ledger, or document numbers: today `inventory_lock_date` and `document_prefixes`) instead makes business reads throw a typed error, so the work it guards is refused rather than run unguarded (amended 2026-11-07, security review S1). A read given a transaction (`executor`) goes to the database; any other read is served from a per process cache. Reading a key that is not in the registry fails `tsc`.
- **AC-3** (one write path): `PUT /api/settings/:key` validates the value with the entry schema and, in one transaction, writes the row (`updated_at`, `updated_by`), writes the `setting.changed` audit entry with before, after, and reason, sends `NOTIFY ssd_platform_changed`, and enqueues the `platform.reconcile_modules` job. A value equal to the stored one (or to the default when there is no row) writes nothing, no audit entry and no notification, and answers the entry with `changed: false`, so `updated_at` always marks the last real change (the watermark of AC-27). It answers 404 `SETTING_UNKNOWN`, 422 `SETTING_INVALID` (with the Zod issues), 422 `REASON_REQUIRED`, 409 `STALE_SETTING` when `expectedUpdatedAt` differs from the row, 409 `SETTING_LOCKED` when `whoMayChange` is `nobody`, and 403 `FORBIDDEN` for a caller without `settings.manage`.
- **AC-4** (cache across processes): after a committed change, a running api and a running worker both read the new value within 5 seconds (LISTEN on `ssd_platform_changed`); with the listener connection killed, both read it within 35 seconds (a 30 second cache lifetime), and the listener reconnects by itself. A rolled back change is never seen by any process.
- **AC-5** (what is public): `GET /api/config` stays `@Audience('public')` and returns exactly the fields of spec 0004 AC-4 (`clientName`, `version`, `currency`, `timezone`, `languages`, `defaultLanguage`, `mailEnabled`) and only registry entries marked `public_config`. Nothing about bundles, the license, module states, executing steps, policy knobs, owner policies, or cost rules. A test asserts the exact key set.

*Modules, capabilities, bundles, and what "off" means*
- **AC-6** (module registry): one registry in `packages/contracts/src/modules/` lists every api module with its `bundle`, whether it has a toggle (`core` modules never do), the modules it `requires`, and its capabilities. A capability has a `key` (`<module>.<name>`), a `bundle` (may differ from its module's, for example the Shopify stock push is `warehouse` inside the `core` connectors module), a `kind` (`read`, `write`, or `executing_step`), `windDown` (`none`, `pre_lapse`: keeps working in the wind down for pre lapse records and stops when it ends; or `until_closed`: keeps working for records opened before the lapse or the toggle off until it reports no open item, also after the wind down), optional `requiresOneOf` (capability keys, at least one of which must be `on`, AC-29), and `workOf` (the permissions whose holders' work it carries, for the staff notice of AC-17). In the api, a capability may register `openItems`, `backfill`, `onDisable`, and `offImpact` hooks with the platform. A unit test fails when a `core` module requires a non core module, a module requires one with no path to it, a capability key repeats or does not start with its module key, a `requiresOneOf` key is unknown or forms a cycle, or an `executing_step` has a `windDown` other than `none`.
- **AC-7** (one state rule): one pure function, `moduleState` in `packages/contracts/src/modules/module-state.ts`, gives every module and capability one state: `on` (with `since`, the instant it last became runnable), `limited` (with `before`: it works only for records opened before that instant), `read_only`, or `off`, plus a `reason` (`not_licensed`, `lapsed`, `toggled_off`, `step_off`, `no_stock_out_source`). Its inputs are each bundle's phase (AC-15) with its lapse instant, the module toggles with their `updated_at`, each executing step's switch with its `updated_at`, the open item counts of `until_closed` capabilities, and the instant each bundle was last renewed. The rules are in *Effective state* below. An exhaustive test covers every combination.
- **AC-8** (routes): every api controller declares exactly one of `@RequiresModule(moduleKey)` or `@RequiresCapability(capabilityKey)` at class level; a handler may narrow with `@RequiresCapability` naming a capability of the same module. A controller inside a core module that serves an Operations or Warehouse capability declares that capability (for example the confirmation queue controller of feature 18 declares `orders.confirmation_queue`; see *Module registry*). `requires-module.spec.ts` fails the build when a controller has none or two class declarations, or names a key missing from the registry or a capability of another module (the same shape as `audience.spec.ts`). A global `ModuleGate` guard, after the audience and permission guards, answers 404 `{ "code": "MODULE_OFF" }` for every route of an `off` module or capability, and for every non `GET` route of a `read_only` one; `GET` routes of a `read_only` one keep answering so the brand's data stays readable. Every route of a `limited` capability answers; its owning service refuses a write on a record opened at or after `before` with 409 `MODULE_LIMITED`. Portal routes (`@Audience('portal')`) that start new work answer 404 `MODULE_OFF` unless their capability is `on`; a portal `GET` of a request the customer submitted before the capability stopped keeps answering while it is `limited` or `read_only` (D17). Hook routes (`@Audience('hook')`) never answer 404 for module state: they answer 200 and the connector records `ignored_unlicensed`, except the wind down events of AC-18. No route answers 500 because a module is off.
- **AC-9** (screens): the back office shell reads `GET /api/platform/modules` and hides every navigation and command palette entry whose module or capability is `off`, and every action entry (new, approve, queue) whose capability is `read_only`, which shows its history pages with a read only notice naming the date it went read only and "ask a person who manages settings". A `limited` capability shows its pages with a notice saying only records from before that date can be finished. A page of an `off` module opened by its URL shows a "not available on this install" state inside the shell with one `<h1>`, never a crash. Module state is refetched on window focus, at most every 60 seconds otherwise, and at once after any api answer of 404 `MODULE_OFF` or 409 `MODULE_LIMITED`. Changing a toggle, a step, or the license never signs anyone out. The portal (feature 29) shows, instead of an error, a branded Arabic first page "Requests are handled on WhatsApp" with the brand's contact number from the `public_config` setting `portal_contact_whatsapp`, and a submitted request's status read only (AC-8). Both languages, keyboard reachable.
- **AC-10** (no orphaned jobs): every pg-boss queue and cron schedule is declared through the platform `JobRegistry` with the capability it serves. A capability is runnable when its state is `on` or `limited`; a `limited` handler works only on records opened before `before`. When a capability stops being runnable (`off` or `read_only`), the worker's `ModuleJobSupervisor`, in this order: removes its schedules (`unschedule`), stops its workers (`offWork`), and cancels its queued jobs (`cancel`); marks its `waiting` outbound commands `failed` with reason `MODULE_OFF` (one task for the manager per capability, not one per command, feature 17; the task links to the filtered list of affected records, each showing its own failed sync state); and calls the capability's `onDisable` hook (connector features remove the Shopify and Meta webhook subscriptions they registered through those APIs). Every job handler asks `ModuleStateService.isRunnable(capability)` before any work; a job that starts in the race window completes with output `{ "skipped": "MODULE_OFF" }`, never `failed`. The test `apps/api/test/module-off-no-orphaned-jobs.e2e-spec.ts`, case "a module turns off with no orphaned jobs", proves it with a fixture Operations module: after the toggle, `getSchedules()` lists none of its queues, `findJobs` with `queued: true` finds none, no job of the module is `active` or `failed`, its waiting command is `failed` with `MODULE_OFF`, its routes answer as AC-8 says, and no error level log line was written.
- **AC-11** (turning back on): turning the same module on again restores its schedules (in the current `timezone` setting) and workers, replays nothing that was cancelled, leaves `MODULE_OFF` commands for a person to retry, and, when the capability declares a `backfill`, enqueues one backfill job for the gap from the moment it went off to now (singleton key on the gap, so a second reconcile adds none). The backfill and every executing step follow AC-27: nothing in the gap is acted on toward a customer or an outside system. Same test file, case "turning it back on restores schedules and replays nothing".
- **AC-12** (toggles): a module toggle is the setting `module.<key>.enabled` (default `true`), changed only by a holder of `settings.manage` with a required reason through AC-3 (owner ruling 3, 2026-11-07). Turning on a module whose bundle is not licensed answers 409 `NOT_LICENSED`; turning off a module that another `on` module requires answers 409 `MODULE_REQUIRED_BY` with the dependants; a `core` module has no toggle (404 `SETTING_UNKNOWN`). The off dialog shows what is in flight and what will drop (AC-30) before it asks for the reason; for `credit` with outstanding balances or `exchanges` with approved requests it also asks for typed confirmation. Work in flight can still finish (AC-28), and turning the module back on acts only on new events (AC-27). The worker reconciles within 5 seconds (the `platform.reconcile_modules` job from AC-3) and at worker start.
- **AC-13** (calls between modules): a core module never depends on an optional one; it asks `ModuleStateService.isOn(key)` before calling one. Write methods of an optional module's exported services call `ModuleStateService.assertOn(key)` (or `assertMayFinish(key, recordOpenedAt)` for a `limited` capability) and throw the domain error `ModuleOff`; its in process event listeners return without work when it is not `on`.

*The license*
- **AC-14** (file and verification): a license is a JSON envelope `{ "keyId", "payload", "signature" }` of at most 16 KB, where `payload` is base64url of UTF 8 JSON bytes and `signature` is a base64url Ed25519 signature over exactly those bytes. The payload (Zod, strict) is `{ "format": 1, "licenseId", "clientCode", "tenantId", "bundles" (non empty subset of `warehouse`, `operations`), "operationsExpiresOn" (a date, present exactly when `operations` is in bundles), "warehouseExpiresOn" (optional date, allowed only when `warehouse` is in bundles; absent means the Warehouse grant never expires), "issuedOn" }`. `format` stays 1: no license has been issued yet, so the optional field changes no issued meaning. Verification uses only public keys built into the image (`license-keys.ts`), never the network. A key marked `devOnly` is refused when `NODE_ENV` is `production`. This release ships the committed `devOnly` key only; the owner supplies the production primary and standby public keys for a later release (owner ruling 1, 2026-11-07). `clientCode` and `tenantId` must equal the `install` row. A license is checked at api start, at worker start, daily by the worker (`LICENSE_CHECK_CRON`), and on upload; a valid one not yet recorded is added to `licenses`.
- **AC-15** (bundle phases): one pure function, `bundlePhase(bundle, input)` in `packages/contracts/src/license/license-phase.ts`, gives each licensed bundle its phase from the recorded licenses for that bundle, today's date in the `timezone` setting, and, for Operations, `operations_wind_down_days`, `operations_wind_down_pickup_days`, the count of open `pre_lapse` items, and whether the wind down already ended. Operations returns `not_licensed`, `active`, `expiring` (0 to 30 days left; behaves as active), `grace` (expiry plus 1 to plus 14 days; behaves as active), `wind_down`, or `off`. Warehouse returns `not_licensed`, `active` (always, when a recorded Warehouse license has no expiry), `expiring`, `grace`, or `off`: it never takes `wind_down`, because no outside party holds the brand's cash for Warehouse work; its one piece of work in flight, stock in transit, finishes through AC-28. The lapse instant of either bundle is local midnight starting day expiry plus 15. The Operations wind down never ends early before the pickup window (AC-18) has passed. The test covers, for both bundles, expiry day (still `expiring`, 0 days left), day 1 and day 14 of grace, the lapse day, and for Operations the last wind down day, an early end at zero open items, the pickup window holding the early end, and that `off` stays `off` until a renewal.
- **AC-16** (bad or missing file): a missing file, an unset `LICENSE_FILE`, unreadable or malformed JSON, a bad signature, an unknown key, a dev key in production, or a license for another install each records a `license_checks` row with its outcome, logs one error with the outcome and the file's SHA 256 (never its contents), and changes nothing else: recorded licenses keep counting, so a deleted or damaged file never switches a module off. The api and the worker keep running. A holder of `settings.manage` sees a banner naming the outcome. With no license ever recorded, only `core` modules are on. A server clock set back in time is recorded (`clock_behind`) and shown, never enforced (owner ruling 2, 2026-11-07).
- **AC-17** (warnings): `LicenseService.notice(day)` returns, per bundle with an expiry, the phase, days left, a level, what stops and when, and what continues and until when. The shell shows a banner to holders of `settings.manage` from 30 days before expiry and through grace and the wind down, in words such as "On 15 April at 00:00 the confirmation queue, new Bosta tracking, and WhatsApp messages stop. Cash for shipments already out keeps being followed until 14 June." From 7 days before the lapse and through the wind down, people whose work stops (holders of a stopping capability's `workOf` permission) see a neutral notice with no price and no commercial terms: "From 15 April the confirmation queue stops. Ask your manager." The daily report's automation status line (feature 25) includes the manager notice on days 30, 14, and 7 before expiry and on every grace and wind down day; in the wind down the report is the reduced one of AC-18. A warning is never sent outside the brand's own report channel.
- **AC-18** (lapse and wind down): at the Operations lapse instant the next license check (or the worker start) records phase `wind_down` and emits `LicenseChanged`. Every Operations capability with `windDown: none` goes `read_only` and loses its jobs as AC-10 says (the confirmation queue, driver mode, new shipment mirroring, the dashboard, Meta and WhatsApp sends stop). Capabilities with `pre_lapse` (`connectors.bosta.mirror_reads`, `connectors.bosta.cash_cycle_sweep`, `settlement.carrier_reconciliation`, `reporting.daily_report` in its reduced form) and `until_closed` (`settlement.carrier_close_out` and the finish in flight list of AC-28) go `limited` before the lapse instant. A shipment is in the wind down scope when the carrier created the delivery before the lapse instant (the carrier's own creation time, not when we discovered it), or when its order was confirmed before the lapse instant and the carrier created it within `operations_wind_down_pickup_days` after it (D5); `LicenseService.inWindDownScope({ carrierCreatedAt, orderConfirmedAt })` answers it. One discovery sweep runs after the lapse for deliveries in that scope. The matching job, a person's match and account rows, the Bosta settlement file import, and closing a carrier period that contains in scope lines keep working, so pre lapse orders can go `collected_by_carrier`, `remitted`, `reconciled` and the month can close (D1). The reduced daily report shows the phase, the wind down days left, the pre lapse cash still expected (count and amount of open items), and what failed (D7). During the wind down a Bosta webhook for an in scope shipment is still enqueued; one for a later shipment, and every Operations event after the wind down ends, is answered 200 and recorded `ignored_unlicensed` (carried n2). The wind down ends at `operations_wind_down_days` after the lapse, or earlier, once the pickup window has passed, when every `pre_lapse` capability reports zero open items (orders not in a final cash state: `reconciled`, `nothing_to_collect`, `prepaid`). At its end `LicenseService` emits `WindDownEnded { lapsedAt, endedAt }`: the last reduced report lists what is still open, and one manager task (feature 17) links to the settlement module's "open after the wind down" list (order, store, tracking number, expected COD, last carrier state, last cash state), downloadable there, so the accountant can chase Bosta by hand (D8). `until_closed` capabilities stay `limited` after the end until their open items reach zero. Core capabilities never change, with no time limit (owner ruling 5, 2026-11-07). At a Warehouse lapse (only with a `warehouseExpiresOn`), the phase goes from `grace` to `off`: Warehouse capabilities go `read_only` except `inventory.transfers_receive` (`until_closed`, AC-28), and the stock push pauses (AC-29). The test `apps/api/test/license-lapse.e2e-spec.ts` proves each step with a fixture clock.
- **AC-19** (renewal): recording a license that extends a bundle's expiry (or makes it perpetual) moves the phase to `active` or `expiring` and emits `LicenseChanged`. From `wind_down` or `off`, the supervisor restores schedules and enqueues each capability's `backfill` job once for the gap from the lapse instant to the renewal (singleton key on the gap), under AC-27. From `grace`, nothing was stopped, so nothing is backfilled. On the upload answer and in the license section, the manager sees the executing steps that will resume, in plain words, and that they act only on new events. Same test file.
- **AC-20** (installing a license): a holder of `settings.manage` can upload a license on the settings screen (`POST /api/platform/license`), which verifies it like the file, records it, and writes the `license.added` audit entry. A license that verifies but grants nothing new (an older or identical one) answers 200 with `changed: false`. Recorded licenses only ever add; the entitlement per bundle is their union: a bundle with any recorded license lacking an expiry never expires; otherwise its latest expiry counts. A new license never shortens an expiry or removes a bundle, so a later perpetual Warehouse license supersedes a pilot one.

*Executing steps and policy knobs*
- **AC-21** (executing steps): each step in *Executing steps* below is its own registry entry with `kind: executing_step`, default `false`, `whoMayChange: settings.manage`, reason required, its bundle, `notifiesCustomer` (whether the app or the provider messages the customer because of it; a Shopify write passes `notifyCustomer: false` and the entry says `false`, D10), and an optional precondition its feature supplies (turning on answers 409 `STEP_PRECONDITION` with the precondition's code). A fresh install has every step off. The code that executes asks `ModuleStateService.isRunnable(step)` inside the job, at the moment it would act, never only at enqueue time, and acts only on records whose triggering event is at or after the step's `since` (AC-27). Turning a step off shows the off dialog of AC-30, makes queued executions complete as skipped, and marks their waiting commands `failed` with reason `STEP_OFF`, as AC-10 does for a module.
- **AC-22** (policy knobs): the knobs in *Policy knobs* below exist with the defaults shown, are changed only by a holder of `settings.manage` with a required reason, and each feature that applies one records the value it used on its decision (for example the approval record of feature 31). Changing `operating_day_cutoff_hour` or `timezone` shows that days already stamped are never restated and that the day of the change is longer or shorter (the entry's `warning`), and the supervisor re registers every cron schedule in the new time zone within 5 seconds.
- **AC-23** (per order cost rules): a holder of `cost.view` sees the current rule for each kind and its history; a holder of `settings.manage` and `cost.view` adds a rule (`set` with a value, or `not_set`) from an effective date through `CostRulesService.record` (a new append only row, `cost_rule.recorded` audit entry, reason required). The rules from spec 0002 AC-32 hold (percent 0 to 100, a value exactly when `set`). An `effective_from` on or before the `inventory_lock_date` setting answers 409 `COST_RULE_IN_LOCKED_PERIOD` with the months whose margins it would change; the same request with `inLockedPeriod: true` and a written reason is recorded and audited as `cost_rule.recorded_in_locked_period`, so nobody moves the lock date (which would reopen stock postings) for a narrow cost fix (D14). While `inventory_lock_date` is unset, the Cost rules page shows a prompt that nothing is locked yet.

*Location owner types as a setting*
- **AC-24** (owner policy editing): a holder of `settings.manage` edits a `location_owner_policies` row through `PUT /api/inventory/owner-policies/:ownerType`, served by the inventory module (which owns the table) through `LocationPolicyService.updatePolicy`, with a required reason, the `policy.changed` audit entry, and `expectedUpdatedAt` (409 `STALE_SETTING`). It refuses: an inconsistent row (`handover_is_sale` must equal not `stock_owned_by_brand`; `sale_recorded_at` is `at_handover` exactly when `handover_is_sale`; `can_sell_online` must be false when `stock_owned_by_brand` is false, so partner stock is never offered online) with 422 `OWNER_POLICY_INCONSISTENT`; any change to the locked fields (`stock_owned_by_brand`, `handover_is_sale`, `sale_recorded_at`, `tax_document`, `settlement_owner_type`) of the `own` row, or of a row with at least one location that is not archived, with 409 `OWNER_POLICY_IN_USE`, so changed terms mean a new location (D13); and `can_sell_online` set to false while a location of that type has `sellable_online`, with 409 `SELLABLE_LOCATIONS_EXIST`. A change answers only future questions; recorded movements and settlement lines are never reinterpreted, and a refund decision records the policy answer it used (feature 35). `test/location-owner-types.e2e-spec.ts` (spec 0002) still passes, and a new case edits a refund field through the endpoint and sees the next `policyFor` answer change with no code branch.

*The settings screen and staff reads*
- **AC-25** (settings screen): a holder of `settings.manage` opens `/settings` in the back office (one `<h1>`) with sections: Brand (languages, default language, currency shown read only, time zone, operating day cutoff, document prefixes, prices include VAT, inventory lock date), Modules and license, Automations (executing steps), Policies, and Location owner types; a holder of `cost.view` opens Cost rules at `/settings/cost-rules` (its own nav entry, `needs: 'cost.view'`; the add action also needs `settings.manage`), so a person with the cost grant but no settings permission can read the rules (D15). Each item shows its value, its default, whether it is the default, who changed it last and when, and whether its bundle is licensed (an unlicensed item is shown disabled with "needs the Warehouse plan" or "needs the Operations plan"). A change opens a dialog with the new value, the entry's `warning` when it has one, typed confirmation where the registry says `confirm: 'typed'`, and a reason field (required where the registry says so). Turning on an executing step states in plain words what the app will start doing for the brand, whether the customer hears about it (for a Shopify write: "Shopify will not email the customer"), and that it acts only on what happens from now on. Turning a step or module off shows the off dialog of AC-30. The retention bonus item says the bonus is store credit only, never cash (owner ruling 4, 2026-11-07), and shows a worked example ("a 1,000 refund can be offered up to 1,100 in credit"). The Location owner types section says each row "applies to every location of this type" and points to the partner's own agreement (feature 41) for per partner terms (D22). Errors show on the field from the stable codes. Both languages, logical CSS, keyboard and focus support, axe clean, built to `packages/ui/DESIGN.md`. A person without `settings.manage` opening `/settings`, or without `cost.view` opening `/settings/cost-rules`, gets the no access state of spec 0008 AC-11.
- **AC-26** (staff reads): `GET /api/settings` (`settings.manage`) returns every registry entry with value, default, `isDefault`, `invalid`, `updatedAt`, `updatedBy` (name through the identity service), `canChange`, and `licensed`. `GET /api/platform/modules` (any staff hat, `@AnyHat()`) returns each module's and capability's state, the staff notice of AC-17 for the caller's permissions, and, for a holder of `settings.manage` only, the license notice. `GET /api/platform/license` (`settings.manage`) returns, per bundle, its expiry (or perpetual) and phase, days left, the last check's outcome, and the recorded licenses (id, bundles, expiries, issued, source, recorded at), never signatures or file paths.

*Lapse, return, and in flight work (amended 2026-11-07)*
- **AC-27** (backfill and the step watermark, D3): a `backfill` catches up mirror state only. It imports provider facts, records them with the `system` actor and a backfill marker, and never acts toward a customer or an outside system: it sends no command, opens no queue work for a record whose next step already happened outside the app (a gap order that already has a carrier delivery skips the confirmation queue and is recorded as confirmed outside the app, with no agent and no outcome code), and its events are never a trigger for an executing step. An executing step acts only on records whose triggering event is at or after its `since`: the latest of the `updated_at` of the write that switched the step on, of the write that turned its module back on, and of the check that renewed its bundle out of `wind_down` or `off`. A module turned back on acts only on new events. The lapse test proves it: a step is on before the lapse, an order and its shipment arrive in the gap, and after the renewal zero outbound commands exist for gap records and none of them is in the queue; the steps test proves a step switched on today sends nothing for last week's open orders.
- **AC-28** (finish in flight, D6): at a lapse and at a module toggle off, a short list of `until_closed` capabilities stays `limited` to records opened before that instant, so work already physically or financially in motion can finish: restock a returned to origin or returned piece against its order (`orders.returned_to_origin_restock`, feature 21; this keeps the Warehouse plan's stock true); inspect a returned exchange piece, then restock or write it off, and cancel an approved exchange with a reason (`exchanges.finish_in_flight`, features 31 and 34); record a manual refund or a credit payout as paid with proof (`credit.record_payout`, features 28 and 35); close out pre lapse carrier cash (`settlement.carrier_close_out`, feature 22); and, at a Warehouse lapse, receive a transfer dispatched before it (`inventory.transfers_receive`, feature 38). None of them opens a new request or runs an executing step. At the lapse and at the toggle off, the platform opens one task per area with in flight records (exchanges approved but not shipped, refunds owed, credit balances outstanding, returns in transit), from each capability's `openItems`.
- **AC-29** (stock truth, D2): `connectors.shopify.stock_push` declares `requiresOneOf: [connectors.bosta.new_shipments, connectors.shopify.fulfillment_stock_out]`: it is runnable only while at least one source that records an online sale leaving stock is `on` (the Bosta mirror of new shipments, Operations; or recording stock out from Shopify fulfillment, owned by feature 13). A feature that adds another source (for example pick, pack and ship, feature 33) adds it to the list. Otherwise the push is `read_only` with reason `no_stock_out_source`: the supervisor removes its jobs (AC-10) and opens one manager task saying Shopify's own counts now lead. Turning `step.shopify_stock_push` on with no source runnable answers 409 `STEP_PRECONDITION` (`NO_STOCK_OUT_SOURCE`), so a Warehouse only install cannot push until feature 13 builds the fulfillment source. The lapse test proves that after the Operations lapse, with no other source, the push stops and the task opens.
- **AC-30** (the off dialog, D11): before turning a module or an executing step off, the screen calls `GET /api/settings/:key/off-impact`, which answers the count of waiting outbound commands by kind that will be failed, the in flight records per area that stay finishable (AC-28), and whether typed confirmation is needed (AC-12). The dialog shows them before it asks for the reason.

## Decision

**Chosen option**: Option 2 in [rationale.md](rationale.md): one typed registry in `packages/contracts` for settings and modules, module toggles and executing steps stored as ordinary settings rows, a signed license file whose verified copies are recorded in an append only table, and one worker supervisor that reconciles jobs and schedules with the computed module and capability states.

Module toggles and executing step switches are settings (one table, one cache, one audit path, one screen), and their bundle gate comes from the registry; only the license needs its own two tables. Runner up: a dedicated `module_toggles` table with its own service, rejected because it doubles the read, cache, audit, and screen paths for a boolean per module.

### Data model sketch

No change to `settings` (spec 0002: `tenant_id`, `key`, `value jsonb`, `updated_at`, `updated_by`; primary key (`tenant_id`, `key`)). Two new platform tables, both append only (`ssd_reject_change()` triggers and the app role revokes of the tenancy child A4), both in `packages/db/src/schema/platform.ts` and in `table-ownership.ts` under `platform`:

### Effective state

```
moduleState(capability c, of module m, in bundle b), first matching rule wins:
  1. b is not core and phase(b) = not_licensed       -> off (reason not_licensed)
  2. phase(b) = wind_down (Operations only)           -> c.windDown in (pre_lapse, until_closed) and c is not an executing step
                                                          ? limited (before = lapsedAt) : read_only (lapsed)
  3. phase(b) = off                                   -> c.windDown = until_closed and openItems(c) > 0 ? limited (before = lapsedAt) : read_only (lapsed)
  4. m toggle false                                   -> c.windDown = until_closed and openItems(c) > 0 ? limited (before = toggledOffAt) : read_only (toggled_off)
  5. c.requiresOneOf and none of those is on          -> read_only (no_stock_out_source)
  6. c is an executing step and its switch is false   -> off (step_off; its module keeps its own state)
  7. otherwise                                        -> on (since = latest of the step switch-on, the module turn-on, the bundle renewal)
```

"Licensed now" is `core` always; any other bundle when its phase is `active`, `expiring`, or `grace`. `toggledOffAt` is `updated_at` of the `module.<key>.enabled` row while it is `false`. "Runnable" (jobs) means `on` or `limited`; an executing step is never `limited`.

### Bundle phases

| Today (local date in `timezone`) | Operations | Warehouse |
|---|---|---|
| no recorded license has the bundle | `not_licensed` | `not_licensed` |
| a recorded license has the bundle with no expiry | (not possible: Operations always has one) | `active`, never expires |
| more than 30 days before expiry | `active` | `active` |
| 30 to 0 days before expiry (expiry day included) | `expiring` | `expiring` |
| expiry plus 1 to expiry plus 14 | `grace` | `grace` |
| from expiry plus 15 (the lapse instant is local 00:00 that day) until the wind down ends | `wind_down` | `off` (no wind down) |
| after `operations_wind_down_days`, or once the pickup window has passed and open `pre_lapse` items reached zero, until a renewal | `off` | `off` |

Expiry per bundle is the union rule of AC-20: never, when any recorded license with the bundle lacks an expiry; otherwise the latest expiry across recorded licenses.

### Key invariants

- A missing settings row means the registry default; the default of every `executing_step` is `false`; a `sqlRead` key always has a row; `updated_at` moves only on a real change.
- Writes to `settings` happen only in `SettingsService.write`, always with an audit entry, a `NOTIFY`, and the reconcile job in the same transaction.
- No pg-boss queue or schedule exists outside `JobRegistry`; a capability that is not runnable has no schedule and no queued job after the supervisor's reconcile, and no handler does work for it; a `limited` handler touches only records opened before `before`.
- A backfill never acts toward a customer or an outside system, and an executing step never acts on a record whose triggering event is before its `since`.
- The Shopify stock push never runs while no stock out source runs.
- `licenses` and `license_checks` are append only; the entitlement per bundle is the union of recorded licenses, so it never shrinks except by time.
- License verification never opens a network connection; the private signing key never enters the repository, an image, or an install.
- Only `LocationPolicyService` writes `location_owner_policies`; owner type values are compared nowhere else (spec 0002 boundary test); partner stock is never sellable online.
- `GET /api/config` exposes no commercial state.

### Security model

- Settings, toggles, steps, policies, owner policies, and the license are read and changed only with `settings.manage` (the manager hat, spec 0008). Cost rules need `cost.view` to read and `settings.manage` plus `cost.view` to change ("all listed permissions required", spec 0008). `currency` changes by nobody in the app. Module states are readable by every staff hat (`@AnyHat()`, the shell needs them); the license notice only by `settings.manage` holders; the staff notice carries no price or commercial term.
- The license carries no personal data and no secret; tampering only makes it invalid. The worst case of a stolen vendor private key is free bundles for any install; mitigated by keeping it offline and by a second, standby public key in the image for rotation (owner ruling 1).
- A setting reason is free text from staff: stored only in the audit entry (phone shaped text masked by spec 0010), never logged.
- No compliance scope beyond the existing Law 151 logging rule: no setting holds customer data (`portal_contact_whatsapp` is the brand's own business number).

### Configuration required

- `LICENSE_FILE`: path to the signed license inside the container (api and worker env lists only). Optional; unset gives `none_configured`.
- `LICENSE_CHECK_CRON`: when the daily license check runs (worker), default `20 0 * * *` in the `timezone` setting, validated by the existing `cron()` helper in `env.ts`.
- Both added to `apps/api/src/config/env.ts`, `.env.example`, and the Compose `api` and `worker` services. `pnpm bootstrap` writes a dev license signed with the committed dev key (`devOnly`) for the local install. No production public key exists in this release (owner ruling 1); a production image refuses every license until the owner's keys ship.

## Consequences

**Positive**:
- Adding a setting, a policy knob, or an executing step costs one registry entry and its labels: no migration, no new endpoint, no new screen code.
- A module that is off is provably quiet: no schedule, no queued job, no half sent command, and every later feature inherits that by declaring its jobs through the registry.
- A lapse never strands cash already out with the carrier, the last month can close, work in flight can finish, and the license never phones home, so self hosted and offline installs behave like vendor hosted ones.
- A renewal or a switched on step never treats history as fresh work or fresh messages.
- A paid pilot can carry a time limited Warehouse grant, and a later perpetual license simply supersedes it.
- Location owner types stay one code path while their answers become the brand's to edit.

**Negative / tradeoffs**:
- Every controller carries one more decorator and every job one more declaration; the build test makes forgetting cheap to catch, not free.
- One shared `PgBoss` instance replaces the per job instances: a refactor of three working jobs in milestone 3.
- A dedicated LISTEN connection per process costs one connection on the shared PostgreSQL server per api and worker; a future connection pooler in transaction mode would break LISTEN, leaving only the 30 second lifetime.
- The license cannot stop a determined self host client who rolls back the clock or patches the image; it records evidence instead. It is a commercial lock, not copy protection.
- Recorded licenses only add, so a mistaken license issued with too long an expiry cannot be revoked remotely; the vendor fixes it by contract.
- Read only and `limited` states mean history pages of every Operations feature must work without their write routes, and every `until_closed` capability must scope its writes by record age.
- On a Warehouse only install the stock push cannot run until feature 13 builds stock out from Shopify fulfillment.
- No production license can verify until the owner's public keys ship in a later release.

**Neutral**:
- The settings registry, module registry, and step list become shared files every later feature edits (like the table ownership map).
- `apps/web/src/shell/nav.ts` gains a required `module` field on every entry.
