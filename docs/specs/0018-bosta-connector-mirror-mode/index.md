## Summary

The brand's own Bosta Shopify app creates every delivery; this feature only reads them, so the app never writes to Bosta (mirror mode). A Bosta webhook (a message Bosta sends after each state change) is only a hint: it moves that delivery to the front of one read queue, and every state, fee, and cash cycle the app applies comes from Bosta's single delivery read, spaced at least one second apart and capped per run, because Bosta starts refusing at about sixty quick calls. Each delivery is linked to its store and order, and its state moves the order through the named moves spec 0013 already offers (picked up, failed attempt, delivered, returned, lost), so features 21 and 22 can build on clean events. When a confirmation edit changes what the customer owes after Bosta already holds the delivery, the app compares Bosta's COD (cash on delivery amount) with the order's `cod_expected_amount`, flags the carrier record stale, tells the agent where it can still be fixed for that Bosta state, never claims it updated Bosta, and clears the flag once a later read shows the fix. It also keeps Bosta's list of cities, zones, and districts, so the confirmation queue (spec 0017) can fix an address into Bosta's own areas.

## Requirements

**User stories**:
- As the brand's manager, I want to connect our Bosta account once with a read only key, paste a webhook address, header name, and value that the screen shows me, and see plainly when Bosta stops talking to us, so that I never wonder whether tracking is current.
- As an operations agent, I want every parcel's Bosta state on its order within minutes, and a short list of parcels that need a person (exception, on hold, stuck at pickup, no movement, Bosta's delayed flag, repeated attempts, stalled), so that I chase the right parcels each morning without opening Bosta's dashboard.
- As a support agent, I want to be told, right after I change a size or a piece on a confirmed order, that Bosta still holds the old COD, where I can still change it for the parcel's current state, and to see the warning go away once Bosta shows the new amount, so that the courier never asks the customer for the wrong amount.
- As the accountant, I want Bosta's fees and cash cycle per delivery recorded from the delivery's own detail, never blanked by a list pass, and read again until Bosta settles it, so that feature 22 can match a month of real settlement line by line.
- As the developer of features 21 and 22, I want one documented service and a set of past tense events for delivery states, attempts, the returned to origin change, and cash cycles, so that my feature never calls Bosta itself.
- As the vendor, I want every Bosta behaviour proven on recorded fixtures with no live call, so that CI never depends on a real account or touches customer data.

**Acceptance criteria** (the contract; each is checked in [verify.md](verify.md)):

*Connecting an account*
- **AC-1** (connect): a manager (`settings.manage`) connects a Bosta account on `POST /api/connections/bosta` with a label, the API key, an optional store binding (`storeId`; none means one account for every store), and the detail API version (`v0` default, or `v2`). In one transaction the connectors module creates the connection (provider `bosta`, health `connecting`, credentials sealed, a generated webhook key), writes the audit entry `connection.created`, and enqueues a `bosta-connect` job. The job reads list page 1 and the newest delivery's detail and sets health `ok`, or `failing` with one code: `CREDENTIALS_REJECTED` (HTTP 401 or 403), `SHAPE_UNKNOWN` (a detail answer without a tracking number or a numeric state code in any accepted envelope), or `BOSTA_UNREACHABLE` after the transient budget. It always adds the warning `KEY_SCOPE_UNCHECKED` (Bosta offers no read we found that tells a key's scope; the screen says "use a Read Only key"). A second unbound account, or a bound account while an unbound one is live (or the reverse), answers 409 `BOSTA_BINDING_CONFLICT`; a second account bound to the same store answers 409 `BOSTA_STORE_TAKEN`.
- **AC-2** (secrets): the API key and the webhook key are stored only inside the sealed credentials (`kind: 'bosta_api_key'`, AES-256-GCM under `CONNECTOR_SECRET_KEY`, as spec 0015 AC-2). No answer, log line, audit entry, error, inbox row, or event carries the API key; the screen shows "set" and its last 4 characters. The webhook key is the one secret a person must read, so it is answered only by `GET /api/connections/:id/bosta-webhook` (manager, audited `connection.webhook_key_revealed`), and `POST /api/connections/:id/bosta-webhook/rotate` (reason required, audited `connection.webhook_key_rotated`) replaces it; after a rotation the previous key is still accepted for 24 hours so the brand can update Bosta's dashboard.
- **AC-3** (webhook setup by hand, carried M2): the connection screen shows the webhook address (`PUBLIC_URL` + `/api/hooks/bosta/<connection id>`), the header name (`config.webhookHeaderName`, default `x-ssd-webhook-key`), and a "Show value" action with copy buttons, plus the steps to paste them into Bosta's business dashboard (Settings, API Integration, Set Up Your Webhook). `docs/runbooks/bosta-connection.md` lists the steps to register the webhook, to replace the value after a rotation, and to remove it when the connection is archived, the Operations plan lapses, or the wind down ends. The app never claims a webhook is registered: it shows "last webhook N minutes ago" or "no webhook received yet".

*Webhooks and the inbox*
- **AC-4** (header check first): `POST /api/hooks/bosta/:connectionId` decides method, path, id shape, and connection (unknown, archived, or not `bosta`) before reading a byte, reads at most 64 KB within 10 seconds, and compares the configured header with the stored key (or the previous key inside its 24 hours) in constant time (SHA-256 of both, then `timingSafeEqual`). Any failure answers the same empty 401, writes no inbox row, and counts a failure on a live connection (at most one write per connection per minute, as spec 0015 AC-4).
- **AC-5** (durable inbox, hints only): a verified call inserts one `inbound_events` row (subject `delivery`, topic `bosta.state_changed`, dedupe key `bosta:<trackingNumber>:<state>:<timeStamp>`, `ON CONFLICT DO NOTHING`) and enqueues its job in the same transaction, then answers 200; a repeat answers 200 and adds nothing. The payload keeps only `trackingNumber`, `state`, `type`, `timeStamp`, `numberOfAttempts`, and `cod`; never `exceptionReason`, a name, a phone, or an address. The job applies nothing from the payload: it moves that delivery to the front of the read queue (priority 1, creating a stub row for an unknown tracking number) and marks the event `processed` with outcome `read_queued`. A body without a tracking number or a numeric state answers 400 `INVALID_HOOK_BODY`.
- **AC-6** (licence and wind down, carried M5 and domain-stack n2): the hook asks `LicenseService.acceptsHook` with scope facts read from the stored delivery row (`carrier_created_at`, and the order's confirmation time through `OrderQueries`), never from the webhook payload. While Operations is active the call is processed. During the wind down a call for a delivery in the wind down scope (`LicenseService.inWindDownScope`) is still enqueued and read; a call for a delivery created after the lapse, or for a tracking number the app does not know, is answered 200 and recorded `ignored_unlicensed`; after the wind down ends every Bosta call is answered 200 and recorded `ignored_unlicensed`. Discovery of new deliveries (`connectors.bosta.new_shipments`) stops at the lapse; one discovery run after the lapse picks up deliveries in scope; detail reads (`connectors.bosta.mirror_reads`) and the cash cycle sweep (`connectors.bosta.cash_cycle_sweep`) keep running, limited to in scope deliveries, until each reaches a final cash state or the wind down ends. Each of the two `pre_lapse` capabilities registers its `openItems` hook (spec 0009 Follow-up). On renewal, `connectors.bosta.new_shipments` declares a `backfill` hook that walks the list from the gap start (at most 60 days back, as the first backfill); a gap longer than 60 days is shown on the Overview tab with its start, because older deliveries are no longer reachable by the list walk (review m9).

*Reading Bosta*
- **AC-7** (one mapper, read back first): every state, attempt, COD, fee, and cash cycle the app applies comes from one parse of Bosta's single delivery read (`BostaDeliveryMapper.fromDetail`), whatever caused the read (webhook, discovery, list change, schedule, a person). The parser accepts the delivery at the root, under `data`, under `delivery`, or as `data.deliveries[0]`; reads attempts from `numberOfAttempts`, else `attemptsCount`, else the length of `state.exception`; reads the creation time from `creationTimestamp`, else `createdAt`; parses every money field from a number or a string to 2 decimal places (half away from zero) and never derives VAT or totals itself; and keys every rule on the numeric `state.code`, never on the label. A detail answer that fails the parse sets the read failed with `SHAPE_UNKNOWN` (AC-11) and changes nothing.
- **AC-8** (discovery and the list pass): every 5 minutes the list pass reads `GET /deliveries?page=N` newest first, from page 1 until a page whose oldest creation time is older than the connection's listed watermark minus 30 minutes, at most 30 pages a run. A tracking number it has not seen becomes a delivery row at priority 2; a known one whose listed state code differs from the stored one goes to priority 3. On the first successful connect check, a first backfill walks the list back over the same 60 days as spec 0015 AC-17 (from the store's Shopify go live instant when one is set, else the connect time, minus 60 days), resumable under the run budget, queueing every delivery it finds at priority 2 (review M8); the list watermark starts at its end. A nightly deep list pass (02:15 in the install time zone) walks back 45 days of creation time, at most 600 pages, to find anything the 5 minute pass missed. A list pass writes only `last_listed_at` and `listed_state_code` and the creation and type facts of a new row: it never writes `state_code`, `phase`, attempts, COD, fees, cash cycle, or exception data, so a list sync can never blank or overwrite them.
- **AC-9** (the read queue and the rate policy, carried M1): all calls of one connection run one at a time (pg-boss group per connection, `groupConcurrency: 1`) with at least 1,000 ms between any two Bosta calls. A call times out after 15 seconds; a transient failure (network, timeout, HTTP 5xx, 429) is retried in the call at most 4 times with backoff of 500 ms doubling to at most 8 seconds with full jitter, and a 429 waits at least its `Retry-After` (delta seconds or an HTTP date). A run spends at most 60 seconds waiting on 429 answers, makes at most 120 detail reads and 30 list pages, and lasts at most 10 minutes (each job chunk ends within 55 seconds and sends its continuation); past any limit the run ends `partial` and the next run resumes. Detail reads are taken by priority, then least recently read first: 1 webhook hint, a stale carrier record (AC-21), or a person's "read now"; 2 newly discovered; 3 the list showed a changed state; 4 an open delivery due again (60 minutes after its last read once picked up, 6 hours while awaiting pickup), followed until 45 days after Bosta created it (awaiting pickup only 14 days); 5 the cash cycle sweep (AC-10). Three runs in a row that end `partial` on the 429 budget set health `degraded` with `RATE_LIMITED`.
- **AC-10** (fees and the cash cycle sweep, carried M1): `shipmentFees` and `wallet.cashCycle` (`_id`, `shipping_fees`, `opening_package_fees`, `flex_ship_fees`, `vat`, `bosta_fees`, `cod`, `deposited_amt`, `deposited_at`) are written only from a detail read. A delivery in a final phase (delivered, returned, terminated, cancelled, lost, damaged) with no cash cycle, or with a cash cycle that has no deposit time, is read again every 24 hours for 60 days after it reached that phase, then weekly with no end while it holds collected COD and no deposited cash cycle (review M2: never dropped silently). A detail read that answers no fees or no cash cycle never clears a stored value. A first cash cycle, or a changed amount or id on a stored one, raises the delivery's `cash_cycle_revision` and publishes `CarrierCashCycleRecorded` with every amount, the deposit time, and the revision; a negative `deposited_amt` (a returned to origin or prepaid parcel) is stored and published as negative.
- **AC-11** (failed reads are seen and retried): a transient failure leaves the delivery in the queue with its read attempts counted; three hours of transient failure on a connection set health `degraded` with `READS_FAILING`. HTTP 404 on a detail read marks the delivery `read_failure_code = 'NOT_FOUND_AT_CARRIER'` and stops following it after 3 such answers on 3 days. A delivery whose apply throws a domain error is marked with the error code, publishes `CarrierDeliveryReadFailed` (connection, delivery, tracking number, order id when linked, code) in the same transaction, and is listed on `/deliveries/failed-reads` with a retry action for hats with `orders.confirm` (review M4); the domain writes roll back.

*Linking a delivery to its store and order*
- **AC-12** (the store, carried B1): a delivery's store comes from the account's binding when it has one. For an unbound account it comes, in order, from `shopifyInfo.storeName` matched against the connection's store name map (prefilled from every Shopify connection's shop domain and shop name, editable on the Mapping tab), then from the business reference's prefix before `:` matched against the prefix map (prefilled from each Shopify shop domain's first label, for example `pilotbrand` for `pilotbrand.myshopify.com`). The source is stored (`binding`, `shopify_store_name`, `business_reference`, or `person`). When neither map gives a store, the connector tries `OrderQueries.idByNumber` with the reference's order number in every store of the tenant and links when exactly one order matches (`store_source` `order_number_unique`, review M4); otherwise the delivery is `store_unknown`, listed with the candidate orders and their store codes, shown on `/deliveries/unlinked` (AC-28), and tried again on every detail read, when a map changes, and on `OrderPlaced` with a matching number (review m6).
- **AC-13** (the order): within its store a delivery links to an order, in order, by `shopifyInfo.orderId` through the store's Shopify connection's order mappings (`connection_external_ids`, gid `gid://shopify/Order/<id>`), then by the order number in the business reference or `shopifyInfo.orderNumber` (`#1001`, `1001`, or `<prefix>:#1001`) through `OrderQueries.idByNumber(storeId, orderNumber)`. A delivery with no match is `order_not_found` on `/deliveries/unlinked`, tried again on `OrderPlaced` in its store with a matching number, also after its follow window (review m6). A person with `orders.confirm` may link it by hand with a reason code (`carrier_delivery.linked_by_person`, audited); a link is never changed afterwards except by a person with the same audit. Among an order's linked forward deliveries (type send, return to origin that began as a send, or an exchange (30) linked to an exchange replacement order, AC-33) one is active: the newest not cancelled or terminated before pickup. Only the active one moves the order; when two are past pickup at once the delivery gets the flag `duplicate_forward_delivery` and only the older one moves the order until a person resolves it.

*Moving the order (the state mapping)*
- **AC-14** (states move the order, decision D-1): the active forward delivery's detail read applies the order move the *State mapping* table gives for its type and state code, inside one `OrderTransactions.run` unit (the read happens before the unit; the unit writes the connector's rows first, then calls orders, touches one order, calls no provider). While Bosta reports pickup requested (10) or waiting for route (11) the delivery is only recorded: the order stays editable and its money is not frozen, because Bosta lets the merchant change COD and address only in those states. At first link the connector calls `recordCarrierDeliverySeen` (decision D-1). The first state from route assigned (20) on, for an order already `confirmed` or `packed` (else at its confirmation or the first pickup, D-1), calls `recordCarrierDelivery` (`source: { type: 'carrier_delivery', id: <delivery id> }`, at the state's time), which freezes `cod_expected_amount`; the first pickup or later forward state calls `recordShipmentFact` `shipped`, which books the shipment posting through orders (the stock out). A fact that orders refuses for the `carrier` actor comes back `{ applied: false }` with orders' own `carrier_fact_contradicts_state` attention; the connector records the event row's `order_move` as `not_applied` and goes on. Each applied move writes one `carrier_delivery_events` row with the Bosta time; replaying the same detail read applies nothing new.
- **AC-15** (attempts and the returned to origin change): each new failed attempt (an entry of `state.exception` beyond `attempts_reported`, or a state 47 with a higher attempt count) calls `recordShipmentFact` `failed_attempt` once, with that attempt's time, and stores its exception code and reason text on the event row; `CarrierAttemptFailed` is published per attempt. When the same tracking number's type changes from send to return to origin, the connector records it, publishes `CarrierDeliveryTypeChanged`, and moves the order only at returned to business (46), which calls `recordShipmentFact` `returned_to_origin`. A send at 46 is treated as returned to origin as well. Refusal at the door, the next try, restock, and partial delivery are spec 0019's (feature 21); this feature never calls `refused` or `recordPartialDelivery`.
- **AC-16** (collection at delivery, owner decision Q-19.4): at delivered (45) on the active send the connector calls `recordShipmentFact` `delivered` and, when the order has COD due, `recordCollection` with the amount Bosta reports collected: the cash cycle's `cod` when present, else the webhook `cod` (stored on the delivery only after a detail read confirmed 45, never on the webhook alone, review m1), else the delivery's `cod`, with `source` the delivery and reason code `carrier.reported`, `carrier.reported_by_webhook`, or `carrier.assumed_from_cod` respectively. A later cash cycle `cod` that differs corrects the collection with a new `recordCollection` call. A collected amount that differs from `cod_expected_amount` by 0.01 or more flags the delivery `collected_differs` and publishes `CarrierCollectionDiffers` for spec 0019 (partial delivery) and spec 0020. Before any hold the connector compares the collected amount with the delivery's own `cod_amount` (spec 0019 second pass): when it equals `cod_amount` within 0.01 but is below `cod_expected_amount`, the courier collected what Bosta held, so `delivered` applies with no hold and the difference is published with `cause` `cod_rule_mismatch` (the delivery is `cod_rule_mismatch`, AC-31) or else `carrier_record_stale`; a delivery under a standing `COD_RULE_MISMATCH` warning is never held. Otherwise, when the collected amount is at least 0.01 below `cod_amount` and below `cod_expected_amount` (`cause` `courier_short`) and the order has two or more open pieces (spec 0019 AC-12, Q-21.4), the connector records the collection but holds the `delivered` move: it sets `delivered_held_at` on the delivery and publishes `CarrierCollectionDiffers` with `deliveredHeld: true` and `heldAt`; from then on it never calls `delivered` for that delivery, because spec 0019 decides the move (a partial delivery, or delivered after all). Collected more than expected, or any difference on a one piece order, applies `delivered` as usual with `deliveredHeld: false`.
- **AC-17** (ends without delivery): terminated (48) or cancelled (49) before any pickup calls `recordShipmentFact` `cancelled` with reason `carrier.terminated_before_pickup`; after a pickup it moves nothing, flags the delivery `terminated_after_pickup`, keeps it on the 60 minute open cadence (not the cash cycle cadence) until 46, 100, or a person clears the flag (review m2), and publishes `CarrierDeliveryStateChanged` for spec 0019. Lost (100) calls `recordShipmentFact` `lost` with reason `carrier.lost`, damaged (101) `lost` with reason `carrier.damaged`. Investigation (102), awaiting your action (103), archived (104), on hold (105), fulfilled (25), and returned to stock (60) move nothing and are recorded.
- **AC-18** (exchange and return pickups, amended 2026-11-13): a delivery of type customer return pickup (25), a new tracking number by Bosta's design, is mirrored, linked to the order its business reference or order number names, and published with its type on every event, but never moves that order's fulfillment or cash state; features 21, 34, and 37 decide what it means. A delivery of type exchange (30) is linked and moves orders by AC-33: it is the forward delivery of the exchange replacement order, and its old piece is spec 0019's returned parcel.
- **AC-19** (a cancel Bosta must hear about, revised for review M3 and m5): after every detail read, every link, and every `OrderCancelled`, a linked order that is `cancelled` whose active forward delivery is at 10, 11, or 20 holds the flag `cancel_in_bosta`, whatever came first (a delivery discovered or linked after the cancel included). Its task opens only if Bosta still shows 10, 11, or 20 thirty minutes after the later of the cancel and the sync of its Shopify cancel write back, because the Bosta apps can cancel on their own (S6, S14); then `CarrierDeliveryNeedsAttention` with that kind is published, since in mirror mode the app cannot terminate the delivery. The flag clears when a read shows 48 or 49. Spec 0013 raises `terminate_carrier_delivery` when the cancel happens while it already knows the delivery (through `recordCarrierDeliverySeen`), and spec 0017's card says to terminate it in Bosta; in that case this spec opens no second task for the flag, and opens its own only for a delivery found after the cancel, so one cancel opens one task. When a read shows 48 or 49 (Bosta or its app terminated the delivery, which the newer app can do on its own, S14), the connector clears the flag and closes spec 0013's attention through `OrderAttentions.resolve(tx, orderId, 'terminate_carrier_delivery', { source: deliveryId, reason: 'carrier_terminated' })` (requested from spec 0013), so the task closes by itself (spec 0017 review m12). A delivery picked up after the cancel follows spec 0013's own `cancelled` to `shipped` rule. The flag also holds for an order with an open manual handover (spec 0019 AC-23, set from `ManualHandoverRecorded`) whose active forward Bosta delivery is at 10, 11, or 20: its task opens at once (no Shopify cancel is involved, so no grace) with the text "cancel the Bosta delivery for this order; it left with your driver", and clears when a read shows 48 or 49.

*The carrier side of a confirmation edit (audit item 9, spec 0002 review n1)*
- **AC-20** (stale carrier record, widened for review X1 by the lead's ruling): once the order is confirmed (`confirmed_at` set) and until it reaches a final state, after every detail read of its linked active forward delivery and within one minute of an `OrderEdited` (which sends a priority 1 read), the connector compares five fields of Bosta's delivery with the order's confirmed values, in memory, reading the order's side through `OrderQueries.carrierCheckViewOf(tx, orderId)` (requested from spec 0013; personal data, connectors only, never logged, like `writeBackViewOf`). The five fields are the only values of `CarrierMismatchField` (see *Carrier record fields*): `receiver_address` (Bosta `dropOffAddress.firstLine` against the order's ship to address, both normalized: trimmed, spaces collapsed, Arabic digits to Latin, letter case folded), `receiver_phone` (Bosta `receiver.phone`, and `receiver.secondPhone` when present, normalized with spec 0014's `EgyptianPhone`, against the order's primary and second phone: it differs when a Bosta phone is neither of the order's, or the order's primary is not among Bosta's), `carrier_area` (Bosta `dropOffAddress` city, zone, and district, by id when the read gives one, else by name against `carrier_areas` `name` and `other_name`, against the order's carrier area codes after spec 0017's fix; compared only when the order has area codes), `cod` (Bosta `cod` against `cod_expected_amount`, never `cod_due_amount`; it differs at 0.01 or more), and `items_count` (Bosta's item count against the order's open piece count). A field marked unverified is compared only when Bosta's read carries it; an absent field is never a mismatch. Any mismatch sets on the delivery `stale_since`, the mismatched field names (`stale_reasons`), the expected COD, and `fixableBy`, sets the order's flag through `OrderCarrierRecord.markStale` (requested from spec 0013, decision D-2) in the same unit, and publishes `CarrierRecordStale` with the payload in *Exported services and events*: the tracking number and the list of mismatches, where `cod` and `items_count` carry Bosta's value and the order's value and `receiver_address`, `receiver_phone`, and `carrier_area` carry the field name only (Law 151: no address, phone, or area text leaves memory, and only field names are stored). A `cod` mismatch also says whether it was there at first link with no later edit (`origin` `at_creation`) or followed an edit (`after_edit`), and whether the order's payment method disagrees with Bosta (`paymentMethodDiffers`: a prepaid order with COD at Bosta, or a COD order with 0 there; the spec 0015 Follow-up carried here, review M8). A changed list or `fixableBy` publishes `CarrierRecordStale` again. While the flag is set, spec 0013's `markPacked` refuses the order (requested by this spec and spec 0017); because in slice 1a packing is not the only gate (review M7), the hold also shows on `/deliveries` and the carrier panel as "hold: Bosta holds a different delivery, do not hand it to the courier". The agent's banner reads `CarrierDeliveries.bannerFor(orderId)`. `fixableBy` comes from the *Who can still fix it* table by state code and field. Every text names what differs and where to change it for that state, with amounts for `cod` and `items_count` only; no text, event, audit entry, or task ever says the app changed, sent, or updated Bosta. The flag is named "carrier record stale" as in spec 0017; this spec's task `carrier.record_stale` comes before spec 0017's reconfirmation (AC-30); spec 0017 owns the reconfirmation, closes it as `cleared_by_carrier`, and owns what the agent sees in the confirmation queue.
- **AC-21** (the fix mirrors back): while a delivery is stale and any mismatched field is still fixable (`merchant`, `bosta_support`, or `bosta_support_best_effort`), it is read again every 10 minutes at priority 1. The first read on which no field mismatches clears the flag on the delivery and on the order (`OrderCarrierRecord.clearStale`) and publishes `CarrierRecordStaleCleared` with the mismatch list that was set, the reason `fixed_at_carrier`, and the latest fix outcome of AC-30; an order edit that makes the order match Bosta again clears it with reason `order_matches`. When the delivery reaches a state where every mismatched field is `nobody` or `closed`, `CarrierRecordStale` is published again with the new `fixableBy`, so the task can say it is too late; the mismatch stays on the delivery for spec 0020.

- **AC-30** (fix before reconfirm, spec 0017 domain review M6): a stale carrier record opens this spec's task `carrier.record_stale` first; spec 0017's reconfirmation with the customer waits for its outcome. When every mismatched field is `merchant` fixable and the editor is known (`editedBy`), the task is assigned to the editor with a 30 minute due time and spec 0017's banner shows the fix at once ("change it in the Bosta app now", review M6); left open after 30 minutes, or at once when a field is only fixable by Bosta support, it moves to the operations hat. A person with `orders.confirm` closes the task through `POST /api/carrier-deliveries/:id/record-fix` with exactly one outcome: `updated` (changed in Bosta's dashboard or app, or by Bosta support), `recreated` (the delivery was cancelled in Bosta and a new one made, with its new tracking number), `cannot_update` (too late for the state, or Bosta refused), or `cancel_recommended` (operations advises cancelling the order), and a reason code; audited `carrier_delivery.record_fix_recorded`. The connector publishes `CarrierRecordFixRecorded` (order, delivery, outcome, the new delivery and tracking number for `recreated`) in the same transaction, and `CarrierRecordStaleCleared` carries the latest fix outcome when the flag clears; a read that shows the fix before anyone acts closes the task as the system with `updated`. `updated` sends a priority 1 read and the flag clears only when a read confirms the amount; until then it stays set and `CarrierRecordFixRecorded` already told spec 0017. `recreated` needs the new tracking number (a delivery Bosta already shows, or one the connector reads at once): the connector links the order to the new delivery, makes it the active forward delivery, retires the old one (`forward_active` false, flag `replaced`, `replaced_by_delivery_id` set, no further order moves from it, followed only until Bosta shows 48 or 49, else flagged `cancel_in_bosta`), and runs the stale check on the new one. `cannot_update` and `cancel_recommended` leave the flag set; spec 0017 decides the customer call and what the agent says, and the cancel itself.
- **AC-31** (a COD rule difference is a setup finding, review M7): the connect check, and the hourly check until the store's go live plus 7 days, compares Bosta's `cod` with `cod_expected_amount` over the last 50 linked deliveries of confirmed orders and shows the distribution of differences on the Overview tab. When at least 80% of them share one non zero difference, the connection gets the warning `COD_RULE_MISMATCH` with that amount and the runbook step (the Bosta app's shipping and deposit settings); while it stands, a `cod` mismatch of exactly that amount with `origin` `at_creation` is recorded on the delivery as `cod_rule_mismatch` and sets no stale flag, opens no task, and blocks no packing. A manager clears the warning by fixing the setting (the next check finds no common difference) or acknowledges it with a reason (`connection.cod_rule_acknowledged`, audited), after which such differences are stale again. A mismatch after an edit is always stale.
- **AC-32** (the send mode of a connection, owner decision Q-18.1 of 2026-11-13, spec 0017 AC-33): `BostaConnectionConfig` gains `sendMode` (`by_hand_after_confirmation` or `app_sync_at_creation`, required, chosen at connect with no default so the brand answers it), `bostaShopifyApp` (which of Bosta's two Shopify apps the store uses, a code from the runbook's list), and `bostaAutoCancel` (boolean: whether that app cancels the delivery when the Shopify order is cancelled), and `bostaAppSyncsEdits` (boolean, default false: whether that app copies a Shopify edit onto the delivery; read only by spec 0017's checklist). A holder of `settings.manage` changes them on the connection page with a reason (`connection.send_mode_changed`, audited, `before` and `after` the three values). `CarrierDeliveries.sendModeFor(storeId)` answers the mode of the connection that serves the store (the bound one, else the unbound one), `by_hand_after_confirmation` when none. Under `app_sync_at_creation`, `OrderStateChanged` to `confirmed` sends a priority 1 detail read of the order's delivery, and AC-20's check at the freeze compares only on that read's result, never on an earlier cached read (domain review of 2026-11-13, M3). Otherwise the mode changes three things: (a) under `app_sync_at_creation` a 20 on a `new` order records `route_before_confirmation` as the delivery's attention label but opens no task, because it is every order's normal path (spec 0017 shows it on the card); (b) `bostaAutoCancel` on makes `cancel_in_bosta` wait for Bosta's own 49 for 30 minutes after a synced Shopify cancel (the rule of AC-19), and off opens it at once; (c) the Overview tab shows the mode, and under `app_sync_at_creation` a store where 5 of its last 20 orders have no delivery 30 minutes after placing gets the warning `APP_SYNC_NOT_SEEN` (the app may be set to manual). The stale check (AC-20), the freeze (D-1), and the state mapping are the same in both modes.
- **AC-33** (a Bosta Exchange as the replacement's forward delivery, owner decision Q-21.13 of 2026-11-13, spec 0019 AC-34): a type 30 delivery links, in order: to the order its business reference names when that order is an exchange replacement (`type = 'exchange_replacement'`); else, when the named order is the original of exactly one exchange replacement that is not cancelled and has no active forward delivery, to that replacement, recorded as `carrier_delivery.linked_to_exchange_replacement` (system, audited); else to the named order as a non forward delivery that moves nothing, and spec 0019 opens `delivery.exchange_unlinked`. A person may relink it with the existing link route and the reason code `dashboard_exchange`. Linked to a replacement, it is that order's forward delivery (AC-13) and moves it by the *State mapping* rows for type 30: picked up from business (21) `shipped`; in transit and out for delivery as a send; a failed attempt `failed_attempt`; delivered (45) `delivered` with `recordCollection` of Bosta's `cod` when the replacement has COD due (the price difference, spec 0019 AC-34); after 45, the old piece's trail (22, 23, 46) moves no order and is spec 0019's exchange parcel. A type 30 that never reaches 45 and ends returned to business (46) is `returned_to_origin` on the replacement (*unverified*: no recording of a refused exchange yet). The stale check of AC-20 runs on it like a send, comparing `receiver_address`, `receiver_phone`, `carrier_area`, and `cod` (Bosta's COD against the replacement's `cod_expected_amount`); `items_count` is not compared for type 30 until a recording shows what Bosta counts.

*Attention*
- **AC-22** (attention rules, revised for review M1, M2, M5, m3, m4): every followed forward delivery has at most one current attention kind, the first that holds in this order: `exception` (state 47), `on_hold` (105), `needs_action` (103 or 102), `route_before_confirmation` (20 on an order still `new`, D-1; a task only when the store's connection sends by hand, and under `app_sync_at_creation` a label read by spec 0017's card with no task, AC-32), `delayed` (Bosta's `isDelayed`), `repeated_attempts` (2 or more attempts), `stuck_at_pickup` (state 10 with the order `confirmed` or `packed`, longer than `bosta_stuck_at_pickup_hours`, default 48, measured from the later of Bosta's creation and the order's `confirmed_at`), `no_movement` (not picked up, at 11 or 20, no state change for longer than `bosta_no_movement_hours`, default 72), `stalled` (a send picked up and not final, no state change for longer than `bosta_stalled_hours`, default 48), `return_stalled` (a return to origin not yet at 46, no state change for longer than `bosta_return_stalled_hours`, default 96, owner decision Q-19.8); and for final deliveries `cash_cycle_overdue` (COD collected and no deposited cash cycle more than `bosta_cash_cycle_overdue_days`, default 14, after the final state, owner decision Q-19.7), then `cash_cycle_not_seen` once the 60 day cash window ended (weekly reads continue, AC-10). On spec 0020's `CarrierCashSettledByFile` for a delivery (by connection and tracking number), the connector sets `settled_by_file_at` and holds back both cash kinds for it (clearing a current one with `CarrierDeliveryAttentionCleared`); a later cash cycle read still records and publishes as AC-10 says. A delivery whose order is `new` gets no kind and counts on `/deliveries` as "waiting for confirmation"; an unlinked delivery gets only its unlinked flag; a cancelled order's delivery gets only `cancel_in_bosta`. Kinds are evaluated after each detail read and by the hourly check (so time based kinds hold as the clock moves) and shown live on read. A change of kind publishes `CarrierDeliveryNeedsAttention` (delivery, order, kind, since, `opensTask`) or `CarrierDeliveryAttentionCleared`; feature 17 turns each one with `opensTask: true` into one task per delivery and kind. `opensTask` is false, and so no `carrier.attention` task opens, only while `deliveries.carrier_failures` (spec 0019) is runnable, for a linked forward delivery, and only for the kinds `exception` and `repeated_attempts` (spec 0019's `delivery.failed_attempt` replaces them) and the flags `collected_differs` (`delivery.collection_differs`), `terminated_after_pickup` (`delivery.terminated_after_pickup`), and `no_longer_followed` (`delivery.outcome_overdue`); these kinds and flags still show as labels on `/deliveries` and the carrier panel. Every other kind and flag (`on_hold`, `needs_action`, `route_before_confirmation`, `delayed`, `stuck_at_pickup`, `no_movement`, `stalled`, `return_stalled`, `cash_cycle_overdue`, `cash_cycle_not_seen`, `cancel_in_bosta`, `duplicate_forward_delivery`, and unlinked) keeps `opensTask: true`. The connector reads runnability through `ModuleStateService.isRunnable` when it publishes. When a follow window ends on a delivery with an open kind, the kind becomes `no_longer_followed` and its task stays open, and a list pass that later sees a changed code on that delivery follows it again (review m4). The operational flags (`cancel_in_bosta`, `duplicate_forward_delivery`, `terminated_after_pickup`, `collected_differs`, and unlinked) are separate from the current kind and publish the same events with their own kind.

*Freshness, health, stock, and the exported contract*

The connection records its last webhook, last state change found, and last successful list pass. ### Decisions taken with spec 0017 (lane C agreements, 2026-11-12)

- **D-1 When a mirrored delivery freezes the order** (revised for review X1 item 2 and M5, owner decision Q-19.9). Orders learns that a delivery exists at its first link in any state, pickup requested included, through `OrderTransitions.recordCarrierDeliverySeen` (requested from spec 0013), so spec 0013's `delivery_created_before_edit_synced` and its cancel rule see it within one read cycle; this records no freeze. The money freeze (`recordCarrierDelivery`) happens at the first state from route assigned (20) on for an order already `confirmed` or `packed`; a 20 on a `new` order is recorded, raises `route_before_confirmation` (for support as a task when the connection sends by hand, as a card label under `app_sync_at_creation`, AC-32), and the freeze then waits for the order's confirmation (`OrderStateChanged` to `confirmed`) or the first pickup (21 or later), whichever comes first. It never happens at 10 or 11. Assumed: Bosta reaches 20 only when it routes a pickup, and the time from an auto synced creation to 20 is unknown (brand question 2 in Follow-up). Whether the brand's Bosta app creates deliveries on order creation (auto sync) or after confirmation by hand is one owner question, **Q-18.1 of spec 0017** (switch auto sync off and send manually after confirmation, or keep auto sync and accept stale COD); this spec asks no second one. D-1 works for both answers: with auto sync off a delivery appears after confirmation and nothing changes; with auto sync on the order stays editable while Bosta itself still lets the merchant change COD and address (S10 in [rationale.md](rationale.md#bosta-api-evidence)), and a COD difference is a stale carrier record (AC-20). Freezing at discovery instead would make confirmation edits impossible for an auto sync brand. Needs the spec 0002 orders child sentence amended (Follow-up); spec 0013's calls are used as they are.
- **D-2 The stale carrier record is order data.** The flag lives on the order and is written through the orders module (requested from spec 0013, *Calls this feature makes*); this connector decides when it is set and cleared, and publishes `CarrierRecordStale` (with the delivery's COD and tracking number) when it sets it and `CarrierRecordStaleCleared` when it clears it, in the same transaction. This spec's operations task to fix the delivery in Bosta (`carrier.record_stale`) comes first and closes with one outcome (`updated`, `recreated`, `cannot_update`, `cancel_recommended`), published as `CarrierRecordFixRecorded` and carried on the cleared event; spec 0017 then decides whether support reconfirms with the customer and what the agent says, and closes its reconfirmation as `cleared_by_carrier` when the flag clears (AC-30, from spec 0017's domain review M6). This spec and spec 0017 both ask spec 0013's `markPacked` to refuse an order whose flag is set.
- **D-3 Carrier areas.** This spec owns `carrier_areas` (Bosta cities, zones, and districts with their names and ids), loaded by a refresh job from Bosta's v2 area reads, with an operator import command as the fallback; spec 0017 uses it to fix an address into Bosta's areas (AC-29).

(b) Require one account per store. **Recommended: (a)**, spec 0007 gate decision 3.

(c) Only at the end of the 60 day window. **Recommended: (a)**: 14 days covers the weekly cash out Bosta gives small accounts (S12) with margin, and the brand tunes it once it knows its own cadence (brand question 8).

### Inbound processing

1. **Hook** (`@Audience('hook')`, `@RequiresModule('connectors')`, no permission): `mountHooks` routes `/api/hooks/bosta/<uuid>`, checks the connection before reading the body, reads at most 64 KB, compares the header (AC-4), then `BostaHookService` asks `acceptsHook` (AC-6), inserts the inbox row with the minimized payload, and sends a `bosta-inbox` job in one transaction (`send` with the `db` option), then answers 200. `last_inbound_at` moves at most every 30 seconds.
2. **Queue**: one pg-boss queue `connector-bosta` declared through spec 0009's `JobRegistry`, owned by `connectors.bosta.mirror_reads`; every job carries `data.capability` (discovery jobs `connectors.bosta.new_shipments`, reads `connectors.bosta.mirror_reads`, cash cycle reads `connectors.bosta.cash_cycle_sweep`) and every schedule a `key`; jobs are grouped per connection with `groupConcurrency: 1`. Priorities: inbox 20, reads 15, list pass 10, deep list 0.
3. **Inbox job**: finds or creates the delivery row (stub: tracking number only, priority 1), sets priority 1 and `next_read_at = now()`, marks the event `processed` with `read_queued`, and sends a `bosta-read` job with a singleton key per connection (repeats within 5 seconds add none). It applies no state.
4. **Read job** (`bosta-read.job.ts`): takes due rows (`next_read_at <= now()`) of its connection by priority and least recently read, honours the run budget (AC-9), reads each detail outside any transaction, parses it (AC-7), then per delivery opens `OrderTransactions.run` when the delivery is linked (else a plain transaction): locks its own row (`FOR UPDATE`), writes the mirror and its event rows, resolves the link (AC-12, AC-13), calls the orders moves of the *State mapping*, runs the carrier record check (AC-20, AC-21) and the attention rules (AC-22), publishes its events, and sets the next due time. A crash after the read leaves the row due; the retry reads again and the unique event key keeps every move once.
5. **List pass** and **deep list**: as AC-8; inserts new rows with priority 2 (`ON CONFLICT DO NOTHING` on the tracking number) and bumps changed ones to priority 3; moves the watermark only when the run completes.
6. **Hourly check**: evaluates time based attention kinds for every open forward delivery, retires rows past their follow window (`next_read_at = null`), retries links for `store_unknown` and `order_not_found` rows changed by a map edit, sets and clears `WEBHOOK_SILENT`, `SWEEP_LATE`, and `READS_FAILING`.

### Key invariants

- The connectors module is the only writer of `carrier_deliveries` and `carrier_delivery_events`; orders changes only through the named calls above.
- No Bosta call happens outside a `connector-bosta` job; at most one runs per connection; no call is anything but a GET on the allow list.
- Fees, cash cycle, state, attempts, and COD change only from a detail read; a list pass never writes them; a missing value never clears a stored one.
- Every order move comes from the order's one active forward delivery and happens at most once per (delivery, state, type, time, attempt).
- No order move happens while Bosta reports 10 or 11; the money freeze happens at the first state from 20 on (decision D-1).
- The stale check compares with `cod_expected_amount`, never `cod_due_amount`; no text says the app changed Bosta.
- An inbox row exists only for a verified call; its payload never holds a reason text or personal data.

### Security model

- Personal data (Law 151): detail reads carry the receiver's name, phone, and address; they pass through memory and are never stored by this feature (the order already holds the ship to fields); the carrier record check of AC-20 compares them in memory and stores only field names. `exception_reason` may hold courier text about a person: it is stored on the event row, read only through `attemptsOf` and the order page, never logged or published; the redaction list gains `exceptionReason`, `receiver`, `dropOffAddress`, `pickupAddress`, `apiKey`, and `webhookKey` (`packages/config/src/redaction.ts`).
- The hook is public by necessity and proves itself only by the shared header; it reveals nothing about which connections exist. Bosta documents no signature (S1); a stolen header value lets someone queue reads of tracking numbers, never write state, because every fact is read back from Bosta. Rate limiting at the edge is feature 26's.
- Connect, keys, the webhook value, mapping, the COD rule acknowledgement, pause, resume, archive: `settings.manage`. Deliveries list, carrier panel, read now: `orders.view`. Unlinked deliveries, link by hand, failed reads and their retry, record fix, and the latest attempt reason: `orders.confirm` (review M4).
- Audit (spec 0010 registry additions, English and Arabic labels, proof tests): `connection.webhook_key_revealed`, `connection.webhook_key_rotated` (reason required), `carrier_delivery.linked_by_person` (reason code), `carrier_delivery.record_fix_recorded` (reason code), `carrier_areas.imported`, `connection.cod_rule_acknowledged` (reason required), and the existing `connection.created`, `connection.edited`, `connection.credentials_replaced`, `connection.paused`, `connection.resumed`, `connection.archived`. New record type `carrier_delivery` (label the tracking number). Entries never hold a key.

## Consequences

**Positive**:
- Bosta's rate limit can never stall the mirror: every call has a priority, a spacing, and a budget, and a burst of webhooks only reorders the queue.
- Fees and cash cycles are always the delivery's own detail figures, so spec 0020 can match a real month line by line.
- A confirmation edit after Bosta holds the delivery is visible within a minute with honest instructions for that state, which closes audit item 9 without any write to Bosta.
- Specs 0019 and 0020 get one service and a set of events and never call Bosta.

**Negative / tradeoffs**:
- The mirror lags Bosta by up to a webhook plus one read (2 to 10 minutes), and by up to 75 minutes when a webhook is lost on an older delivery.
- Decision D-1 changes when the money freeze happens in mirror mode: orders stay editable while Bosta reports pickup requested, so the carrier record can go stale and needs a person; spec 0002's orders child must be amended.
- The webhook is protected only by a shared header (Bosta documents no signature); the read back rule limits the damage to wasted reads.
- Several Bosta facts are unverified (exception codes, state 48 after forward attempts, partial delivery, the v2 list); the design records them without moving the order until a recording or spec 0019 proves them.
- A table moves out of orders' planned ownership (Q-19.1), which spec 0002's A5 table must reflect.

**Neutral**:
- `carrier_delivery_events` grows by a few rows per delivery and is never purged by this feature.
- The fixtures are synthetic until the brand's Read Only key exists; the feature is not done until they are recorded.
