# 0003. Reset the migrations to one baseline

- **Status**: accepted
- **Date**: 2026-11-05
- **Spec**: [0002 Core data model, tenancy and platform](../specs/0002-core-data-model/0002-tenancy-platform.md) (section "Migration baseline and the app role name")

## Context

The database package has nine migrations, `0000` to `0008`, with their Drizzle `meta` snapshots. Feature 4 adds tenancy, a tenant column on every table, new extensions, triggers, and grants that name the app role. No install runs the current history: there is no client extension and no client environment yet, and the pilot brand starts after slice 1a (spec 0007 open question 1). So there is no live data to move and nothing that must apply from an old version.

Two facts shape the new history:

- Drizzle regenerates the SQL it owns. Any hand written statement placed in a generated file is lost or conflicts the next time `drizzle-kit generate` runs, so hand written SQL must never share a file with generated SQL.
- Roles are global to a PostgreSQL server, and spec 0007 gives each client its own app role name (`ssd_<client>_app`). A migration that hard codes `ssdashboard_app` would need to change per client.

Options considered:

- **Keep the nine migrations and add a tenant migration.** Rejected: it spreads one change over expand and contract steps across nine files for data that does not exist, and the old history carries rules that the new schema would immediately undo.
- **One single baseline file.** Rejected: generated and hand written SQL would be mixed, and Drizzle would overwrite the hand written part.

## Decision

We will replace migrations `0000` to `0008` and their `meta` snapshots with one baseline of three files, kept apart by who writes them:

- `0000_baseline_extensions.sql`: hand written; `pg_trgm`, `unaccent`, and `btree_gist`.
- `0001_baseline_tables.sql`: generated by `drizzle-kit generate` only and never edited by hand.
- `0002_baseline_rules.sql`: hand written, started with `drizzle-kit generate --custom`; the functions, triggers, grants, revokes, seeds, and the `pgboss` schema.

Grants and revokes read the app role name from the database setting `ssd.app_role`, falling back to `ssdashboard_app` when it is unset, so a per client role name needs no migration change. Inside feature 4 only `0001` is regenerated as the schema grows; the two hand written files are edited directly.

**The baseline freezes the day the pilot brand's first import runs.** From then on the three files are never edited, and every change is a new forward migration that follows expand and contract (`packages/db/AGENTS.md`).

## Consequences

- Developers recreate their dev database once: `docker compose -f deploy/compose.dev.yaml down -v`, then `pnpm bootstrap`. `pnpm bootstrap` detects a database migrated by the old history and stops with that instruction instead of failing halfway. CI starts from an empty Postgres service and needs no step. The step is also in the [root README](../../README.md).
- A reader can tell at a glance which file may be edited by hand and which one only Drizzle writes.
- Before the freeze, an edit to a baseline file is allowed but means every developer recreates their database again; after the freeze it is forbidden.
- A restore needs `pg_dump --create`, or the two database settings (`ssd.tenant_id`, `ssd.app_role`) reapplied from the `install` row, because a plain dump leaves out `ALTER DATABASE` settings. Feature 27 owns that step.
- Rolling back means reverting the commit and recreating the dev database again.
- Follow up: `packages/db/test/migrate.e2e-spec.ts` is updated in the same milestone, and the freeze date is noted here when the pilot import runs.
